# 流程平台技术路线 v5

版本：v0.5
范围：① 流程平台。本文档根据需求文档 11.2 流程平台验收重新整理，第一阶段目标即完成流程平台验收，不以端到端 11.4 作为本阶段验收范围；数据库验收只覆盖 SQLite，不展开 Oracle 或国产数据库适配。

## 1. 第一阶段目标

第一阶段由三名实习生共同完成 ① 流程平台。验收范围以需求文档 11.2 为准：

1. 能创建一个包含开始、申请、审批、结束的流程定义。
2. 流程定义可以完成校验、发布、激活。
3. 用户可以发起流程并生成首个活动任务。
4. 审批人可以处理待办并推动流程流转到下一节点。
5. 流程结束后可以查到完整历史轨迹。
6. 可以查询待办、办结、我发起的流程三类基础列表。
7. 至少具备终止流程和删除流程两项基础管理能力。
8. 能支持驳回、撤回、加签、转办、委托代办等动作。
9. 能支持并行、会签、或签、条件分支等场景。
10. 能支持任意节点跳转和强制办结等运维操作。
11. 关键动作后能触发回调并携带归档任务和新建任务信息。
12. 能以 Starter 形态被业务代码嵌入，也能独立运行。
13. 至少能在 SQLite 上完整运行；第一阶段不做 Oracle 和国产数据库适配。

## 2. 入金申请基准流程说明

需求文档中的入金申请流程结构为：

```text
开始 → 申请节点 → 部门经理审批 → 财务确认 → 结束
```

平台运行时按以下方式理解：

1. 业务员在前端录入页填写申请人姓名、入金金额、入金账号等表单字段，并上传银行回单。
2. ③ 后端通过 Starter 调用 `startAndSubmit` 启动流程实例，平台保存流程变量并生成首个活动任务：申请节点。
3. `startAndSubmit` 返回实例信息和申请节点任务标识。
4. 若业务前端一次提交了银行回单，③ 后端在同一个业务提交动作中继续调用 `submitTask` 办理申请节点，银行回单作为申请节点附件参与附件模板校验。
5. 申请节点办理后写入历史任务。
6. 平台创建部门经理审批任务。
7. 部门经理审批通过后创建财务确认任务。
8. 财务确认通过后流程结束。

因此，首个活动任务是申请节点；申请节点需要进入历史轨迹。平台不把入金业务逻辑写入引擎，业务适配层只负责把一次前端提交拆成平台 Starter 调用序列。

## 3. 技术路线

### 3.1 实现方式

流程平台采用轻量流程引擎实现，不引入完整 BPMN 引擎。

核心方式：

- 流程定义保存节点、连线、审批人规则、表单字段、附件模板。
- 流程实例保存流程变量和运行状态。
- 活动任务保存当前待处理任务。
- 历史任务保存已经办理过的任务轨迹。
- 附件模板约束申请节点或任务节点上传材料。
- 回调记录关键动作后的归档任务和新建任务。

### 3.2 模块划分

```text
flow-mind
└── platform
    ├── platform-core       # 平台主体：API 合约、核心逻辑、SQLite 持久化、REST 适配、本地 Mock
    └── platform-starter    # Spring Boot Starter 自动装配
```

原则：

- `platform-core` 是第一阶段主体模块，不出现具体业务概念。
- `platform-starter` 是业务运行期调用平台的入口。
- DTO、枚举、Service 接口、SPI 接口不单独拆 `platform-api`，先作为 `platform-core` 的 `api` 包维护，避免接口与实现分离过早导致三人协作成本上升。
- SQLite 是第一阶段唯一实际运行数据库，表结构、Repository、SQL 直接放入 `platform-core` 的 `persistence` 包；只有后续需要 Oracle、国产数据库等多实现适配时，才拆 `platform-persistence`。
- 本地 Mock 是验收和调试辅助能力，放入 `platform-core` 的 `mock` 包；只有 Mock 需要作为独立测试工具包复用时，才拆 `platform-mock`。
- REST Controller 是平台调试和独立运行的适配层，先放入 `platform-core` 的 `web` 包；只有独立服务需要单独发布、单独依赖 Web 容器或与 Starter 发布节奏分离时，才拆 `platform-web`。
- 本地演示场景优先通过集成测试、临时启动类或业务侧样例应用承接；只有演示应用需要长期维护独立启动配置和演示数据时，才拆 `platform-demo`。
- REST Controller 与 Starter 共用同一套 Service，不重复实现流程逻辑。
- 文件内容不直接存数据库，附件元数据存平台，文件内容走文件存储 SPI。
- 附件同时支持实例级附件和任务级附件；入金申请银行回单在申请节点上传，并作为流程实例级材料供后续审批人查看。

### 3.3 技术选型

| 类别       | 建议                                                               |
| ---------- | ------------------------------------------------------------------ |
| 后端语言   | Java 8（JDK 1.8）                                                   |
| 框架       | Spring Boot 2.7.18（适配 Java 8；不使用 Spring Boot 3.x）          |
| 构建       | Maven 多模块，Maven 建议 3.5+                                      |
| 数据库     | SQLite 文件数据库                                                  |
| 持久化     | MyBatis 或 Spring JDBC                                             |
| 数据库同步 | 三人通过复制 SQLite 数据库文件同步                                 |
| 表结构管理 | 保留简单建表 SQL 说明，不引入复杂迁移工具                          |
| 数据库范围 | 第一阶段实际运行验收以 SQLite 为准，不做 Oracle 和国产数据库适配     |
| 测试       | JUnit 5、Spring Boot Test、SQLite 集成测试                         |

Java 8 编码约束：

- 不使用 Java 9+ API 或语法，例如 `List.of`、`Map.of`、`Stream.toList`、`Optional.isEmpty`、`Path.of`、`var`、`record`、switch 表达式。
- Spring 相关包使用 Spring Boot 2.x / Spring Framework 5.x 体系，避免使用 Spring Boot 3.x 引入的 Jakarta EE 命名空间迁移内容。
- Controller、Starter、SPI、DTO 均按 Java 8 可编译代码编写。

## 4. 三人并行协作方式

三人都参与 ① 流程平台，不按“一个人单独负责一整块”切分。为了让三人能同时推进，采用三条并行工作线：

| 阶段              | 实习生 A                                         | 实习生 B                                                            | 实习生 C                                                              | 阶段产出             |
| ----------------- | ------------------------------------------------ | ------------------------------------------------------------------- | --------------------------------------------------------------------- | -------------------- |
| M0 契约冻结       | 数据模型、流程状态设计                           | 运行时DTO、动作结果DTO                                             | SPI接口、Starter接口、回调事件模型、入金申请验收用例                  | 接口基线、测试基线   |
| M1 流程定义       | 流程定义 CRUD、流程复制、节点/连线管理、版本管理 | 发布校验、流程图解析、定义加载缓存                                  | 表单字段、附件模板                                                    | 可发布流程定义       |
| M2 运行时闭环     | 审批规则解析、节点配置读取                       | 启动实例、变量保存、任务创建、审批通过结束判断、历史任务归档        | 审批意见、流程轨迹、回调记录、实例详情查询、运行状态验证              | 串行流程跑通         |
| M3 查询与 Starter | 流程发布、激活、停用、归档、灰度发布             | 流程实例管理（删除、终止）、流程状态维护                            | 待办、已办、我发起、活动任务查询、Starter自动装配、本地验收用例、集成测试 | 可嵌入、可独立运行   |
| M4 SPI 与附件     | 组织架构SPI、审批人解析SPI                       | 附件运行时管理（实例附件、任务附件、权限校验）                      | 文件存储SPl、附件元数据、消息推送SPI、Mock实现                        | 附件与审批人解析跑通 |
| M5 增强动作       | 节点监听配置、条件表达式配置、会签/或签配置、驳回/直送规则 | 驳回、撤回、转办、加签及历史归档                         | 委托代办、认领/取消认领、审计日志、已阅、提醒、回归测试              | 常用审批动作可用     |
| M6 高级流转       | 条件分支、或签                                   | 会签                                                              | 并行汇聚、管理员修复、超时处理、催办、异常告警                        | 高级能力可演示       |

协作规则：

- 三条线同时编码。
- 每天合并一次主干，避免最后集中集成。
- A 先提供最小流程定义和任务模型，B、C 基于模型并行开发。
- B 新增动作时，必须同步 C 线补查询和回调字段。
- C 新增 SPI 或附件字段时，必须同步 A、B 两线调整调用。
- 回调事件模型在 M0 冻结；从 M2 开始，每个会改变活动任务的动作都必须同步产生日志和回调事件。
- 每个功能完成后都要补一个验收场景。

## 5. 编码计划

### 第 1 步：共同冻结模型和接口

三人同时完成：

- 核心枚举：节点类型、实例状态、任务状态、动作类型、审批人规则。
- 核心表：流程定义、节点、连线、实例、活动任务、任务组、历史任务（含审批意见）、已阅、附件模板、附件记录、回调记录、审计日志、提醒记录、异常告警记录。
- Starter Service 接口。
- 独立 REST API 草案。
- 回调事件模型、提醒/超时/告警接口草案。
- 入金申请流程定义样例。

完成标准：

- 工程可以编译。
- SQLite 数据库可创建基础表。
- 能保存入金申请流程定义。

### 第 2 步：流程定义与发布激活

A 线主做，B、C 同步联调：

- 创建流程定义。
- 保存节点、连线、坐标、顺序。
- 保存审批人规则。
- 保存表单字段。
- 保存附件模板。
- 发布前校验。
- 发布、激活、停用。
- 归档流程定义。
- 配置灰度发布规则、关闭灰度。
- 复制、删除、查询流程定义。

完成标准：

- 能创建、校验、发布、激活入金申请流程定义。
- 能对流程定义执行停用、归档、灰度发布和关闭灰度。
- 发布前校验能拦截缺少开始节点、结束节点、孤立节点、用户任务无审批人的情况。

### 第 3 步：实例启动与申请节点

B线主做，C 线配合附件，A 线配合任务动作：

- 启动流程实例。
- 保存流程变量。
- 创建首个活动任务：申请节点。
- 返回申请节点任务标识，供业务适配层继续办理申请节点。
- 业务员办理申请节点。
- 申请节点校验银行回单附件模板。
- 申请节点归档为历史任务。
- 创建部门经理审批任务。
- 触发流程发起、任务创建、申请节点完成、部门经理任务创建等回调事件。

完成标准：

- 发起入金申请后可以查到申请节点活动任务。
- 办理申请节点时必须上传银行回单。
- 银行回单格式限制为 `pdf/jpg/png`，大小限制为 `10MB`。
- 申请节点写入历史任务。
- 一次业务提交可以由业务适配层串联 `startAndSubmit` 与 `submitTask` 完成，不要求平台感知入金业务。
- 关键动作产生回调记录。

### 第 4 步：基础审批流转

B 线主做，A、C 配合：

- 审批通过。
- 活动任务归档。
- 创建下一节点任务。
- 到达结束节点后实例办结。
- 任务归档时将审批意见写入历史任务。
- 查询完整历史轨迹。
- 触发任务完成和任务创建回调。

完成标准：

- 入金申请可以从申请节点流转到部门经理审批，再到财务确认，最后结束。
- 办结后无活动任务。
- 历史任务包含申请节点、部门经理审批、财务确认。

### 第 5 步：查询能力

C 线主做，A、B 提供数据：

- 查询待办。
- 查询办结。
- 查询我发起的。
- 查询活动任务。
- 查询历史任务。
- 查询审批意见。
- 支持分页。
- 支持按流程编码、流程名称、标题、发起人、时间范围、状态过滤。
- 待办列表区分本人任务和委托代办任务。

完成标准：

- 满足 11.2 中待办、办结、我发起三类基础列表。
- 流程结束后可查完整轨迹。

### 第 6 步：管理动作

A、B 并行，C 补查询和审计：

- 终止流程。
- 删除流程定义或流程实例。
- 任意节点跳转。
- 强制办结。
- 管理员查询流程定义、实例、任务、历史任务。
- 流程定义版本治理：发布、停用、归档、灰度发布和关闭灰度。

完成标准：

- 终止后活动任务被清理。
- 删除流程定义时级联删除该定义下的节点、连线、表单字段、附件模板、实例、活动任务、任务组、历史任务（含审批意见）、已阅、附件记录等运行数据。
- 删除流程实例时同步删除关联活动任务、任务组、历史任务（含审批意见）、已阅、附件记录等运行数据。
- 审计日志和回调日志默认保留，并标记目标已删除，便于排查。
- 跳转和强制办结能写入历史或审计记录。

### 第 7 步：审批动作补齐

B 线主做，A、C 配合：

- 驳回。
- 撤回。
- 加签。
- 转办。
- 委托代办。
- 认领和取消认领。
- 直送。

完成标准：

- 每个动作都能正确更新活动任务和历史任务。
- 每个动作都能触发回调。
- 特殊动作可在历史或审计中追溯。

### 第 8 步：并行、会签、或签、条件分支

B 线主做，A 线补定义配置，C 线补查询：

- 条件分支：根据流程变量选择后续连线。
- 或签：多个候选人中任一人办理后节点完成。
- 会签：多个审批人全部办理后节点完成。
- 并行：一个节点可以创建多个后续分支任务。
- 汇聚：多个分支满足后继续后续流转。

完成标准：

- 具备独立测试流程验证每类场景。
- 查询结果能反映当前节点和活动任务。

### 第 9 步：SPI、附件、提醒与告警

C 线主做，A、B 接入：

- 当前用户 Mock。
- 组织架构 Mock。
- 审批人解析 SPI。
- 委托关系 SPI。
- 消息推送 SPI。
- 文件存储 SPI。
- 消息推送或回调 Mock。
- 手动催办与自动提醒。
- 超时任务扫描。
- 异常告警记录与处理。

完成标准：

- 审批人可按指定用户、发起人、部门、角色、表达式解析。
- 文件内容通过文件存储 SPI 保存。
- 附件元数据保存在平台。
- 支持实例级附件和任务级附件。
- 能查询提醒记录和异常告警记录。
- 超时任务能产生提醒或告警，且通过消息推送 SPI 或 Mock 发送。

## 7. 质量门禁

每次合并前检查：

- 平台代码不出现具体业务逻辑。
- 业务表单值只作为流程变量保存。
- 首个活动任务为申请节点。
- 申请节点必须写入历史任务。
- 银行回单按附件模板校验。
- 文件内容不直接存数据库。
- Starter 和 REST 共用同一套 Service。
- 活动任务变化必须有历史或审计记录。
- 关键动作必须触发回调。
- 回调失败不能影响主流程。
- 查询接口必须分页。
- 删除流程定义或实例必须覆盖任务组、历史任务（含审批意见）、已阅、附件记录等关联运行数据。
- 提醒、超时和异常告警必须有记录可查。
- 第一阶段只要求 SQLite 完整运行，不做多数据库适配。

## 8. 第一阶段完成定义

满足以下条件，视为 ① 流程平台第一阶段完成：

- 能创建、复制、删除、查询流程定义。
- 能发布、激活、停用、归档流程定义，并支持灰度发布。
- 能启动流程实例并生成申请节点活动任务。
- 能办理申请节点，并按附件模板校验银行回单。
- 能完成串行审批并办结。
- 能查询待办、办结、我发起的流程。
