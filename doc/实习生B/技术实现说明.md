# 实习生 B 技术实现说明

本文件记录已落地的技术契约，避免与实施计划重复。后续 M1～M6 按阶段追加实际实现说明。

## M0：运行时请求契约

### 位置与边界

- 代码包：`com.flowmind.platform.api.request`，位于 `platform-core`。
- 使用 Java 8 JavaBean：公开无参构造及标准 getter/setter；可手写访问器，也可使用 Lombok `@Data`，禁止使用 `record` 或 Java 9+ API。
- M0 不包含流程流转、持久化、SPI、Starter 自动装配、事件或输入校验逻辑。

### 请求继承

```text
OperationRequest
├─ 实例级请求
│  ├─ StartProcessRequest
│  ├─ UpdateVariablesRequest
│  ├─ TerminateProcessRequest
│  ├─ DeleteProcessInstanceRequest
│  ├─ JumpNodeRequest
│  └─ ForceCompleteRequest
└─ TaskOperationRequest
   ├─ SubmitTaskRequest
   ├─ ApproveTaskRequest / RejectTaskRequest / ReturnTaskRequest
   ├─ WithdrawTaskRequest / DirectSendRequest
   ├─ TransferTaskRequest / AddSignRequest
   └─ ClaimTaskRequest / UnclaimTaskRequest / RemindTaskRequest
```

- `OperationRequest`：`operationId`，所有状态修改请求共用。
- `TaskOperationRequest`：继承 `OperationRequest`，增加 `taskId`、`expectedTaskVersion`（`Long`）、`operatorUserId`、`comment`。
- `JumpNodeRequest` 是实例级请求，只含实例 ID 与目标节点等字段，不继承任务基类，也不携带任务版本。

### 关键字段

| 类型 | 已冻结字段 |
| --- | --- |
| `StartProcessRequest` | 流程编码、业务键、实例标题、发起人、发起部门、变量 |
| `UpdateVariablesRequest` | 实例 ID、操作人、变量 |
| `SubmitTaskRequest` | 任务基类字段、变量、`List<AttachmentUploadItem>` |
| 定向动作 | 驳回、直送、跳转使用 `targetNodeCode`；转办使用 `targetUserId`；加签使用 `addSignUserIds` |
| 实例操作 | 终止、删除、跳转、强制办结均包含 `instanceId`；需要操作人/意见的请求显式携带相应字段 |
| `AttachmentUploadItem` | 附件模板编码、归属类型、文件名、内容类型、大小、`byte[] content` |

`AttachmentUploadItem` 位于 `com.flowmind.platform.api.request`，是上传请求的内存载荷，不表示文件存入 SQLite；后续实现须通过文件存储 SPI 保存实际内容。

### 契约测试

- `OperationRequestContractTest` 验证两个请求基类的继承与 JavaBean 属性。
- `RuntimeRequestContractTest` 在 B0.2/B0.4 为原计划 17 个运行时修改请求提供有效夹具；B0.5 接入 A/C 契约后又纳入实例附件保存、任务附件保存、附件删除和告警处理 4 类请求；后续补充会写入提醒/告警的超时扫描请求，当前共覆盖 22 类。所有夹具统一验证 `operationId`，任务级请求额外验证 `taskId`、`expectedTaskVersion`、`operatorUserId` 和 `comment`。
- 测试覆盖每个请求的专有字段，并独立验证 `AttachmentUploadItem` 的全部六个属性及二进制内容。
- 验证命令：`mvn -q -pl platform/platform-core -am test`。

### 夹具汇总与覆盖门禁（B0.4）

- `RuntimeRequestContractTest` 以 17 个计划内运行时修改请求的类型集合为清单，并与参数化夹具的类型集合比较；集合不一致或出现重复夹具时测试失败。
- 每个请求夹具都需提供非空 `operationId`；任务级夹具还需提供 `taskId`、`expectedTaskVersion` 和 `operatorUserId`。`JumpNodeRequest` 单独断言不继承 `TaskOperationRequest`。
- `RuntimeResultContractTest` 保持对 `TaskActionResult.archivedTasks`、`createdTasks` 和 `replayed` 的验证。测试只验证 DTO 可表达性，不引入运行时幂等、版本校验或流程执行逻辑。

### 运行时结果 DTO（B0.3）

- 代码包：`com.flowmind.platform.api.dto`，同样采用 Java 8 JavaBean。
- `ProcessInstanceDTO` 表达实例标识、定义与流程信息、发起信息、正式实例状态、当前节点、变量、起止时间和创建出的 `TaskDTO` 列表。
- `TaskDTO` 表达节点、候选人、受理人、委托人、任务组/分支、正式任务状态、`taskVersion` 及时间字段；`HistoryTaskDTO` 表达归档任务、办理方式、动作类型、操作关联、变量快照、意见和完成时间。
- `TaskActionResult` 聚合 `operationId`、实例、归档/新建任务及重放标识；`OperationResult` 表达操作号、目标 ID、删除和重放标识。
- `RuntimeResultContractTest` 覆盖上述 DTO 的 JavaBean 属性、任务版本、任务归档/创建关系与操作结果标识；附件上传项由 `RuntimeRequestContractTest` 独立覆盖。
- 实例/任务状态、历史任务办理方式与动作类型、`OperationResult.targetType` 已全部使用正式枚举，不保留 `String` 兼容字段。

### 与 A 的模型及乐观锁契约对齐（B0.5）

- 本地 `feature/m0-b-dto-contract` 先快进到 `origin/develop@376dfd0`，再合并定义管理动作提交至 `origin/develop@3f0ffa3`；当前基线包含 A/B/C 的共享契约、SPI、Starter Service 接口和测试基线。
- `process_active_task` 仅通过 `definition_id` 关联具体流程定义，不重复保存定义版本；SQLite Schema、`ProcessActiveTaskEntity` 和 `TaskDTO` 均不包含 `version`。实例自身仍通过 `process_instance.version` 和 `ProcessInstanceDTO.version` 保存启动时的定义版本快照。
- `TaskDTO.taskVersion` 为 `Long`，对应 `ProcessActiveTaskEntity.lockVersion`；任务级请求通过同为 `Long` 的 `TaskOperationRequest.expectedTaskVersion` 原样回传该值。
- `RuntimeResultContractTest` 通过反射冻结 `ProcessInstanceDTO.version`、`TaskDTO.taskVersion`、`HistoryTaskDTO.operationId/comment` 与 A 持久化实体及任务请求的对应字段类型，同时继续以真实 setter/getter 调用验证 Lombok 生成的 JavaBean 契约。
- `FlowPlatformSchemaTest.activeTaskReferencesDefinitionWithoutDuplicatingItsVersion` 使用 `PRAGMA table_info(process_active_task)` 正向断言 `definition_id/lock_version`、反向断言不存在 `version`；Repository 集成测试按删除后的六列活动任务结构插入数据。
- `RuntimeRequestContractTest` 的当前唯一清单包含 22 类运行时/外围修改请求；相较 B0.4 的 17 类历史基线，B0.5 新接入 `SaveInstanceAttachmentRequest`、`SaveTaskAttachmentRequest`、`DeleteAttachmentRequest` 和 `HandleAlertRequest`，后续又纳入 `TimeoutScanRequest`。五类均提供非空 `operationId`，其中任务级的 `SaveTaskAttachmentRequest` 还提供 `expectedTaskVersion`。
- 已执行 `mvn -q -pl platform/platform-core -am test` 和根目录 `mvn -q test`；合并后联合测试共 139 项通过，0 失败、0 错误、0 跳过，子 agent 终审未发现阻断问题。
- `001_init_flow_platform.sql` 使用 `CREATE TABLE IF NOT EXISTS`，已由旧脚本创建的本地 SQLite 库不会自动删除原列；M0 未引入迁移框架，需要重建旧本地库后再验证新结构。
- B0.5 已完成正式枚举、公共 SPI 分层、附件授权失败关闭、`WorkflowEvent`/回调 DTO 单一契约及重复字段清理，并通过联合测试与逐项子 agent 审查。

### 公共 SPI 数据契约分层（B0.5）

- `AttachmentUploadItem` 是请求的嵌套二进制载荷，位于 `api.request`。
- `FileContent`、`StoredFile` 是文件存储 SPI 的读取/写入结果，`ProcessMessage` 是消息发布 SPI 的传输载荷，三者均位于 `api.dto`。
- `persistence.entity` 仅承载数据库映射实体；公共 `api.spi` 方法签名不得依赖该包。
- `PublicSpiContractTest` 通过反射冻结 `FileStorageProvider` 和 `MessagePublisher` 的公共参数、返回值，并拒绝暴露持久化包类型。

### 正式枚举收口（B0.5）

- 直接复用现有 `InstanceStatusEnum`、`TaskStatusEnum`、`ActionTypeEnum`、`DefinitionStatusEnum`、`ActivationStatusEnum`、`GrayStatusEnum`、`NodeTypeEnum`、`ApproverRuleTypeEnum`、`MultiInstanceModeEnum`、`AttachmentOwnerTypeEnum` 和 `WorkflowEventTypeEnum`。
- v4 已冻结有限值且目录中确实没有同义枚举的字段，新增 `HandleTypeEnum`、`OperationTargetTypeEnum`、`AttachmentConfigStatusEnum`、`AttachmentTemplateStatusEnum`、`ReminderTypeEnum`、`AlertTypeEnum`、`AlertSeverityEnum`。
- `FormalEnumContractTest` 冻结 21 个公共字段的声明类型及新增枚举值；`AuditLogDTO` 与 `AuditLogQuery` 统一通过 `OperationTargetTypeEnum + targetId` 表达流程定义、实例、任务或附件目标。
- `ProcessFormFieldDTO.fieldType/controlType` 是可演进的前端元数据，`ProcessMessage.messageType` 是宿主扩展类别；二者没有核心枚举闭集，继续使用 `String`。
- `WorkflowEvent.eventType` 和 `CallbackLogDTO.eventType` 以 `WorkflowEventTypeEnum` 为唯一 Java 契约；删除字符串重载、适配 setter、code getter 及枚举 `fromCode` 方法。序列化边界直接使用枚举名称，持久化实体仍可按数据库列保存字符串并在映射层显式转换。
- 回调失败信息严格映射 v4 的 `process_callback_log.last_error`：`CallbackLogDTO` 仅公开 `lastError`，不再维护会造成双字段序列化和状态同步的 `errorMessage` 别名。
- 定义管理动作由 `DefinitionActionTypeEnum` 表达，写入日志时转换为 `DEFINITION_*`；运行时动作仍来自 `ActionTypeEnum`。为统一 `process_operation_record` 与 `process_audit_log` 的单列存储，`OperationRecordDTO.actionType` 和 `AuditLogDTO.actionType` 使用 `String`，并提供原始字符串及两类枚举的重载 setter。
- 合并 `AuditLogDTO` 时保留 `OperationTargetTypeEnum targetType` 与 `targetId`，因此定义管理审计同时具备规范动作值和明确目标；`OperationLogContractTest` 覆盖运行时动作、定义动作、字符串存储和目标字段。
- 三个同名 setter 会让源码调用 `setActionType(null)` 时产生重载歧义，调用方需显式指定类型；原始 `String` 入口的合法性由上层映射和 Schema 约束保证，M0 不额外引入运行时校验。
- SQLite CHECK 约束已接受完整 `DEFINITION_*` 动作集合；旧数据库因 `CREATE TABLE IF NOT EXISTS` 不会自动更新，需要重建或迁移后使用。

### 附件访问失败关闭（B0.5）

- Starter 始终为缺失的 `AttachmentAccessProvider` 注册拒绝全部访问的后备实现；关闭本地 Mock 不会产生隐式放行。
- `AttachmentAccessGuard` 是附件 Service 的统一授权边界，只有 SPI 明确返回 `true` 才允许继续；SPI 缺失、返回拒绝或抛出运行时异常均返回 `false`。
- 单元测试分别覆盖缺失、拒绝、异常和明确允许；附件业务实现必须在调用 `FileStorageProvider` 之前通过 Guard。

### 已知阶段边界

- M0 的夹具只证明 DTO 可表达有效请求，不代替运行时非空、权限、幂等或乐观锁校验。
- 运行时校验、幂等执行、任务状态变更、附件 SPI 调用和数据库操作留待后续阶段实现。
