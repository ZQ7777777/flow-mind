### B0.2 说明

- `AttachmentUploadItem` 是提交任务和保存附件请求的嵌套输入，固定放在 `api.request`；它不属于查询结果或持久化实体，二进制载荷只由请求契约测试覆盖。
- 本阶段仅冻结 DTO 契约；不实现流程流转、Repository、SQLite、SPI、Starter、事件或运行时参数校验。

### B0.3 说明

- 结果 DTO 已冻结实例、任务、历史任务及操作结果的非枚举字段；`ProcessInstanceDTO.createdTasks`、`TaskDTO.taskVersion`、归档任务和重放/删除标识均有契约测试。
- 实例/任务状态、历史任务的处理类型与动作类型、操作结果目标类型必须等待 C 提供正式枚举后以枚举类型对齐；未以 `String` 临时替代，也未创建兼容别名。

### B0.4 说明

- `RuntimeRequestContractTest` 将计划内 17 个运行时修改请求列为唯一清单，并断言每种请求恰有一个参数化有效夹具；防止生产请求未进入契约测试或夹具重复。
- 每个夹具验证非空 `operationId`；任务级夹具额外验证已赋值的 `expectedTaskVersion`；`JumpNodeRequest` 继续明确为实例级请求。结果 DTO 测试持续覆盖归档任务、新建任务和 `replayed` 的表达能力。

### B0.5 说明

- 已将本地 `feature/m0-b-dto-contract` 快进同步到只包含 A/B 代码的最新远程 `develop`，同步过程无冲突。
- `process_active_task` 通过 `definition_id` 关联具体流程定义，不再重复保存 `version`；已从 SQLite Schema、`ProcessActiveTaskEntity`、Repository 测试插入语句和 `TaskDTO` 删除对应字段。`process_definition.version` 与 `process_instance.version` 保持不变。
- `TaskDTO.taskVersion` 继续使用 `Long` 对齐 `ProcessActiveTaskEntity.lockVersion` 和 `TaskOperationRequest.expectedTaskVersion`；`FlowPlatformSchemaTest` 通过 `PRAGMA table_info` 断言活动任务表保留 `definition_id/lock_version` 且不存在 `version`。
- `RuntimeResultContractTest` 保留 A 实体、B DTO 与任务请求之间的字段类型冻结断言；`TaskDTO` 使用 Lombok `@Data`，仍通过无参构造和标准访问器契约验证。
- 子 agent 两轮独立审查分别检查初次A/B对齐和删除冗余字段后的最终契约，均确认字段映射、Java 8/Lombok兼容性、测试范围和职责边界无阻断问题。
- 初始化脚本使用 `CREATE TABLE IF NOT EXISTS`，旧脚本创建的本地 SQLite 库不会自动删除原列；M0 未引入迁移框架，继续使用旧库前需要重建。
- 已同步 C 的枚举、事件、SPI、Starter Service 接口和幂等测试基线；正在按公共文档逐项完成最终契约收口。
- `FileContent`、`StoredFile`、`ProcessMessage` 是 SPI 方法签名使用的公共数据契约，已从 `persistence.entity` 移至 `api.dto`；`PublicSpiContractTest` 防止公共 SPI 再暴露持久化类型。
