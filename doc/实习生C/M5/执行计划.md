# 实习生 C：M5 执行计划

> 编制日期：2026-07-27  
> 范围：委托待办收口、认领/取消认领、已读记录、统一审计、手动催办、提醒/告警查询与处理、M5 回归测试。  
> 代码范围：`platform-core`、`platform-starter`。  
> 依赖边界：B 线 M5 已负责 `reject/return/withdraw/directSend/transfer/addSign` 增强动作；C 线 M5 不重复实现这些动作，只补齐其审计、查询、待办展示和回归验证。

## 1. 阶段目标

M5 的核心目标不是再建一套流程运行时，而是在现有 M0-M4 基线上补齐外围可追溯能力：

1. `claim/unclaim` 从阶段占位改成正式运行时动作，支持幂等、任务版本 CAS、历史记录、审计、回调和返回最新任务版本。
2. 委托代办在待办查询中收口，确保本人、候选人、委托人任务不会重复展示，并明确代理来源。
3. 实例详情或显式接口可写入已读记录，管理员和任务查询侧可分页查询已读。
4. 抽出统一审计写入能力，替代运行时继续借用 `ProcessDefinitionRepository.insertAuditLog` 的做法。
5. 实现 `ProcessMonitorService` 的手动催办、提醒查询、告警查询、告警处理；自动超时扫描只做 M5 可验收的最小实现，深度超时策略留到 M6。
6. 补齐 REST、Starter 装配和跨阶段回归测试，保证 C 线能力能被独立应用和嵌入式 Starter 复用。

## 2. 不做范围

1. 不新增第二套 `ProcessRuntimeService`、`TaskQueryService`、`AdminProcessService` 或附件服务。
2. 不重做 B 线 M5 六个增强动作。
3. 不新增真实短信、邮件、企业微信、HTTP 回调投递实现，只复用 `MessagePublisher` 和 `WorkflowCallbackHandler` SPI。
4. 不在 M5 做完整 M6 超时策略引擎、并行汇聚治理和复杂告警升级策略。
5. 不新增委托关系数据库表；第一阶段委托关系仍由 `DelegateProvider` 或本地 Mock 提供。

## 3. 数据库计划

### 3.1 优先复用的现有表

| 表 | M5 用法 |
| --- | --- |
| `process_active_task` | 认领、取消认领、待办、委托代办、超时扫描；复用 `task_status`、`assignee_user_id`、`delegate_from_user_id`、`lock_version`、`due_at`。 |

| `process_audit_log` | 统一动作审计，覆盖定义、实例、任务、附件、提醒、告警。 |
| `process_reminder_record` | 手动催办、自动提醒和超时提醒记录。 |
| `process_alert_record` | 任务超时、回调失败、动作异常告警。 |
| `process_operation_record` | `CLAIM/UNCLAIM/REMIND/ALERT_HANDLE` 幂等记录。 |
| `process_callback_log` | `CLAIM/UNCLAIM` 事件和后续告警联动查询。 |

### 3.2 建议新增或调整的索引

先检查现有查询计划，只有确认慢查询或分页过滤缺口时再新增迁移脚本 `004_m5_query_monitor_indexes.sql`：

```sql
CREATE INDEX IF NOT EXISTS idx_process_read_record_instance
    ON process_read_record (instance_id, read_at);

CREATE INDEX IF NOT EXISTS idx_process_audit_log_target_created
    ON process_audit_log (target_type, target_id, created_at);

CREATE INDEX IF NOT EXISTS idx_process_reminder_record_instance_created
    ON process_reminder_record (instance_id, created_at);

CREATE INDEX IF NOT EXISTS idx_process_alert_record_task_created
    ON process_alert_record (task_id, created_at);
```

不建议新增表。若已有 SQLite 库的 `process_operation_record` 约束缺少 `ATTACHMENT_UPLOAD/ATTACHMENT_DELETE` 或 M5 动作，先单独修复迁移，避免把历史基线问题混入 M5 业务提交。

## 6. 核心实现逻辑

### 6.1 认领 `claim`

1. 校验 `operationId/taskId/expectedTaskVersion/operatorUserId`。
2. 读取当前用户，要求请求操作人与当前用户一致。
3. 读取活动任务和实例，实例必须 `RUNNING`，任务必须 `ACTIVE`。
4. 权限规则：当前用户必须在 `candidate_user_ids` 中，或通过 `DelegateProvider.findPrincipals` 代理候选人任务。
5. 开启幂等租约，成功重放直接返回首次 `TaskActionResult`。
6. 在事务内调用 `ActiveTaskRepository.claim(taskId, expectedTaskVersion, operatorUserId, operatorUserName)`。
7. 受影响行数为 0 时写幂等确定性失败并返回并发或状态错误。
8. 写 `process_history_task` 的 `CLAIM` 控制轨迹，写 `process_audit_log`，写 `TASK_CLAIMED` 回调。
9. 重新读取任务，返回 `updatedTasks[0].taskVersion = old + 1`。

### 6.2 取消认领 `unclaim`

1. 校验请求、当前用户和幂等。
2. 读取任务，任务必须 `CLAIMED`，且 `assignee_user_id` 必须是当前用户。
3. 代理场景下也只允许实际认领人取消认领，不能由委托人远程取消。
4. 事务内调用 `ActiveTaskRepository.unclaim(taskId, expectedTaskVersion)`。
5. 写 `UNCLAIM` 控制轨迹、审计和 `TASK_UNCLAIMED` 回调。
6. 返回恢复为 `ACTIVE` 的最新任务快照。

### 6.3 委托待办查询

1. `CurrentUserProvider` 取得可信当前用户。
2. 查询本人已指派任务、本人候选任务、当前用户代理的委托人任务。
3. 使用 `ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY source_priority)` 去重。
4. 委托任务补 `delegateFromUserId/delegateFromUserName`。
5. 分页前统一应用流程、标题、发起人、节点、状态、时间范围过滤。
6. 已认领给委托人的任务允许代理人看到；已认领给其他人的任务不能被普通候选人看到。

### 6.4 已读记录

1. 建议新增显式接口 `POST /api/platform/instances/{instanceId}/read`，并可选在实例详情读取时自动标记。
2. 写入使用 `INSERT ... ON CONFLICT(instance_id, user_id) DO UPDATE SET read_at = excluded.read_at`。
3. 审计只记录首次已读，重复刷新不重复刷审计；如实现复杂，M5 可只记录 upsert 后的最后阅读时间，不写审计。
4. `queryReadRecords(ReadRecordQuery)` 支持 `instanceId/userId/readFrom/readTo/pageNo/pageSize`，按 `read_at DESC, id DESC` 排序。

### 6.5 统一审计

1. `AuditLogWriter.append(AuditLogCommand)` 是唯一新增写入口。
2. 运行时动作、附件动作、定义动作、监控动作统一写 `process_audit_log`。
3. 审计写入和主业务状态修改在同一事务内提交。
4. 删除实例后审计默认保留；已有删除逻辑若会置空 `instance_id`，`detail_json` 要保留 `targetDeleted=true`。
5. 查询支持管理员分页，按目标类型、目标 ID、实例 ID、操作人、动作、时间范围过滤。

### 6.6 手动催办

1. 校验 `operationId/taskId/message/operatorUserId`。
2. 读取任务和实例，任务必须 `ACTIVE/CLAIMED`，实例必须运行中。
3. 目标人解析规则：优先任务办理人；无办理人则取候选人；委托任务不直接推代理人，除非产品明确要求。
4. 事务内写 `process_reminder_record(PENDING)`、审计和幂等成功基础结果。
5. 事务提交后调用 `MessagePublisher.publish(ProcessMessage)`。
6. 发送成功更新 `SENT/sent_at`；发送失败更新 `FAILED/error_message`，但不回滚已提交的催办记录。
7. 幂等重放返回首次提醒记录，不重复发消息。

### 6.7 提醒和告警查询

1. `queryReminders(ReminderQuery)` 按实例、任务、状态、类型、时间分页。
2. `queryAlerts(AlertQuery)` 按实例、任务、状态、类型、级别、时间分页。
3. DTO 映射禁止泄漏内部数据库异常，只返回稳定枚举和摘要信息。

### 6.8 告警处理

1. 校验 `operationId/alertId/targetStatus/operatorUserId`。
2. 只允许 `OPEN -> HANDLED` 或 `OPEN -> IGNORED`，已关闭告警重复处理返回幂等结果或明确错误。
3. 事务内更新 `handled_by/handled_at/alert_status`，写 `ALERT_HANDLE` 审计和幂等成功。
4. 不删除告警记录。

### 6.9 自动超时扫描的 M5 最小闭环

1. `scanTimeoutTasks(TimeoutScanRequest)` 支持 `now/limit/dryRun/operatorUserId`。
2. 查询 `due_at <= now` 且状态为 `ACTIVE/CLAIMED` 的任务。
3. M5 最小实现：`dryRun=true` 只返回任务；`dryRun=false` 可按任务生成一条 `TIMEOUT` 提醒或 `TASK_TIMEOUT` 告警。
4. 防重复规则：同一 `task_id + reminder_type + 时间窗口` 已存在记录时不重复发送。
5. 节点级复杂 `timeout_config/reminder_config` 策略解析留到 M6 扩展。

## 8. 推荐提交顺序

1. `m5-c-baseline`：跑通当前测试，记录 M5 开工基线；单独处理非 M5 红色基线。
2. `m5-c-audit-writer`：新增 `AuditLogWriter`、`ProcessAuditLogRepository`、管理员审计查询。
3. `m5-c-claim-unclaim`：实现 `TaskClaimCoordinator` 和 `DefaultProcessRuntimeService.claim/unclaim`。
4. `m5-c-read-records`：实现已读 upsert、查询、REST。
5. `m5-c-monitor-reminder`：实现手动催办、提醒查询、消息发送补偿。
6. `m5-c-alerts-timeout-minimal`：实现告警查询、处理、最小超时扫描。
7. `m5-c-wiring-regression`：Starter/Standalone 装配、REST 冒烟、与 B 线 M5 联调回归。

## 10. 完成标准

1. `claim/unclaim` 不再抛阶段未实现异常。
2. 认领和取消认领全链路具备幂等、任务 CAS、历史、审计、回调和最新任务版本返回。
3. 待办查询可稳定展示本人、候选和委托代办任务，且不重复。
4. 已读记录可幂等写入和分页查询。
5. 手动催办能写提醒记录并调用 `MessagePublisher`，失败只更新提醒状态，不回滚主记录。
6. 告警可查询、处理或忽略，处理动作可审计。
7. 审计写入有统一入口，新增 M5 代码不再直接借用定义仓储写审计。
8. Starter 和独立 REST 应用可注入 M5 新增服务。
9. 目标 Maven 测试通过，并更新 M5 技术实现说明和阶段完成记录。
