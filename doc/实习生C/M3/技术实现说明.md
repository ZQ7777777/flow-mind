# 实习生 C：M3 阶段技术实现说明

> 编制日期：2026-07-23  
> 实现范围：C3.1-C3.8  
> 代码范围：`platform/platform-core`、`platform/platform-starter`

## 1. 实现结论

本阶段已完成 M3 查询读侧闭环的核心代码：

- 补齐查询 DTO 与列表展示字段。
- 实现待办、已办、我发起、活动任务、历史任务、审批意见查询。
- 查询身份统一通过 `CurrentUserProvider` 获取可信当前用户。
- 委托代办通过 `DelegateProvider.findPrincipals(...)` 获取“当前代理人可代办的委托人”。
- 查询层只读运行态数据库，不修改流程状态、历史、回调、幂等记录。
- 提供 REST 查询适配入口，便于 Starter 或宿主应用暴露 HTTP 接口。
- Starter 默认装配 core 中的真实 `DefaultTaskQueryService`，并接通 SQLite DataSource、`JdbcTemplate`、Repository、Assembler 与 schema 初始化。

`queryReadRecords` 属于 M5 已阅能力，M3 仍保持阶段未实现异常，不伪造空结果。

## 3. 对外接口

### 3.1 Service 接口

M3 主要实现 `TaskQueryService` 的以下方法：

- `queryTodoTasks(TodoTaskQuery query)`：我的待办。
- `queryCompletedTasks(CompletedTaskQuery query)`：我的已办。
- `queryStartedInstances(StartedInstanceQuery query)`：我发起的流程实例。
- `queryActiveTasks(String instanceId)`：实例当前活动任务。
- `queryHistoryTasks(String instanceId)`：实例历史任务。
- `queryComments(String instanceId)`：实例审批意见。

身份规则：

- `queryTodoTasks`、`queryCompletedTasks` 的 `userId` 如果传入，必须等于当前可信用户。
- `queryStartedInstances` 的 `starterUserId` 如果传入，必须等于当前可信用户。
- 最终查询用户以 `CurrentUserProvider.getCurrentUser().getUserId()` 为准。

### 3.2 REST 接口

新增 `PlatformQueryController`，提供以下 GET 入口：

| HTTP 接口 | Service 方法 | 说明 |
| --- | --- | --- |
| `GET /api/platform/tasks/todo` | `queryTodoTasks` | 待办分页列表 |
| `GET /api/platform/tasks/completed` | `queryCompletedTasks` | 已办分页列表 |
| `GET /api/platform/instances/started` | `queryStartedInstances` | 我发起分页列表 |
| `GET /api/platform/instances/{instanceId}/active-tasks` | `queryActiveTasks` | 当前活动任务 |
| `GET /api/platform/instances/{instanceId}/history-tasks` | `queryHistoryTasks` | 历史任务 |
| `GET /api/platform/instances/{instanceId}/comments` | `queryComments` | 审批意见 |
| `GET /api/platform/instances/{instanceId}` | `ProcessRuntimeService.getInstance` | 实例详情复用 B 线已有能力 |

Controller 只做 HTTP 参数绑定和服务委托，不拼 SQL、不处理业务身份。

### 3.3 Starter 自动装配

`platform-starter` 的 `PlatformAutoConfiguration` 已从 skeleton 服务切换为真实查询链路：

- 默认创建 SQLite `DataSource`，路径来自 `flow-mind.platform.sqlite.path`；未配置时使用 `./data/flow-mind.db`。
- 默认创建 `JdbcTemplate`，并通过 `PlatformSchemaInitializer` 执行 `schema/sqlite/001_init_flow_platform.sql`；初始化器会检查 `process_operation_record` 是否已支持 M2 动作，避免对已内置 M2 动作的新库重复执行迁移脚本。
- 默认装配 `ProcessHistoryTaskRepository`、`ActiveTaskRepository`、`ProcessInstanceRepository`、`ProcessTraceAssembler`、`RuntimeQueryAssembler`。
- 默认 `TaskQueryService` 为 `DefaultTaskQueryService`，复用 core 查询实现，不在 starter 中维护第二套查询逻辑。
- 宿主自定义 `TaskQueryService`、`DataSource`、`JdbcTemplate`、Repository、Assembler 或 SPI Bean 时，starter 通过 `@ConditionalOnMissingBean` 让位。
- `flow-mind.platform.enabled=false` 时不装配平台 Bean。
- `flow-mind.platform.mock.enabled=false` 时不装配 mock SPI；此时若宿主没有提供 `CurrentUserProvider`，查询调用会抛出清晰的 `CurrentUserProvider bean is required for TaskQueryService` 异常。

## 4. 数据库读流程

### 4.1 待办查询

读取表：

- `process_active_task`
- `process_instance`
- `process_node`

查询来源：

1. 直接待办：`process_active_task.assignee_user_id = currentUserId`。
2. 候选待办：`candidate_user_ids` JSON 数组包含 `currentUserId`，且任务状态为 `ACTIVE`。
3. 委托待办：通过 `DelegateProvider.findPrincipals(currentUserId, now)` 获取委托人，再匹配委托人的直接任务或候选任务。

实现要点：

- 使用 SQLite CTE 合并直接、候选、委托来源。
- 使用 `json_each(candidate_user_ids)` 做 JSON 数组精确匹配，避免 `operator-001` 误匹配 `operator-0010`。
- 使用 `ROW_NUMBER() OVER (PARTITION BY task_id ORDER BY source_priority)` 对同一任务去重。
- 默认按 `created_at DESC, task_id DESC` 稳定排序。
- 支持流程编码、流程名称、实例标题、发起人、节点、任务状态、创建时间范围等过滤。

### 4.2 已办查询

读取表：

- `process_history_task`
- `process_instance`
- `process_node`

查询规则：

- 默认只查当前可信用户经办过的历史任务。
- 支持流程编码、流程名称、实例标题、发起人、节点、动作类型、完成时间范围等过滤。
- 通过实例表补齐流程编码、流程名称、实例标题、发起人展示字段。
- 通过节点表补齐节点名称。

### 4.3 我发起查询

读取表：

- `process_instance`

查询规则：

- `starter_user_id` 固定为当前可信用户。
- 支持实例标题、业务键、实例状态、当前节点、发起时间范围等过滤。
- `current_node_codes` 为 JSON 数组时，通过 `json_each(current_node_codes)` 精确匹配当前节点编码。

### 4.4 活动任务、历史任务、审批意见

活动任务读取：

- `process_active_task`
- `process_instance`
- `process_node`

只返回 `ACTIVE`、`CLAIMED` 状态任务，并补齐流程、实例、节点展示字段。

历史任务和审批意见读取：

- `process_history_task`

历史任务保持既有按实例查询顺序：`started_at ASC, completed_at ASC, id ASC`。审批意见只转换 `comment_text` 非空的历史记录。

## 5. DTO 与读模型

### 5.1 查询 DTO

- `TodoTaskQuery`：新增流程名称、实例标题、发起人、节点、任务状态、创建时间范围、排序字段。
- `CompletedTaskQuery`：新增流程名称、实例标题、发起人、节点、动作类型、完成时间范围。
- `StartedInstanceQuery`：新增实例标题、业务键、实例状态、当前节点、发起时间范围。

### 5.2 展示 DTO

- `TaskDTO`：新增流程编码、流程名称、实例标题、发起人 ID、发起人名称。
- `HistoryTaskDTO`：新增流程编码、流程名称、实例标题、发起人 ID、发起人名称、节点名称。

### 5.3 查询读模型

新增只读实体：

- `TaskQueryEntity`：承载活动任务和实例、节点展示字段。
- `HistoryTaskQueryEntity`：承载历史任务和实例、节点展示字段。

新增 `RuntimeQueryAssembler` 负责将查询读模型转换为 API DTO，避免 Repository 直接依赖 API 层转换逻辑。

## 7. 边界与后续

- M3 查询层不实现已阅记录，`queryReadRecords` 保持未实现异常。
- M3 查询层不实现附件、催办、告警、审计查询的完整能力。
- `DelegateProvider.findPrincipals(...)` 当前以默认方法提供兼容实现，真实宿主侧应按“代理人 -> 有效委托人”语义覆盖。
- Starter 已纳入 C3.8，本阶段仅自动装配查询读侧所需 Bean；附件、回调、监控等 Service 仍保持 starter skeleton，等待后续阶段接入真实实现。
