# 实习生 C：M4 文件存储、附件元数据、附件授权、消息、回调、认证、组织架构 Mock 执行计划

> 编制日期：2026-07-27  
> 范围：`platform-core` 文件存储 SPI、附件授权 SPI、附件元数据 Repository、消息推送 SPI、流程回调 SPI、当前用户 SPI、组织架构 SPI 与本地 Mock；`platform-starter` 和独立 REST 的默认装配支撑。  
> 依据：实习生 C 开发文档、A/B 线 M4 编码计划、流程平台技术路线 v5.2、流程平台设计与接口文档 v4，以及当前代码基线。

## 1. M4 目标与职责边界

M4 阶段 C 线负责给 B 线附件运行时管理提供稳定底座：文件内容通过 SPI 保存，平台数据库只保存附件元数据；本地验收通过可复用 Mock 完成；附件授权 SPI 为附件访问提供失败关闭边界；消息推送 SPI 为后续提醒、催办和告警提供统一扩展点，流程回调 SPI 为宿主接收流程事件提供扩展点，认证和组织架构 Mock 为本地运行时校验和审批人解析提供基础数据。

### 1.1 C 线必做项

| 范围 | C 线交付 | 说明 |
| --- | --- | --- |
| 文件存储 SPI | `FileStorageProvider` 契约语义、请求/返回 DTO 回归 | 平台不绑定真实文件系统、OSS 或业务存储。 |
| 附件元数据 | `process_attachment` 表结构核查与 `ProcessAttachmentRepository` 补齐 | 只保存文件名、大小、类型、存储键、上传人、删除信息等元数据。 |
| 附件授权 Mock | `MockAttachmentAccessProvider` | 支持默认拒绝/允许和授权请求记录，便于本地验收和权限链路断言。 |
| 本地文件 Mock | 可复用 `InMemoryFileStorageProvider` | Starter 和独立应用共用，测试可断言保存、读取、删除。 |
| 消息推送 SPI | `MessagePublisher` 与 `ProcessMessage` 契约回归 | 供 M5/M6 提醒、催办、告警复用。 |
| 消息 Mock | 可复用记录型消息发布器 | 不能只作为 Starter 私有内部类存在。 |
| 流程回调 SPI | `WorkflowCallbackHandler` 与 `WorkflowEvent` 契约回归 | 供宿主接收流程事件回调。 |
| 流程回调 Mock | 可复用记录型回调处理器 | 不能只用不可断言的空实现。 |
| 认证 Mock | `MockCurrentUserProvider` | 供本地验收返回可信当前用户。 |
| 组织架构 Mock | `InMemoryOrganizationProvider` | 供本地验收查询部门、用户、角色关系。 |
| 审批人解析 | `DefaultApproverResolver` 默认装配 | 基于组织架构 SPI，不重复实现组织规则。 |
| 装配支持 | Starter/Standalone 条件装配 SPI 和 Mock | 宿主 Bean 可覆盖；生产缺失关键 SPI 时不静默放宽权限。 |
| 测试联调 | Repository、SPI、Mock、Starter 装配和 B 线附件服务联调 | 保证 B 的上传、查询、下载、删除、必填校验有可靠底座。 |

### 1.2 不属于 C 线 M4 主实现

| 内容 | 负责人/阶段 | C 的配合 |
| --- | --- | --- |
| 附件运行时主服务 `DefaultAttachmentService` | B 线 M4 | C 提供唯一 Repository、文件存储 SPI 与 Mock，不复制服务实现。 |
| 附件上传、下载、删除 REST 编排 | B 线 M4 | C 确认装配和 Mock 可用，配合端到端测试。 |
| 附件权限矩阵和 Guard 调用顺序 | B 线 M4 | C 保留 `AttachmentAccessProvider` 契约、默认拒绝策略和本地 Mock，不实现生产权限矩阵。 |
| 组织架构 SPI 与审批人解析 SPI | A 线 M4 | C 不新增组织数据生产实现。 |
| 真实 OSS、对象存储、短信、企微、邮件实现 | 宿主系统 | 平台只提供 SPI；Mock 仅用于本地验收。 |
| 审计日志、已阅、催办、超时提醒、异常告警 | M5/M6 | M4 只提供消息 SPI 和 Mock 基础。 |

### 2.2 需要重点补齐或确认的缺口

1. `ProcessAttachmentRepository` 必须满足 B 线全部调用点，不能让 B 在 Service 中直接写 SQL。
2. 需要确认附件来源任务门禁使用 `process_attachment.task_id` 保存来源任务 ID，实例附件和任务附件都能按来源任务判断是否仍可删除。
3. `countActiveByInstanceAndCode` 当前按实例和附件编码统计，需确认实例附件和任务附件共同参与数量限制。
4. 物理删除实例或定义前需要可靠收集 `storage_key`，供事务提交后最佳努力清理外部文件。
5. `RecordingMessagePublisher` 若仍是 Starter 私有内部类，应整理为 `platform-core.mock` 下可复用类，避免独立应用和测试复制实现。
6. `WorkflowCallbackHandler` 默认不应只是空实现，应提供可断言的 `RecordingWorkflowCallbackHandler`。
7. `CurrentUserProvider` 默认不应只是 Starter lambda，应整理为可复用 `MockCurrentUserProvider`。
8. `OrganizationProvider` 需要本地内存 Mock，支撑部门、角色、角色+部门查询。
9. `AttachmentAccessProvider` 默认不应只是匿名 lambda，应整理为可复用 `MockAttachmentAccessProvider`，支撑默认拒绝、独立应用允许和授权请求记录。
10. 文件 Mock 需要覆盖缺失文件读取、重复删除、并发保存、内容不被外部数组修改等边界。
11. Starter 在 `flow-mind.platform.mock.enabled=false` 时不能装配本地文件、消息、流程回调、认证和组织架构 Mock；宿主未提供必需 Bean 时应清晰失败。

## 3. 微任务拆分

### M4-C.0 基线核查与测试恢复

目标：

- 同步 A/B 线 M4 已完成代码，确认当前基线可编译。
- 执行现有测试，区分基线失败和 C 线 M4 新增失败。
- 梳理 B 线 `DefaultAttachmentService` 对 `ProcessAttachmentRepository`、`FileStorageProvider`、`MessagePublisher` 的实际调用点。

执行项：

1. 阅读 `AttachmentService`、附件 request/DTO、`DefaultAttachmentService`、`AttachmentController` 和 Starter 装配。
2. 阅读 `ProcessAttachmentRepository` 与 SQLite `process_attachment` 表结构。
3. 记录 B 线需要的 Repository 方法清单：读取、查询、计数、写入、软删除、存储键收集。
4. 先运行 `mvn -q -pl platform/platform-core -am test`，再运行根目录 `mvn -q test`，记录当前状态。

完成门槛：

- 明确 C 线需要补齐的代码点和测试点。
- 不把已有 A/B 线实现回退为占位实现。

### M4-C.1 文件存储 SPI 契约收口

目标：

- 固定 `FileStorageProvider.store/load/delete` 的输入输出语义。
- 保证 SPI 不暴露平台持久化实体，也不绑定某种真实存储。

执行项：

1. 补充或核查 `StoreFileRequest`、`StoredFile`、`FileContent` 的字段含义。
2. 明确 `store` 返回的 `storageKey` 是平台后续读取和删除的唯一凭据。
3. 明确 `load` 返回内容以存储实现为准，但下载响应的文件名、类型和大小以平台元数据为准。
4. 明确 `delete` 是最佳努力接口，重复删除在 Mock 中应可安全调用。
5. 增加 SPI 契约测试，确认公共 SPI 不依赖 `persistence` 包类型。

完成门槛：

- 文件存储 SPI 对 B 线上传、下载和删除链路足够稳定。
- 真实存储实现可以由宿主系统通过 Bean 覆盖接入。

### M4-C.2 附件元数据 Repository 补齐

目标：

- `ProcessAttachmentRepository` 成为唯一附件元数据访问入口。
- Repository 层提供 B 线需要的原子门禁和稳定查询能力。

执行项：

1. 核查 `process_attachment` 字段：`instance_id`、`task_id`、`owner_type`、`attachment_code`、`field_code`、`file_name`、`content_type`、`size_bytes`、`storage_key`、`uploaded_by`、`uploaded_at`、`deleted`、`deleted_by`、`deleted_at`。
2. 保留 `findById` 读取能力，下载和删除先读元数据再授权。
3. 保留 `queryActive(AttachmentQuery)`，查询默认排除软删除，并按 `uploaded_at ASC, id ASC` 稳定排序。
4. 保留按实例、任务、归属类型、附件编码、字段编码过滤，禁止 Service 层重复拼接查询 SQL。
5. 保留 `countActiveByInstanceAndCode`，确保数量统计覆盖实例附件和任务附件。
6. 保留 `insertWhenTaskOpenAndWithinLimit`，在同一 SQL 中校验来源任务仍为 `ACTIVE/CLAIMED` 且数量未超上限。
7. 保留 `softDeleteWhenTaskOpen`，落实“未进入下一节点前可删除”的门禁。
8. 补齐按实例和按定义实例集合收集 `storage_key` 的方法，供实例删除、定义删除后清理外部文件。
9. 增加 Repository 集成测试：过滤排序、软删除、任务门禁、版本匹配、数量上限、存储键收集。

完成门槛：

- B 线附件服务不需要绕开 Repository 写 SQL。
- 任务完成后上传或删除附件无法穿透。
- 删除元数据与外部文件清理保持事务边界清晰。

### M4-C.3 本地文件存储 Mock 完善

目标：

- `InMemoryFileStorageProvider` 可同时被 Starter、独立应用和测试复用。
- Mock 足够真实地支撑上传、下载、删除和回滚补偿测试。

执行项：

1. 保持实现位于 `platform-core/src/main/java/com/flowmind/platform/mock`。
2. `store` 生成稳定前缀的唯一 `storageKey`，保存文件名、类型、大小和内容。
3. `load` 在文件不存在时抛出明确异常，便于上层映射为存储失败或资源不存在。
4. `delete` 支持重复调用，不因文件不存在破坏删除补偿流程。
5. 如当前实现直接保存传入 `byte[]`，补充防御性拷贝，避免测试或调用方修改原数组影响已存内容。
6. 增加并发保存、读取、删除、重复删除、读取缺失文件的单元测试。

完成门槛：

- 本地验收可通过 Mock 完成附件上传、查询、下载、删除闭环。
- Mock 不被生产权限逻辑误认为真实宽松能力。

### M4-C.4 消息推送、流程回调、认证、组织架构 SPI 与 Mock

目标：

- 让 M5/M6 的催办、提醒、告警和回调通知共用同一消息 SPI。
- 提供可断言的本地记录型 Mock。
- 为 `AttachmentAccessProvider` 提供可配置附件授权 Mock，支撑默认拒绝和本地调试允许模式。
- 为 `WorkflowCallbackHandler` 提供可记录的本地回调处理器，避免默认空回调无法验证。
- 为 `CurrentUserProvider` 提供可复用认证 Mock。
- 为 `OrganizationProvider` 提供内存组织架构 Mock，支撑默认审批人解析。
执行项：

1. 核查 `ProcessMessage` 字段是否足够表达目标用户、标题、内容、业务类型、实例/任务上下文和 payload。
2. 明确 `MessagePublisher.publish` 抛异常时由调用方记录失败，不在 SPI 内吞掉生产异常。
3. 将 `RecordingMessagePublisher` 从 Starter 私有内部类整理到 `platform-core.mock`，例如 `com.flowmind.platform.mock.RecordingMessagePublisher`。
4. Mock 使用线程安全集合记录消息；`createdAt` 为空时可补当前时间。
5. 提供 `getMessages()` 或等价只读快照方法，方便测试断言。
6. 增加消息 Mock 测试：消息记录、时间补齐、多次发布顺序、并发发布。
7. 新增 `RecordingWorkflowCallbackHandler`，实现 `WorkflowCallbackHandler`。
8. 回调 Mock 线程安全记录 `WorkflowEvent`；`occurredAt` 为空时补当前时间。
9. 提供 `getEvents()` 只读快照，增加事件记录、时间补齐、顺序和并发测试。
10. 新增 `MockAttachmentAccessProvider`，默认拒绝访问，支持切换允许/拒绝模式并记录 `AttachmentAccessRequest` 快照。
11. 新增 `MockCurrentUserProvider`，默认返回 `mock-user`，支持切换当前用户并返回防御性拷贝。
12. 新增 `InMemoryOrganizationProvider`，内置本地部门、用户、角色关系，支持组织 SPI 的全部查询方法。
13. 默认审批人解析继续复用 `DefaultApproverResolver`，不在 Mock 中重新实现审批规则。
完成门槛：

- Starter 和独立应用都能复用同一个消息 Mock。
- Starter 和独立应用都能复用同一个流程回调 Mock。
- Starter 和独立应用都能复用同一个附件授权 Mock，且 Starter 默认拒绝、独立应用默认允许。
- Starter 和独立应用都能复用组织架构 Mock。
- Starter 默认认证 Mock 不再是私有 lambda。
- 后续提醒、告警不需要再定义第二套消息发送接口。

### M4-C.5 Starter 与独立应用装配

目标：

- Starter 和独立 REST 应用使用同一组 core 能力。
- 宿主生产 Bean 能覆盖默认 SPI/Mock。

执行项：

1. `FileStorageProvider` 使用 `@ConditionalOnMissingBean` 与 `flow-mind.platform.mock.enabled` 控制装配。
2. `MessagePublisher` 使用同样覆盖规则；Mock 关闭时不装配本地消息发布器。
3. `WorkflowCallbackHandler` 使用同样覆盖规则；Mock 关闭时不装配本地流程回调处理器。
4. `CurrentUserProvider` 使用同样覆盖规则；Mock 关闭时不装配本地认证 Mock。
5. `OrganizationProvider` 使用同样覆盖规则；Mock 关闭时不装配本地组织架构 Mock。
6. `ApproverResolver` 在存在 `OrganizationProvider` 时默认装配 `DefaultApproverResolver`。
7. `AttachmentAccessProvider` 默认装配 `MockAttachmentAccessProvider(false)`，不能因启用 Mock 文件存储而隐式放行。
8. `AttachmentAccessGuard` 只依赖 `AttachmentAccessProvider`，拒绝和异常都失败关闭。
9. `AttachmentService` 装配真实 `DefaultAttachmentService` 时必须依赖唯一 `ProcessAttachmentRepository`、文件存储、授权 Guard、当前用户和幂等执行器。
10. 独立应用 `PlatformStandaloneConfiguration` 复用 `InMemoryFileStorageProvider`、`MockAttachmentAccessProvider(true)`、记录型消息 Mock、记录型回调 Mock 和组织架构 Mock，不维护重复实现。
11. 增加 Starter 装配测试：默认 Mock、宿主覆盖、Mock 关闭、默认拒绝授权、真实 AttachmentService 可注入。

完成门槛：

- 嵌入式 Starter 与独立应用行为一致。
- 生产宿主可以替换文件存储和消息发布，不被默认 Mock 抢占。

### M4-C.6 与 B 线附件运行时联调

目标：

- 验证 C 线底座可以支撑 B 线完整附件能力。

联调场景：

1. 入金申请实例上传银行回单实例附件。
2. 任务附件上传到指定任务，并校验任务属于目标实例。
3. 缺失必填银行回单时，申请任务提交被拦截。
4. 附件格式、大小、数量超限时，元数据和文件都不留下不一致状态。
5. 权限拒绝时不调用 `FileStorageProvider.store/load/delete`。
6. 查询只返回未软删除附件，排序稳定。
7. 下载返回平台元数据和文件内容。
8. 来源任务仍活动时可软删除，进入下一节点后拒绝删除。
9. 实例或定义删除后，提交事务后最佳努力清理外部文件。

完成门槛：

- B 线附件服务的 Repository 和 SPI 依赖均由 C 线底座满足。
- 附件失败不会破坏运行时事务一致性。

## 5. 风险与处理方式

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| Repository 方法不足导致 B 线直接写 SQL | 形成第二套附件元数据规则 | C 先补 Repository，再让 B 服务只依赖 Repository。 |
| Mock 文件存储过于简单 | 回滚补偿、删除幂等测试不可信 | 补并发、重复删除、防御性拷贝和缺失文件测试。 |
| 默认 Mock 被生产误用 | 生产环境可能静默保存到内存 | 通过 `mock.enabled` 控制，并在发布说明中要求宿主提供生产 Bean。 |
| 附件授权默认放行 | 越权上传或下载 | `AttachmentAccessProvider` 缺省必须拒绝，Guard 失败关闭。 |
| 附件授权 Mock 只存在匿名 lambda | 独立应用和测试无法断言权限链路是否触发 | 整理为 `platform-core.mock.MockAttachmentAccessProvider` 并记录请求。 |
| 消息 Mock 只存在于 Starter 内部 | 独立应用和测试复制实现 | 整理为 `platform-core.mock` 公共 Mock。 |
| 流程回调 Mock 只是空实现 | 无法验证回调事件是否发出 | 整理为 `platform-core.mock.RecordingWorkflowCallbackHandler`。 |
| 认证 Mock 只存在于 Starter lambda | 独立应用和测试复制当前用户逻辑 | 整理为 `platform-core.mock.MockCurrentUserProvider`。 |
| 缺少组织架构 Mock | 本地审批人解析无法覆盖部门/角色规则 | 提供 `platform-core.mock.InMemoryOrganizationProvider`。 |
| 外部文件删除与数据库事务混用 | 文件删除失败导致元数据回滚或状态不一致 | 元数据事务先提交，外部文件提交后最佳努力清理。 |

## 6. 建议提交顺序

1. `m4-c-baseline-contract`：SPI 契约测试、当前基线测试记录。
2. `m4-c-attachment-repository`：附件 Repository 方法补齐和集成测试。
3. `m4-c-file-storage-mock`：内存文件存储 Mock 完善和测试。
4. `m4-c-spi-mocks`：附件授权 Mock、记录型消息发布器、流程回调处理器、认证 Mock 和组织架构 Mock 迁移到 core mock 并补测试。
5. `m4-c-starter-wiring`：Starter/Standalone 装配收口和覆盖测试。
6. `m4-c-b-integration`：与 B 线附件运行时联调、阶段记录和测试结果。

## 7. M4 完成标准

1. `FileStorageProvider`、`MessagePublisher` 契约清晰，且公共 SPI 不暴露持久化类型。
2. `ProcessAttachmentRepository` 支撑附件读取、查询、计数、任务门禁写入、任务门禁删除、软删除和存储键收集。
3. 文件内容只经 `FileStorageProvider` 保存；平台数据库只保存附件元数据。
4. 本地文件 Mock、附件授权 Mock、消息 Mock、流程回调 Mock、认证 Mock 和组织架构 Mock 可被 Starter、独立应用、测试复用。
5. 附件授权默认拒绝，拒绝和异常路径不会访问文件存储。
6. B 线的实例附件、任务附件、查询、下载、删除和必填校验可通过 C 线底座跑通。
7. Starter 宿主覆盖规则有效，关闭 Mock 后不会注册本地文件、消息、流程回调、认证和组织架构 Mock。
8. `mvn -q -pl platform/platform-core -am test`、`mvn -q -pl platform/platform-starter -am test` 和根目录 `mvn -q test` 通过。
