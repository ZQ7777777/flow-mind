## 2. C4.1-C4.3 附件基础能力

### 2.1 基线核查

已确认当前代码中附件底座相关组件存在并可复用：

| 组件 | 说明 |
| --- | --- |
| `FileStorageProvider` | 文件保存、读取、删除 SPI。 |
| `MessagePublisher` | 消息推送 SPI，供后续提醒、催办、告警复用。 |
| `WorkflowCallbackHandler` | 流程回调 SPI，供宿主接收流程事件回调。 |
| `CurrentUserProvider` | 当前登录用户 SPI，供运行时校验可信操作人。 |
| `OrganizationProvider` | 组织架构 SPI，供审批人解析查询用户、部门、角色关系。 |
| `DefaultApproverResolver` | 基于 `OrganizationProvider` 的默认审批人解析器。 |
| `AttachmentAccessProvider` / `AttachmentAccessGuard` | 附件权限失败关闭封装。 |
| `MockAttachmentAccessProvider` | 可配置附件授权 Mock，支持默认拒绝/允许和授权请求记录。 |
| `DefaultAttachmentService` | B 线附件运行时主服务。 |
| `ProcessAttachmentRepository` | 唯一附件元数据 Repository。 |
| `process_attachment` | SQLite 附件元数据表。 |
| `InMemoryFileStorageProvider` | 本地内存文件存储 Mock。 |

### 2.2 文件存储 SPI 契约

`FileStorageProvider` 保持三方法契约：

| 方法 | 语义 |
| --- | --- |
| `store(StoreFileRequest)` | 保存文件内容，返回后续读取/删除使用的 `storageKey`。 |
| `load(String storageKey)` | 按存储键读取文件内容。 |
| `delete(String storageKey)` | 删除外部文件内容，用于事务提交后的最佳努力清理。 |

平台数据库只保存 `storageKey`、文件名、内容类型、大小、上传人、删除人等元数据，不保存文件内容。

已更新 `PublicSpiContractTest.fileStorageProviderUsesOnlyPublicApiContracts`：

- 校验 `store` 返回 `StoredFile`。
- 校验 `load` 返回 `FileContent`。
- 新增校验 `delete` 返回 `void`。
- 校验三个方法的入参和返回值均不暴露 `com.flowmind.platform.persistence` 包类型。

### 2.3 附件元数据 Repository

`ProcessAttachmentRepository` 继续作为唯一附件元数据访问入口，保留并补齐以下能力：

| 方法 | 用途 |
| --- | --- |
| `findById(String id)` | 按附件 ID 读取元数据，可读取已软删除记录。 |
| `insert(ProcessAttachmentEntity)` | 基础元数据插入，供测试和受控内部场景使用。 |
| `insertWhenTaskOpenAndWithinLimit(...)` | 原子校验来源任务仍活动、任务版本匹配和数量未超限后写入。 |
| `queryActive(AttachmentQuery)` | 按实例、任务、归属类型、附件编码、字段编码查询未删除附件。 |
| `countActiveByInstanceAndCode(...)` | 统计同一实例下同一附件编码的未删除附件数量。 |
| `softDelete(...)` | 基础软删除。 |
| `softDeleteWhenTaskOpen(...)` | 来源任务仍活动时才允许软删除。 |
| `findStorageKeysByInstanceId(...)` | 实例删除前收集文件存储键。 |
| `findStorageKeysByInstanceIds(...)` | 批量实例删除前收集文件存储键。 |
| `findStorageKeysByDefinitionId(...)` | 定义删除前收集其所有实例附件的文件存储键。 |

本次代码变更：

- `queryActive` 增加 `instanceId` 入参保护，缺失时抛 `IllegalArgumentException`，避免误查全表。
- `findStorageKeysByInstanceId` 增加稳定排序：`uploaded_at ASC, id ASC`。
- 新增 `findStorageKeysByInstanceIds(List<String>)`，空列表返回空结果。
- 新增 `findStorageKeysByDefinitionId(String)`，通过 `process_instance.definition_id` 关联收集附件存储键。
- 存储键收集方法只读数据库，不调用 `FileStorageProvider.delete`，外部文件清理由事务提交后的上层流程处理。

新增 `ProcessAttachmentRepositoryIntegrationTest`，使用真实内存 SQLite 和正式初始化脚本覆盖：

- `queryActive` 必须指定 `instanceId`。
- `queryActive` 默认排除软删除附件。
- `queryActive` 支持实例、任务、归属类型、附件编码、字段编码过滤。
- 查询按 `uploaded_at ASC, id ASC` 稳定排序。
- 数量统计同时包含实例附件和任务附件，排除已软删除附件。
- `insertWhenTaskOpenAndWithinLimit` 校验来源任务状态、实例归属、任务版本和数量上限。
- `softDeleteWhenTaskOpen` 只允许来源任务处于 `ACTIVE/CLAIMED` 时删除。
- 软删除后保留 `storageKey`、删除人和删除时间。
- 实例、批量实例、定义维度均可稳定收集 `storageKey`。

## 3. C4.4-C4.6 Mock 与装配收口

### 3.1 内存文件存储 Mock

`InMemoryFileStorageProvider` 已完善为更可靠的本地验收 Mock：

- `store` 继续生成 `mock://` 前缀的唯一 `storageKey`。
- 保存文件内容时对 `byte[]` 做防御性拷贝。
- `load` 返回内容时再次拷贝 `byte[]`，调用方修改返回数组不会污染内部存储。
- `delete` 对不存在的 `storageKey` 保持幂等，不抛异常。
- `load` 缺失文件时抛 `IllegalArgumentException`，便于上层映射为存储不可用。

新增 `InMemoryFileStorageProviderTest`，覆盖：

- 保存后可读取原始内容。
- 修改上传原数组不影响已存文件。
- 修改读取结果不影响二次读取。
- 删除后读取失败。
- 重复删除不失败。
- 并发保存生成不同 `storageKey`。

### 3.2 附件授权、记录型消息、流程回调、认证、组织架构 Mock

新增 `platform-core.mock.MockAttachmentAccessProvider`，补齐附件授权 Mock：

- 实现 `AttachmentAccessProvider`。
- 默认拒绝访问，保持失败关闭语义。
- 支持通过构造参数或 `setAllowed(boolean)` 切换允许/拒绝模式。
- 记录每次 `AttachmentAccessRequest`，`getRequests()` 返回防御性只读快照，方便断言附件服务是否触发权限校验。
- `isAllowed(null)` 抛 `IllegalArgumentException`，由 `AttachmentAccessGuard` 统一转换为拒绝。

新增 `MockAttachmentAccessProviderTest`，覆盖默认拒绝、允许切换、请求记录、防御性快照、清空记录和非法入参。

新增 `platform-core.mock.RecordingMessagePublisher`，替代 Starter 私有内部实现：

- 实现 `MessagePublisher`。
- 使用线程安全集合记录 `ProcessMessage`。
- `createdAt` 为空时自动补当前时间。
- `getMessages()` 返回只读快照，避免测试误改内部状态。
- `publish(null)` 抛 `IllegalArgumentException`。

新增 `RecordingMessagePublisherTest`，覆盖：

- 消息记录。
- 时间补齐。
- 保留已有 `createdAt`。
- 多次发布顺序。
- 返回快照不可修改内部状态。
- 并发发布不丢消息。

新增 `platform-core.mock.RecordingWorkflowCallbackHandler`，补齐流程回调 SPI 的本地记录型 Mock：

- 实现 `WorkflowCallbackHandler`。
- 使用线程安全集合记录 `WorkflowEvent`。
- `occurredAt` 为空时自动补当前时间。
- `getEvents()` 返回只读快照，方便测试断言回调事件。
- `handle(null)` 抛 `IllegalArgumentException`。

该 Mock 补的是“流程回调处理器”的可记录实现，不等同于把 `CallbackService.publishCallback` 改成同步直连外部系统。`CallbackService` 的发布、日志或 Outbox 边界仍由现有服务实现负责，宿主生产环境应提供真实 `WorkflowCallbackHandler`。

新增 `RecordingWorkflowCallbackHandlerTest`，覆盖：

- 回调事件记录。
- `occurredAt` 时间补齐。
- 保留已有 `occurredAt`。
- 多次处理顺序。
- 返回快照不可修改内部状态。
- 并发处理不丢事件。

新增 `platform-core.mock.MockCurrentUserProvider`，补齐认证上下文 Mock：

- 实现 `CurrentUserProvider`。
- 默认返回 `mock-user / Mock User / mock-dept / Mock Department`。
- 支持通过 `setCurrentUser(UserContext)` 切换当前用户，方便本地验收和测试。
- `getCurrentUser()` 返回防御性拷贝，避免调用方修改内部用户上下文。
- 拒绝缺失 `userId` 的用户上下文。

新增 `platform-core.mock.InMemoryOrganizationProvider`，补齐组织架构 Mock：

- 实现 `OrganizationProvider`。
- 内置 `mock-dept`、`dept_sales`、`dept_manager`、`dept_finance` 等本地部门。
- 内置 `mock-user`、`user_sales`、`user_sales_manager`、`user_manager`、`user_finance`、`user_admin` 等本地用户。
- 支持按部门、角色、角色+部门查询用户，并支持按 ID 查询用户和部门。
- 返回只读快照和对象拷贝，避免测试修改内部组织数据。

新增 `MockCurrentUserProviderTest` 和 `InMemoryOrganizationProviderTest`，覆盖默认用户、用户切换、防御性拷贝、部门/角色查询、缺失数据空结果和非法入参。

## 4. 与 B 线附件服务的边界

B 线 `DefaultAttachmentService` 当前继续负责：

- 当前用户校验；
- 附件权限 Guard 调用；
- 模板和节点适用性校验；
- 文件存储调用；
- 附件元数据写入；
- 上传、下载、查询、删除和必填校验编排；
- 文件保存后的回滚补偿与删除后的提交清理。

C 线本次提供 Repository、SPI 契约、文件 Mock、附件授权 Mock、消息 Mock、流程回调 Mock、认证 Mock、组织架构 Mock 和装配底座。B 线不得绕过 `ProcessAttachmentRepository` 直接操作 `process_attachment`。

## 5. 测试结果

已执行并通过：

```powershell
mvn -q -pl platform/platform-core "-Dtest=PublicSpiContractTest,ProcessAttachmentRepositoryIntegrationTest" test
mvn -q -pl platform/platform-core "-Dtest=InMemoryFileStorageProviderTest,MockAttachmentAccessProviderTest,RecordingMessagePublisherTest,RecordingWorkflowCallbackHandlerTest,MockCurrentUserProviderTest,InMemoryOrganizationProviderTest,PlatformStandaloneApplicationTest" test
mvn -q -pl platform/platform-starter -am -Dtest=PlatformAutoConfigurationTest -DfailIfNoTests=false test
mvn -q -pl platform/platform-core -am test
mvn -q -pl platform/platform-starter -am -DfailIfNoTests=false test
```

说明：

- 单独运行 `mvn -q -pl platform/platform-starter -Dtest=PlatformAutoConfigurationTest test` 会因未同时构建 reactor 内的 `platform-core` 依赖而解析失败。
- 使用 `-am` 时，`-Dtest=PlatformAutoConfigurationTest` 会传递到依赖模块；因此定向运行 Starter 测试需要加 `-DfailIfNoTests=false`。
