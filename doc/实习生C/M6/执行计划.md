# 实习生 C：M6 执行计划

> 编制日期：2026-07-28  
> 范围：并行汇聚验收收口、管理员查询与修复治理、节点级超时策略、催办策略、回调失败告警、异常告警闭环、M6 跨线回归。  
> 代码基线：当前 `develop@2518c43`。  
> 边界说明：并行拆分与汇聚的核心推进已经完成，C 线 M6 不重复实现 `RuntimeNodeAdvancer` 的流转逻辑；A 线负责条件分支和或签，B 线负责会签，C 线负责查询、监控、告警、管理员治理和跨线验收。

## 0. 需求文档审查结论

根据 `doc/rebuild-functional-requirements-optimized.md`，M6-C 的“管理员修复”不能只理解成一个 `jumpToNode` 接口。需求把它放在“管理与运维能力”中，要求形成一套异常流程人工治理闭环：

1. 管理员能对异常流程执行人工修复动作，核心是任意节点跳转和强制办结。
2. 管理员能查询流程定义、实例、活动任务、历史任务等核心运行数据，用于判断为什么需要修复；流程定义查询复用现有定义服务，C 线不重做定义 CRUD。
3. 关键管理动作和流程状态变更必须记录审计日志。
4. 终止后的流程应能通过管理员跳转重新拉起。
5. 超时自动处理、自动催办、自动跳转、自动终止要能按节点配置触发。
6. 回调失败、超时等异常要有告警或重试机制，告警处理本身也要可查询、可审计。

因此，本执行计划按“可排查、可修复、可追踪、可自动治理”重排优先级：先补齐管理员查询和修复动作的审计一致性，再做任务组诊断、超时策略、自动动作、回调失败告警和跨线回归。

## 1. 阶段目标

M6 的目标是把高级流转能力从“运行时能跑通”补齐到“管理端可观察、异常可处理、超时可治理、组合场景可验收”。

1. 固化并行汇聚已完成能力的验收：重复分支到达不重复计数，最后分支只推进一次，汇聚后任务和回调不重复。
2. 补齐管理端实例、活动任务、历史任务分页查询，使管理员能查看运行实例、并行分支、任务组上下文和历史轨迹。
3. 完善管理员修复治理：`jumpToNode`、`forceComplete` 已有核心命令，M6 要补齐管理员权限、审计统一入口、终止后恢复流转、并行任务组取消后的查询展示和回归。
4. 将 M5 最小超时扫描升级为节点级策略：读取 `process_node.timeout_config` 和 `reminder_config`，计算 `dueAt`、提醒窗口、告警级别、自动处理动作和去重规则。
5. 完成异常告警闭环：任务超时、回调失败、动作异常都能产生可查询、可处理、可审计的告警。
6. 补齐 REST、Starter/Standalone 装配回归和跨 A/B/C 的 M6 集成测试。

## 3. 不做范围

1. 不重写并行拆分、并行汇聚和任务组 CAS 逻辑；已完成部分只补查询、审计、告警和回归。
2. 不实现 A 线的条件分支、或签运行逻辑。
3. 不实现 B 线的会签创建、会签审批、一票驳回运行逻辑。
4. 不新增第二套 `ProcessRuntimeService`、`AdminProcessService`、`TaskQueryService` 或 `ProcessMonitorService`。
5. 不接入真实短信、邮件、企业微信或 HTTP 回调投递；继续通过 SPI 和 Mock 固化扩展点。
6. 不开放嵌套并行网关。当前 `RuntimeNodeAdvancer` 明确拒绝嵌套并行，M6-C 不擅自改变该边界。
7. 不实现完整工作日历、节假日、复杂升级链路；M6 只定义最小可验收的超时策略 JSON。
8. 不重做 A 线流程定义版本治理、发布、停用、归档和灰度逻辑；C 线只验证管理端查询与审计可追溯。

### C6.3：收口管理员修复审计和并行组取消回归

目标：

- 明确管理员修复的权限边界，只允许管理员执行跳转和强制办结。
- `jumpToNode`、`forceComplete` 改用 `AuditLogWriter`。
- 验证终止实例可通过管理员跳转恢复流转。
- 验证管理员修复会取消并行活动任务组，不留下孤立分支。
- 修复动作的审计、历史、回调和幂等结果保持同一事务。

实现要点：

- 增加最小管理员权限 Guard。若当前 SPI 未提供角色能力，可先在 `CurrentUserProvider`/Mock 用户上下文中约定 `operatorUserId=admin` 或配置化管理员用户集合，并在文档记录后续可替换点。
- 替换 `DefaultAdminProcessService.writeAudit` 中直接调用 `ProcessDefinitionRepository.insertAuditLog` 的实现。
- `InstanceTaskCancellationService.cancelOpenWork` 已取消开放任务和活动任务组，M6 需要补测试覆盖并行场景。
- 管理员跳转仍不得直接跳到 `START` 或 `PARALLEL_JOIN_GATEWAY`。
- 跳转到普通用户任务、条件网关、并行拆分、结束节点都要保留现有推进器入口。
- `TERMINATED` 实例跳转时应先恢复 `RUNNING`，再按目标节点推进；其他终态是否允许跳转必须显式拒绝。

测试与完成条件：

- 非管理员调用跳转或强制办结返回权限错误，不修改实例、任务组、历史、审计或回调。
- 并行流程运行中管理员跳转后：原分支任务为 `CANCELED`，原并行任务组为 `CANCELED`，只创建目标路径任务。
- 并行流程运行中强制办结后：开放任务取消，活动任务组取消，实例 `COMPLETED`。
- `TERMINATED` 实例管理员跳转后恢复为 `RUNNING`，并创建目标路径任务。
- 幂等重放不重复取消任务、不重复创建新任务、不重复写审计和回调。

建议提交：`feat: unify admin repair audit`

### C6.4：补齐并行任务组查询展示

目标：

- 管理端能看到并行任务组和分支状态，不只看到活动任务列表。
- 查询结果支持排查“哪些分支已到达、哪些分支仍在运行、组是否已完成或取消”。

实现要点：

- 在 `TaskGroupRepository` 新增按实例查询全部任务组或活动任务组的方法。
- 解析 `branch_state_json` 为稳定 Map，异常 JSON 返回平台错误，不把数据库异常透给前端。
- 对会签组和并行组都保留 `groupType`，但分支状态只对 `PARALLEL_GATEWAY` 展示。
- 可先放在管理端实例详情/单实例诊断接口；若新增公开 DTO，要补契约测试。

测试与完成条件：

- 并行分支刚创建时展示两个或多个 `RUNNING` 分支。
- 一个分支完成后展示 `completedCount=1`，对应分支 `ARRIVED`。
- 全部分支完成后展示任务组 `COMPLETED`。
- 管理员跳转或强制办结后展示任务组 `CANCELED`。

建议提交：`feat: expose task group diagnostics`

### C6.5：实现节点级超时策略和任务 dueAt 生成

目标：

- 从节点 `timeout_config` 解析超时策略。
- 创建活动任务时根据策略写入 `process_active_task.due_at`。
- `scanTimeoutTasks` 不再依赖外部手工填 `due_at` 才能工作。

实现要点：

- 策略建议支持最小结构：`enabled`、`durationMinutes`、`severity`、`action`、`targetNodeCode`。
- `TimeoutPolicyReader` 对非法 JSON、负数时长、未知 severity/action 返回稳定错误。
- `RuntimeNodeAdvancer.createActiveTask` 创建任务时读取当前用户节点配置，计算 `createdAt + duration`。
- 未配置或 `enabled=false` 时 `dueAt=null`，保持 M5 行为。
- 只计算用户任务超时，不对网关和结束节点设置超时。
- `action` 首期只允许 `ALERT`、`REMIND`、`JUMP`、`TERMINATE`、`FORCE_COMPLETE`，不支持脚本或任意 Java Bean 调用。

测试与完成条件：

- 节点配置 `durationMinutes=30` 时，新建任务 `dueAt=createdAt+30min`。
- 未配置或禁用策略时 `dueAt=null`。
- 非法策略在发布校验或运行时准备阶段报明确错误。
- 超时扫描可以发现由运行时自动写入 `dueAt` 的任务。

建议提交：`feat: derive task due date from timeout policy`

### C6.6：升级自动提醒和超时自动处理策略

目标：

- 从 `reminder_config` 解析自动提醒策略。
- 超时扫描按策略生成 `TIMEOUT` 或 `AUTO` 提醒，并调用 `MessagePublisher`。
- 超时扫描按 `timeout_config.action` 触发自动告警、自动跳转、自动终止或强制办结。
- 保证同一任务、同一窗口不重复提醒。

实现要点：

- 策略建议支持最小结构：`enabled`、`intervalMinutes`、`maxCount`、`targetRule`、`messageTemplate`。
- 提醒目标复用 M5 手动催办规则：优先办理人，其次候选人。
- `dryRun=true` 仍只返回超时任务，不写提醒、告警或消息。
- `dryRun=false` 根据提醒策略生成提醒；无提醒策略或已达到最大次数时可生成 `TASK_TIMEOUT` 告警。
- `action=JUMP` 时必须复用管理员跳转能力，并要求 `targetNodeCode` 合法；不允许跳转到 `START` 或 `PARALLEL_JOIN_GATEWAY`。
- `action=TERMINATE` 或 `FORCE_COMPLETE` 时必须复用现有终止/强制办结清理逻辑，取消开放任务和活动任务组。
- 自动动作使用系统操作人，例如 `system_timeout`，并写审计、回调和幂等记录；重复扫描不得重复跳转或重复终止。
- 发送失败只更新提醒状态为 `FAILED`，不回滚扫描结果。

测试与完成条件：

- 启用提醒策略时，扫描生成提醒并记录消息 Mock。
- 相同窗口重复扫描不重复发送。
- 超过 `maxCount` 后不再生成提醒，可升级为告警。
- `action=JUMP` 的超时任务能自动取消当前任务并创建目标节点任务。
- `action=TERMINATE/FORCE_COMPLETE` 的超时任务能自动结束实例并清理开放任务。
- 自动跳转、自动终止和强制办结均有审计和回调。
- 提醒查询能按类型、状态、实例、任务过滤。

建议提交：`feat: apply timeout handling policy`

### C6.7：实现回调投递失败告警

目标：

- 实现 PENDING 回调投递或失败处理入口。
- `WorkflowCallbackHandler` 抛异常时，回调日志标记 `FAILED`，并生成 `CALLBACK_FAILED` 告警。
- 同一 `eventId` 的开放告警不重复生成。

实现要点：

- 使用 `ProcessCallbackLogRepository.findPending/markSuccess/markFailed`。
- 新增 `CallbackDispatchService.dispatchPending(limit)` 或等价内部方法；不要求接入真实定时器。
- 回调失败告警 `detailJson` 包含 `eventId/operationId/eventType/actionType/retryCount/errorSummary`。
- 失败告警可以复用 `AlertRecordRepository.findOpenByTaskAndType` 之外的新方法，因为回调告警可能没有 `taskId`。
- 告警写入失败不应改变已标记的回调失败状态；需要测试并记录边界。

测试与完成条件：

- 回调处理成功后 `callback_status=SUCCESS`。
- 回调处理失败后 `callback_status=FAILED` 且生成 `CALLBACK_FAILED` 告警。
- 同一失败事件重复派发不重复打开告警，只更新 retry 或保留首条 OPEN 告警。
- 告警可被 `queryAlerts` 查到并被 `handleAlert` 处理。

建议提交：`feat: alert on callback dispatch failure`

### C6.8：实现动作异常告警策略

目标：

- 对运行时/管理员动作中的可诊断异常生成 `ACTION_EXCEPTION` 告警。
- 保留错误码、实例、任务、动作、操作人和摘要，便于管理员处理。

实现要点：

- 不对所有参数校验错误都生成告警，避免用户输入错误刷屏。
- 建议只对状态异常、并发重试耗尽、SPI 异常、回调/消息外部异常生成告警。
- 告警写入要避免反向影响主业务事务；主事务失败时不应留下“成功动作”的审计，但可在独立告警事务中记录异常摘要。
- 同一 `operationId + actionType` 的异常告警必须去重。

测试与完成条件：

- 并行汇聚任务组重试耗尽时可生成 `ACTION_EXCEPTION` 告警。
- 管理员修复中发生任务组并发冲突时可生成告警。
- 参数缺失、权限拒绝不生成动作异常告警。
- 告警处理后写 `ALERT_HANDLE` 审计。

建议提交：`feat: record actionable runtime exception alerts`

### C6.9：M6 跨线组合回归

测试场景：

## 8. 最小验收清单

- 并行汇聚核心测试保持通过，重复分支到达不重复计数，最后分支只推进一次。
- 管理端可分页查询实例、活动任务、历史任务、审计日志、回调日志、提醒和告警。
- 管理端能看到并行任务的 `taskGroupId/branchKey`，并能查看任务组计数和分支状态。
- 非管理员不能执行跳转或强制办结。
- 管理员跳转和强制办结在并行流程中不会留下孤立活动任务组。
- 终止实例可通过管理员跳转恢复流转，其他不允许恢复的终态要明确拒绝。
- 管理员修复动作统一通过 `AuditLogWriter` 写审计。
- 用户任务可根据节点 `timeout_config` 自动生成 `dueAt`。
- 超时扫描支持 dry-run、自动提醒、告警升级、自动跳转、自动终止和重复扫描去重。
- 回调投递失败会生成 `CALLBACK_FAILED` 告警。
- 可诊断的运行时/管理员动作异常会生成 `ACTION_EXCEPTION` 告警，参数校验错误不会刷告警。
- 告警可处理或忽略，并写 `ALERT_HANDLE` 审计。
- Starter 和独立 REST 应用均能使用 M6 新增能力。
- M6 跨线回归覆盖条件、并行、会签、管理员修复、超时、回调失败和告警处理。

## 9. 风险与注意事项

1. `RuntimeNodeAdvancer.advanceParallelSplit` 仍明确拒绝嵌套并行，M6 文档和测试不能写成“支持嵌套并行”。
2. 超时策略最好先定义最小 JSON 契约，不要一次性引入复杂调度、节假日、工作日历和升级链路。
3. 回调投递如果接入外部 SPI，必须在主流程事务外执行；主流程只负责 outbox 落库。
4. 告警生成要做去重，否则超时扫描和回调重试容易无限增长。
5. 管理员查询要复用现有分页规范和 DTO，不要为每个页面复制一套 SQL 和映射逻辑。
6. M6 增加的策略 Reader 要和 A 线定义保存/发布校验对齐，非法策略应尽量在发布前发现。
7. 新增 SQL 要隔离在 Repository 内。当前 SQLite 使用 `json_each/json_extract/json_set`，后续 Oracle 或国产数据库适配时必须通过 Repository 方言层替换，不能把方言函数扩散到 Service。
