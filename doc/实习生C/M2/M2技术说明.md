# 实习生 C：M2 运行期外围能力技术说明

## 1. M2 实现范围和边界

实习生 C 的 M2 不实现主流程状态机，而是给 B 线运行期动作提供外围能力。B 线负责真正的流程推进，例如任务办理、创建下一节点任务、实例办结；C 线负责保证这些动作在运行期可校验、可幂等、可追踪、可查询、可回调。

本阶段已经覆盖的功能：

- 操作幂等记录：对每次运行期动作写入 `process_operation_record`，支持首次执行、成功重放、失败重放、处理中、过期接管和冲突识别。
- 运行状态校验：在任务或实例动作执行前读取活动任务、实例、任务组状态，提前拦截非法操作。
- 审批意见：将审批意见作为历史任务的一部分写入 `process_history_task.comment_text`，不单独建评论表。
- 流程轨迹：将已完成或已取消的活动任务归档到 `process_history_task`，查询时组装为历史任务列表。
- 回调幂等和 Outbox：将工作流事件写入 `process_callback_log(PENDING)`，用 `event_id` 保证事件不重复。
- 查询能力：通过 `TaskQueryService` 查询已办、历史任务、审批意见，通过 `CallbackService` 查询回调日志。

本阶段明确不做：

- 不创建下一节点任务，不判断流程是否结束，不硬编码串行流转。
- 不实现真实 HTTP 回调投递，只写 Outbox。
- 不实现审计日志写入和查询，留到 M5。
- 不实现运行时附件保存、下载、删除、必填校验，留到 M4。

## 2. 操作幂等记录怎么实现

### 2.1 功能目标

同一个前端或调用方动作可能因为超时、重试、重复点击被提交多次。M2 的处理方式是：所有运行期动作进入业务逻辑前，先用 `operationId` 在 `process_operation_record` 中占位；后续重复请求根据已保存状态决定是直接重放结果、返回失败、提示处理中、接管过期请求，还是拒绝冲突请求。

所以操作幂等记录需要对 `process_operation_record` 进行插入。首次请求会插入一条 `PROCESSING` 记录，后续执行成功或确定性失败时再更新这条记录。

### 2.2 数据库落点

表：`process_operation_record`

关键字段：

- `operation_id`：全局幂等键，数据库唯一约束。
- `instance_id`：流程实例 ID，运行期动作需要写入。
- `task_id`：任务 ID，任务类动作需要写入；实例类动作可以为空。
- `action_type`：动作类型，例如 `START`、`APPROVE`、`REJECT`、`CANCEL`。
- `operator_id`：操作者 ID。
- `request_hash`：请求内容摘要，用来判断同一个 `operationId` 是否对应同一请求。
- `operation_status`：`PROCESSING`、`SUCCESS`、`FAILED`。
- `result_json`：首次成功结果快照，用于重复请求重放。
- `error_code`：确定性失败错误码，用于重复失败重放。
- `processing_expires_at`：处理中租约过期时间，用于接管卡住的请求。
- `expires_at`：记录整体过期时间，用于后续清理。

索引和约束：

- `operation_id` 唯一，保证同一动作只会有一个幂等记录。
- `idx_process_operation_record_instance(instance_id, created_at)` 支持按实例排查操作。
- `idx_process_operation_record_task(task_id, created_at)` 支持按任务排查操作。
- `idx_process_operation_record_status_expires(operation_status, processing_expires_at)` 支持查询处理中且租约过期的记录。
- `idx_process_operation_record_expires(expires_at)` 支持历史清理。

### 2.3 代码分工

`ProcessOperationRecordRepository`

- 只负责 `process_operation_record` 的数据库访问。
- `insert(...)`：首次插入 `PROCESSING`。
- `findByOperationId(...)`：按 `operation_id` 查询已有记录。
- `markSuccess(...)`：更新为 `SUCCESS` 并保存 `result_json`。
- `markFailed(...)`：更新为 `FAILED` 并保存 `error_code`。
- `extendProcessingLease(...)`：处理中租约过期时更新新的 `processing_expires_at`。
- `findExpired(...)`：查询超过 `expires_at` 的幂等记录，供后续清理任务使用。

`OperationIdempotencyService`

- 封装业务语义，不让 B 线直接判断数据库状态。
- `begin(...)`：尝试开始一次操作，首次会插入记录。
- `beginOrReplay(...)`：运行期推荐入口，返回决策结果。
- 运行期重载会接收并保存 `instanceId`、`taskId`，方便后续按实例或任务追踪。
- `begin(...)` 和 `beginOrReplay(...)` 使用 `REQUIRES_NEW`，幂等占位会独立提交，避免主业务还没开始就因为外层事务回滚丢失处理中记录。
- `markSuccess(operationId, resultJson)`：主业务成功后保存可重放结果。
- `markFailed(operationId, errorCode)`：确定性失败后保存可重放错误码。
- `markFailed(...)` 使用 `REQUIRES_NEW`，确定性失败可以独立固化；`markSuccess(...)` 没有单独开启事务，会参与调用方已有事务，或在无事务时按 JDBC 默认行为执行。

### 2.4 决策语义

`beginOrReplay(...)` 返回的决策含义：

- `NEW`：没有旧记录，已成功插入 `PROCESSING`，调用方可以继续执行业务。
- `REPLAY_SUCCESS`：旧记录是 `SUCCESS`，直接返回旧的 `result_json`，不要重复执行业务。
- `REPLAY_FAILED`：旧记录是 `FAILED`，直接返回旧的 `error_code`，不要重复执行业务。
- `IN_PROGRESS`：旧记录还是 `PROCESSING` 且租约未过期，说明已有请求正在处理。
- `TAKE_OVER`：旧记录是 `PROCESSING` 但租约已过期，同一请求可以接管继续执行。
- `CONFLICT`：同一个 `operationId` 对应了不同 `actionType` 或 `requestHash`，必须拒绝。

### 2.5 B 线接入方式

任务审批、驳回、取消等动作建议按这个顺序调用：

1. B 线根据请求生成稳定 `requestHash`，字段至少覆盖 `taskId/actionType/variables/comment/expectedTaskVersion`。
2. 调用 `OperationIdempotencyService.beginOrReplay(operationId, instanceId, taskId, actionType, operatorId, requestHash, now)`。
3. 只有 `NEW` 或 `TAKE_OVER` 继续执行业务。
4. 对 `REPLAY_SUCCESS` 直接返回旧结果，对 `REPLAY_FAILED` 返回旧错误，对 `IN_PROGRESS` 提示处理中，对 `CONFLICT` 抛冲突错误。
5. 主业务执行成功后调用 `markSuccess(operationId, resultJson)`。
6. 对参数错误、状态错误、权限错误等确定性失败调用 `markFailed(operationId, errorCode)`。
7. 对数据库超时、进程中断等不确定失败不要立刻标失败，保留 `PROCESSING`，等待租约过期后接管。

## 3. 运行状态校验

### 3.1 功能目标

运行状态校验器用于在 CAS 更新前做只读检查，提前发现任务不存在、实例状态不允许、任务状态不允许、版本号不一致、操作者缺失等问题。

它不需要新增数据库表，也不需要新增独立 API Service。M2 中只需要实现一个可被 B 线运行时 Service 调用的内部类：`RuntimeStateValidator`。

### 3.2 数据库

`RuntimeStateValidator` 只读以下表：

- `process_active_task`：读取活动任务、任务状态、任务版本、任务所属实例。
- `process_instance`：读取实例状态。
- `process_task_group`：读取任务组状态、任务组版本、分支状态 JSON。

对应 Repository：

- `ActiveTaskRepository.findById(taskId)`
- `ActiveTaskRepository.findByInstanceId(instanceId)`
- `ProcessInstanceRepository.findById(instanceId)`
- `TaskGroupRepository.findById(taskGroupId)`

### 3.3 代码

`RuntimeStateValidator`

- `validateTaskAction(taskId, expectedTaskVersion, actionType, operator)`
  - 校验操作者不为空。
  - 查询活动任务，不存在则抛 `FLOW_TASK_NOT_FOUND`。
  - 查询任务所属实例，不存在则抛 `FLOW_INSTANCE_NOT_FOUND`。
  - 校验实例必须是 `RUNNING`。
  - 校验当前任务状态允许执行该 `actionType`。
  - 校验 `expectedTaskVersion` 和任务 `lock_version` 一致，不一致抛并发修改错误。
  - 返回 `RuntimeTaskContext`，给 B 线继续执行 CAS。

- `validateInstanceAction(instanceId, actionType, operator)`
  - 校验操作者不为空。
  - 查询实例，不存在则抛 `FLOW_INSTANCE_NOT_FOUND`。
  - `START` 要求实例是 `NOT_STARTED`。
  - 其他实例动作通常要求实例是 `RUNNING`。返回 `RuntimeInstanceContext`。

- `validateTaskGroupState(taskGroupId, expectedGroupVersion, actionType)`
  - 查询任务组，不存在则抛 `FLOW_TASK_GROUP_NOT_FOUND`。
  - 校验任务组仍处于可操作状态。
  - 校验 `expectedGroupVersion` 和任务组 `lock_version` 一致。

`RuntimeValidationException`

- 运行期校验失败统一抛这个异常。
- 异常里带稳定错误码，外层可以把错误码写入幂等记录。

`RuntimeErrorCodes`

- 集中维护运行期稳定错误码，例如：
  - `FLOW_OPERATOR_REQUIRED`
  - `FLOW_INSTANCE_NOT_FOUND`
  - `FLOW_INSTANCE_STATUS_INVALID`
  - `FLOW_TASK_NOT_FOUND`
  - `FLOW_TASK_STATUS_INVALID`
  - `FLOW_TASK_CONCURRENT_MODIFIED`
  - `FLOW_TASK_GROUP_NOT_FOUND`
  - `FLOW_TASK_GROUP_STATUS_INVALID`
  - `FLOW_TASK_GROUP_CONCURRENT_MODIFIED`

### 3.4 和 CAS 的关系

运行状态校验不能替代 CAS。它只能提前做用户友好的错误判断，真正防并发仍然依赖 B 线后续的条件更新。

推荐顺序：

1. `RuntimeStateValidator.validateTaskAction(...)` 先读状态。
2. B 线执行 `ActiveTaskRepository.complete/cancel/claim/...` 这类带版本条件的更新。
3. 如果 CAS 更新返回 0，说明数据已被别人修改，必须停止后续写入。
4. 只有 CAS 成功后，才能写历史任务、写回调 Outbox、更新幂等成功结果。

## 4. 审批意见实现

### 4.1 功能目标

审批意见是用户在审批、驳回、退回等动作里提交的文本。M2 不新建 `process_comment` 表，而是把意见作为历史任务的一部分保存。

原因是审批意见天然依附于一次任务处理动作：谁处理、处理哪个节点、什么动作、什么时候完成、意见是什么，都可以由同一条历史任务表达。

### 4.2 数据库落点

表：`process_history_task`

字段：

- `comment_text`：审批意见正文。
- `active_task_id`：被归档的活动任务 ID。
- `action_type`：本次处理动作，例如 `APPROVE`、`REJECT`。
- `operation_id`：本次幂等操作 ID。
- `assignee_user_id`、`assignee_user_name`：处理人。
- `completed_at`：处理完成时间。

幂等约束：

- `UNIQUE(active_task_id, action_type, operation_id)`

同一个任务、同一个动作、同一个操作 ID 重复归档时，只返回已有历史任务，不重复插入审批意见。

### 4.3 写入实现

`HistoryTaskWriter`

- B 线在活动任务 CAS 成功后调用。
- `archiveCompletedTask(RuntimeTaskContext, actionType, comment, variablesSnapshot, operationId)` 用于归档正常完成的任务。
- `archiveCanceledTask(...)` 用于归档取消类任务。
- `archiveBatch(...)` 用于批量归档。
- 内部把 `comment` 写入 `process_history_task.comment_text`。
- 内部把变量快照序列化后写入 `process_history_task.variables_snapshot`。
- 如果遇到唯一约束冲突，会按 `activeTaskId/actionType/operationId` 查询已有历史任务并返回，保证归档幂等。

`ProcessHistoryTaskRepository`

- `insert(...)` 插入历史任务。
- `findByTaskActionOperation(activeTaskId, actionType, operationId)` 查询重复归档记录。
- `existsByTaskActionOperation(...)` 判断是否已归档。
- `findByInstanceId(instanceId)` 查询实例下全部历史任务。

### 4.4 查询实现

`DefaultTaskQueryService.queryComments(instanceId)`

- 不查单独评论表。
- 先调用 `ProcessHistoryTaskRepository.findByInstanceId(instanceId)`。
- 再通过 `ProcessTraceAssembler.toComment(...)` 转成 `ProcessCommentDTO`。
- `comment_text` 为空或全空白的历史任务会被过滤掉。
- `ProcessCommentDTO.commentId` 使用历史任务 ID。

## 5. 流程轨迹实现

### 5.1 功能目标

流程轨迹展示一个实例从开始到当前已经走过的节点和处理动作。M2 的轨迹数据来源就是历史任务表，不再新增 `process_trace` 表。

### 5.2 数据库落点

表：`process_history_task`

轨迹相关字段：

- `instance_id`：流程实例。
- `node_code`：节点编码。
- `task_group_id`：任务组 ID，后续支持并行、会签、或签展示。
- `branch_key`：分支标识。
- `assignee_user_id`、`assignee_user_name`：处理人。
- `delegate_from_user_id`、`delegate_from_user_name`：委托来源。
- `handle_type`：处理方式。
- `action_type`：处理动作。
- `comment_text`：审批意见。
- `variables_snapshot`：当次处理后的变量快照。
- `started_at`、`completed_at`：开始和完成时间。
- `extra_json`：扩展信息。

### 5.3 写入实现

流程轨迹不是单独写入的。B 线每完成一个活动任务，就调用 `HistoryTaskWriter` 归档一次，这条历史任务同时承担两个角色：

- 作为历史任务记录，用于已办和轨迹查询。
- 作为审批意见记录，用于意见查询。

写入时机必须在活动任务 CAS 成功之后，避免 CAS 失败却出现历史轨迹。

### 5.4 查询实现

`DefaultTaskQueryService.queryHistoryTasks(instanceId)`

- 调用 `ProcessHistoryTaskRepository.findByInstanceId(instanceId)`。
- Repository 按 `started_at ASC, completed_at ASC, id ASC` 排序，保证轨迹展示顺序稳定。
- 调用 `ProcessTraceAssembler.toHistoryTaskDTO(...)` 组装 `HistoryTaskDTO`。
- `variables_snapshot` 用 Jackson 反序列化为 `Map`；为空时返回空 Map。

`DefaultTaskQueryService.queryCompletedTasks(CompletedTaskQuery)`

- 调用 `ProcessHistoryTaskRepository.queryCompletedTasks(query)`。
- 支持按已办条件分页查询。
- 同样通过 `ProcessTraceAssembler` 转 DTO。

当前 `TaskQueryService` 中已实现：

- `queryCompletedTasks(...)`
- `queryHistoryTasks(instanceId)`
- `queryComments(instanceId)`

当前仍未实现：

- `queryTodoTasks(...)`
- `queryStartedInstances(...)`
- `queryActiveTasks(instanceId)`
- `queryReadRecords(...)`

这些留给 M3 查询能力继续补齐。

## 6. 回调幂等和 Outbox 实现

### 6.1 功能目标

流程运行期动作成功后，需要产生回调事件，但不能在主业务事务里同步调用外部系统。M2 采用 Outbox 模式：主业务事务中只把事件写入 `process_callback_log`，状态为 `PENDING`，后续由扫描器或投递组件异步投递。

### 6.2 数据库落点

表：`process_callback_log`

关键字段：

- `event_id`：回调事件幂等键，数据库唯一约束。
- `instance_id`：流程实例 ID。
- `operation_id`：触发该事件的操作 ID。
- `event_type`：事件类型。
- `action_type`：动作类型。
- `payload_json`：完整 `WorkflowEvent` JSON。
- `callback_status`：`PENDING`、`SUCCESS`、`FAILED`。
- `retry_count`：重试次数。
- `last_error`：最后一次失败原因。
- `created_at`、`updated_at`：创建和更新时间。

索引：

- `event_id` 唯一，防止同一事件重复写入。
- `idx_process_callback_log_status(callback_status, created_at)` 支持后续扫描待投递事件。
- `idx_process_callback_log_operation(operation_id, event_type)` 支持按操作排查回调。

### 6.3 代码分工

`WorkflowEventFactory`

- 负责生成 `WorkflowEvent`。
- 推荐事件 ID 格式：`operationId + ":" + eventType.name() + ":" + sequence`。
- 同一个业务动作内如果要发多个事件，用 `sequence` 区分，确保事件 ID 稳定。

`CallbackOutboxService`

- `appendPending(WorkflowEvent event)` 写入一条 `PENDING` 回调日志。
- `appendPendingBatch(List<WorkflowEvent> events)` 批量写入。
- 写入前按 `event_id` 查询已有记录。
- 如果已有记录和本次事件业务字段、载荷一致，视为幂等成功，直接返回旧记录。
- 如果已有记录和本次事件不一致，抛 `FLOW_CALLBACK_EVENT_CONFLICT`。
- 不调用外部 `WorkflowCallbackHandler`。
- 不负责把状态更新成 `SUCCESS` 或 `FAILED`。

`DefaultCallbackService`

- 实现 API 层 `CallbackService`。
- `publishCallback(event)` 当前等价于写入 Outbox。
- 方法会检查当前线程必须已有事务，避免回调日志独立提交而主业务回滚。
- `queryCallbackLogs(query)` 查询回调日志并映射为 `CallbackLogDTO`。

`ProcessCallbackLogRepository`

- `insert(...)` 插入 `process_callback_log`。
- `findByEventId(...)` 做回调幂等判断。
- `query(...)`、`count(...)` 支持分页查询。
- `markSuccess(...)`、`markFailed(...)` 已作为仓储能力保留，M2 当前不主动调用。

### 6.4 B 线接入方式

运行期动作成功后，B 线建议这样使用：

1. 主业务写入仍处于同一事务。
2. 使用 `WorkflowEventFactory` 根据 `operationId`、实例、任务、动作生成稳定事件。
3. 调用 `CallbackOutboxService.appendPending(...)` 或 `DefaultCallbackService.publishCallback(...)`。
4. 只要主事务提交，回调日志就和主业务状态一起落库。
5. 后续投递组件扫描 `callback_status = 'PENDING'` 的记录再调用外部 SPI。

注意：M2 不要在 `publishCallback(...)` 中直接调用外部 HTTP 或 `WorkflowCallbackHandler`。外部系统慢、超时或失败不应该阻塞和污染主业务事务。

## 7. 推荐的任务办理总流程

以任务审批为例，B 线可以按以下顺序接入 C 线能力：

1. 生成 `operationId` 和稳定 `requestHash`。
2. 调用 `OperationIdempotencyService.beginOrReplay(...)`。
3. 如果是重放或冲突，按幂等决策直接返回或抛错。
4. 调用 `RuntimeStateValidator.validateTaskAction(...)` 获取 `RuntimeTaskContext`。
5. B 线执行活动任务 CAS 更新，例如完成、取消、签收、退回等。
6. CAS 返回 0 时停止流程，抛并发修改错误，不写历史、不写回调、不标记幂等成功。
7. CAS 成功后调用 `HistoryTaskWriter.archiveCompletedTask(...)`，写入流程轨迹和审批意见。
8. B 线继续处理主状态机，例如创建下一节点任务、更新任务组、办结实例。
9. 使用 `WorkflowEventFactory` 创建事件，调用 `CallbackOutboxService.appendPending(...)` 写入回调 Outbox。
10. 调用 `OperationIdempotencyService.markSuccess(...)` 保存首次成功结果。
11. 如果第 4 步或业务规则校验发生确定性失败，调用 `markFailed(operationId, errorCode)` 保存失败结果。

事务边界建议：

- `beginOrReplay(...)` 先独立写入或判断幂等记录，只有 `NEW` 或 `TAKE_OVER` 才进入主业务事务。
- 主业务事务内完成状态校验、活动任务 CAS、历史归档、实例/任务组更新、回调 Outbox。
- `markSuccess(...)` 建议在主业务写入完成后调用；当前实现会参与调用方事务，B 线需要保证它和成功结果的提交时机一致。
- `markFailed(...)` 用于确定性失败固化，当前实现会独立提交失败错误码。
- 对外 HTTP 回调不放在这个事务中。
- 不确定失败不要标记为 `FAILED`，保留 `PROCESSING` 给租约过期接管。
