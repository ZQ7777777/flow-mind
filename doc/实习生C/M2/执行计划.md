# 实习生 C：M2 运行期记录、轨迹与回调执行计划

## 1. 阶段目标

M2 的目标是把 M0 冻结的幂等、并发、回调事件和查询契约接入真实运行期动作，使 B 线的串行流程闭环具备可重复调用、可追踪、可查询和可回调的外围能力。

完成后，流程实例启动、申请节点提交、部门经理审批、财务确认和流程办结等关键动作应满足以下要求：

- 相同 `operationId` 的相同请求可安全重放，并返回首次处理结果。
- 相同 `operationId` 的不同请求被拒绝，不产生任何业务副作用。
- 任务级动作通过 `expectedTaskVersion` 和 `lock_version` 保证并发下只有一个请求成功。
- 每个会改变运行状态的动作都有历史轨迹、审批意见和回调日志。
- 回调写入与主业务数据处于同一数据库事务，外部投递失败不回滚主流程。

本阶段不实现完整高级流程能力，例如驳回、撤回、转办、加签、会签、或签、并行汇聚、超时催办和管理员修复；也不实现审计日志和实例级附件运行时能力。审计日志留到 M5，附件运行时保存、下载、删除和必填校验留到 M4。M2 写入的数据模型和幂等机制必须能支撑后续动作复用。

## 2. 当前基线

已有内容：

- M0 已冻结 `operationId`、`expectedTaskVersion`、`WorkflowEvent`、SPI、Starter 和并发幂等契约。
- SQLite 初始化脚本已包含运行期核心表，例如实例、活动任务、任务组、历史任务、操作记录、回调日志、审计日志和附件记录。M2 的写入重点是 `process_operation_record`、`process_history_task` 和 `process_callback_log`；状态校验和轨迹查询会读取 `process_instance`、`process_active_task`、`process_task_group`、`process_node` 等现有表。
- API DTO 已包含 `OperationResult`、`TaskActionResult`、`WorkflowEvent`、任务动作请求和查询 DTO。
- A 线 M1 已提供定义保存、完整定义详情和定义级删除能力。
- B 线 M1/M2 计划负责实例启动、普通串行审批、任务归档和后续任务创建。
- C 线 M1 已负责定义期表单字段、附件模板和定义附件配置；M2 不继续扩展运行时附件能力。

尚缺内容：

- 操作幂等记录的生产级 Repository 和服务编排。
- 审批意见、历史轨迹和回调日志的统一写入规则。
- 运行期状态校验器与稳定错误码。
- 回调日志 Outbox 写入、状态更新和查询能力。
- 与 B 线串行运行时闭环的同事务联调测试。

## 3. 职责边界

C 在 M2 负责：

1. 操作幂等记录的登记、冲突判断、成功结果快照保存和重放。
2. 任务动作和实例动作所需的运行状态校验组件。
3. 审批意见、历史轨迹和回调日志的写入支撑。
4. 回调事件 Outbox 的持久化、查询和失败状态记录。
5. 为 B 线运行时动作提供可复用的外围组件，不侵入 B 的流转决策。
6. 为 M3 查询和 M5/M6 高级动作保留稳定数据语义。

C 在 M2 不负责：

- 实例启动、任务创建、普通审批流转和流程办结的主状态机。
- 读取节点审批人规则并创建下一审批任务。
- 条件表达式、并行网关、会签、或签和复杂分支推进。
- 审计日志写入、审计查询和审计告警。
- 实例级附件保存、下载、删除、必填校验、权限页面和任务级附件管理。
- 真实文件存储服务或真实消息推送服务实现。
- 具体业务规则硬编码，例如入金金额校验、账号校验或业务单据校验。

## 4. 微任务拆分

### C2.1 M2 契约与数据语义整理

目标：

- 明确 `process_operation_record` 的目标类型、请求哈希、结果快照和过期时间语义。
- 明确历史轨迹、审批意见和回调日志分别保存什么信息。
- 明确回调事件 `eventId`、`operationId`、`eventType`、`archivedTasks`、`createdTasks` 和 `variables` 的落库边界。
- 明确审计日志和实例级附件不纳入 M2 交付范围，仅保留表结构和后续扩展边界。
- 明确所有状态修改入口必须携带 `operationId`，任务级修改必须携带 `expectedTaskVersion`。

交付：

- M2 契约说明补充到技术实现说明或阶段完成记录。
- 与 B 线确认运行时动作调用 C 组件的最小接口。
- 与 A/B 线确认审计日志和附件运行时能力留到后续阶段，不阻塞 M2 串行闭环。

### C2.2 操作幂等 Repository 与服务

目标：

- 复用现有 `ProcessOperationRecordRepository` 的新增、查询和状态更新能力，补齐 M2 运行时需要的小缺口。
- 复用并按运行时动作完善现有 `OperationIdempotencyService`。
- 支持请求摘要比对，防止同号不同请求被重复执行。
- 支持成功结果快照保存和重放。
- 支持 `PROCESSING/SUCCESS/FAILED` 状态流转。

能力要求：

- 首次请求登记为 `PROCESSING`。
- 同 `operationId`、同请求、`SUCCESS` 时返回首次结果。
- 同 `operationId`、不同请求时返回 `FLOW_OPERATION_ID_CONFLICT`。
- 同 `operationId`、同请求、`PROCESSING` 时返回处理中或按约定拒绝重复并发执行。
- 业务事务成功后保存 `SUCCESS` 和结果快照。
- 业务事务失败时保存 `FAILED` 或清理处理中记录，具体策略需与 B 线统一。

数据库操作：

- 操作表：`process_operation_record`。
- 首次进入修改类动作时插入一条 `PROCESSING` 记录，不能等业务成功后再补插。
- `operation_id` 使用表唯一约束作为幂等入口，同一 `operationId` 只能对应一个规范化请求。
- 插入字段至少包括：
  - `id`
  - `operation_id`
  - `instance_id`，实例动作可填，定义动作或未创建实例前可空
  - `task_id`，任务动作可填
  - `action_type`
  - `operator_id`
  - `request_hash`
  - `operation_status = PROCESSING`
  - `processing_expires_at`
  - `expires_at`
  - `created_at`
  - `updated_at`
- 业务成功后更新同一行：`operation_status = SUCCESS`、`result_json = 首次返回结果快照`、`error_code = NULL`。
- 确定性失败后更新同一行：`operation_status = FAILED`、`error_code = 稳定错误码`、`result_json = NULL`。
- 进程异常、数据库连接中断等不确定失败保留 `PROCESSING`，等租约过期后允许相同请求接管。
- 已过期记录只允许由清理任务按 `expires_at` 清理；流程实例删除时未过期幂等记录仍保留，保证删除动作可重试。

建议类与方法：

- `ProcessOperationRecordRepository`
  - `findByOperationId(String operationId)`
  - `insert(ProcessOperationRecordEntity entity)`
  - `markSuccess(String operationId, String resultJson)`
  - `markFailed(String operationId, String errorCode)`
  - `extendProcessingLease(String operationId, LocalDateTime processingExpiresAt)`
  - 可选新增 `findExpired(LocalDateTime now, int limit)` 或后续清理任务所需查询；当前 M2 主链路不强制依赖
- `OperationIdempotencyService`
  - `beginOrReplay(operationId, actionType, operatorId, requestHash, now)`
  - `markSuccess(operationId, resultJson)`
  - `markFailed(operationId, errorCode)`
- `OperationIdempotencyDecision`
  - `NEW`：首次插入成功，允许进入业务执行
  - `REPLAY_SUCCESS`：直接反序列化 `result_json` 返回
  - `REPLAY_FAILED`：返回已记录错误
  - `IN_PROGRESS`：租约未过期，返回处理中
  - `TAKE_OVER`：租约已过期，相同请求接管
  - `CONFLICT`：同号不同请求，返回 `FLOW_OPERATION_ID_CONFLICT`

调用边界：

- A/B/C 所有修改类动作都必须先调用 `OperationIdempotencyService.beginOrReplay`。
- 业务 Service 不直接手写 `INSERT INTO process_operation_record`，统一走幂等组件。
- `requestHash` 由动作 Service 在进入幂等组件前生成，必须去掉时间戳、随机值等非业务字段。
- `markSuccess` 应与主业务写入、历史任务和回调日志处于同一数据库事务。
- `markFailed` 只用于确定性失败，例如权限不足、状态不允许、版本冲突、并发冲突。

验收：

- 重复提交同一请求不重复创建历史任务、活动任务和回调。
- 同号不同请求被拒绝。
- 并发登记同一 `operationId` 只有一个请求进入业务执行。

### C2.3 运行状态校验器

目标：

- 新增运行期状态校验组件，供 B 线任务办理和实例操作调用。
- 校验实例、任务、任务版本和可办理状态。
- 输出稳定错误码，不直接吞异常。

能力要求：

- 实例必须存在。
- 实例必须处于允许动作的状态，例如 `RUNNING` 才能继续办理任务。
- 活动任务必须存在并属于目标实例。
- 活动任务状态必须允许当前动作。
- 任务版本必须等于 `expectedTaskVersion`。
- 操作人上下文不得为空；权限细节由后续 SPI 或 B 线动作语义决定。

数据库访问：

- 运行状态校验器需要读取数据库，但不写数据库。
- 需要读取 `process_instance`：
  - `id`
  - `instance_status`
  - `definition_id`
  - `process_code`
  - `variables_json`
  - `current_node_codes`
- 需要读取 `process_active_task`：
  - `id`
  - `instance_id`
  - `node_code`
  - `task_status`
  - `assignee_user_id`
  - `candidate_user_ids`
  - `task_group_id`
  - `branch_key`
  - `lock_version`
- 后续涉及任务组动作时读取 `process_task_group`：
  - `id`
  - `group_type`
  - `group_status`
  - `total_count`
  - `completed_count`
  - `branch_state_json`
  - `lock_version`

建议类与方法：

- `ProcessInstanceRepository`
  - `findById(String instanceId)`
  - `updateStatusByVersion(...)` 可由 B 线主流程按需补充，C 的校验器不直接调用写方法
- `ActiveTaskRepository`
  - 新增 `findById(String taskId)`，供状态校验器读取活动任务上下文
  - 已有 CAS 写方法继续由 B 线业务 Service 调用，例如 `complete/cancel/claim/unclaim/transfer`
- `TaskGroupRepository`
  - 可选新增 `findById(String taskGroupId)`，供后续任务组状态校验复用
  - 任务组 CAS 更新方法继续由 B 线或后续并行汇聚组件调用
- `RuntimeStateValidator`
  - `validateTaskAction(taskId, expectedTaskVersion, actionType, operator)`
  - `validateInstanceAction(instanceId, actionType, operator)`
  - `validateTaskGroupState(taskGroupId, expectedGroupVersion, actionType)`
  - `validateTaskAction` 先按 `taskId` 读取 `process_active_task`，再通过任务上的 `instance_id` 读取 `process_instance`，返回 `RuntimeTaskContext`。
  - 返回 `RuntimeTaskContext` 或 `RuntimeInstanceContext`，把已读取的实例、任务、任务组带回业务层复用。

校验规则：

- `operator` 或 `operator.userId` 为空时，返回稳定错误码，例如 `FLOW_OPERATOR_REQUIRED`。
- 实例不存在时返回 `FLOW_INSTANCE_NOT_FOUND`。
- 任务不存在时返回 `FLOW_TASK_NOT_FOUND`。
- 任务不属于目标实例时返回 `FLOW_TASK_NOT_FOUND` 或 `FLOW_TASK_INSTANCE_MISMATCH`，需在 C2.1 固定。
- 办理类动作要求实例为 `RUNNING`，否则返回 `FLOW_INSTANCE_STATUS_INVALID`。
- `APPROVE/SEND` 要求任务为 `ACTIVE` 或 `CLAIMED`。
- `CLAIM` 要求任务为 `ACTIVE`。
- `UNCLAIM` 要求任务为 `CLAIMED`。
- `TRANSFER` 要求任务为 `ACTIVE` 或 `CLAIMED`。
- 完成类和取消类动作要调用 `ActiveTaskStatusValidator` 校验目标状态迁移。
- `expectedTaskVersion` 与 `lock_version` 不一致时返回 `FLOW_TASK_CONCURRENT_MODIFIED`。
- 校验通过后仍必须执行数据库 CAS；运行状态校验不能替代并发控制。

调用边界：

- `RuntimeStateValidator` 是内部 `@Service` 或 Guard 组件，不暴露成对外 API。
- 它只读数据库和抛出带稳定错误码的业务异常，不写历史、不写回调、不更新幂等记录。
- 外层运行时 Service 捕获确定性错误后，由幂等组件把本次操作标记为 `FAILED`。
- CAS 更新受影响行数为 0 时，以 Repository 冲突码映射为 `FLOW_TASK_CONCURRENT_MODIFIED` 或 `FLOW_TASK_GROUP_CONCURRENT_MODIFIED`，并禁止继续写历史和回调。

验收：

- 非运行中实例不可提交任务。
- 已完成、已取消或版本不匹配任务不可再次办理。
- 并发审批同一任务时，失败请求不产生历史或回调副作用。

### C2.4 审批意见与流程轨迹

目标：

- 补齐历史任务和审批意见的写入辅助能力。
- 提供按实例查询完整流程轨迹的能力。
- 为 M3 的已办、历史轨迹和审批意见查询打基础。

能力要求：

- 流程轨迹表示一个流程实例从发起到当前为止经过了哪些人工任务，以及每个任务由谁在什么时候做了什么动作。
- 历史任务记录节点编码、任务 ID、任务组、分支、处理人、处理类型、审批意见、开始时间、完成时间、动作类型和变量快照。
- 申请节点提交、部门经理审批、财务确认均必须进入历史轨迹。
- 审批意见不单独建表，直接来自 `process_history_task.comment_text`。
- 查询轨迹时返回 `HistoryTaskDTO`，查询意见时把历史任务转换为 `ProcessCommentDTO`。
- 查询结果按 `started_at, completed_at, id` 稳定排序；如果后续前端需要按节点顺序展示，可在查询层补充节点定义排序，但不能破坏时间线默认排序。
- 并行、会签、或签等后续能力虽然不在 M2 完整实现，但 M2 写入轨迹时必须保留 `task_group_id` 和 `branch_key`，避免后续轨迹展示丢失分支信息。
- 特殊动作的扩展信息写入 `extra_json`，例如驳回目标、退回原因、管理员代理信息等，M2 先保留字段语义，复杂动作留到 M5/M6。

数据库操作：

- 主表：`process_history_task`。
- 不新增 `process_comment` 或 `process_trace` 表。
- 审批意见字段：`process_history_task.comment_text`。
- 变量快照字段：`process_history_task.variables_snapshot`，保存任务完成时的流程变量 JSON。
- 扩展字段：`process_history_task.extra_json`，只存结构化补充信息，不存业务大对象。
- 幂等约束：`UNIQUE(active_task_id, action_type, operation_id)`，同一个任务、同一个动作、同一个操作号不得重复归档。
- 写入历史前必须确认当前任务 CAS 已成功；CAS 失败时不得插入历史任务。
- 历史任务写入必须与活动任务状态更新、下一任务创建、实例状态更新、回调日志和幂等成功结果在同一数据库事务内完成。
- 流程实例删除时，应同步删除该实例下的 `process_history_task`；流程定义删除时，应级联删除该定义实例下的历史任务。

写入时机：

- `startProcess` 只创建实例和首个活动任务时，通常不写历史任务；是否写 `START` 轨迹由 B 线主流程和产品展示统一决定，M2 最小闭环以人工任务归档为准。
- `submitTask` 成功完成申请节点后，写一条 `SEND` 或约定动作类型的历史任务。
- `approve` 成功完成审批节点后，写一条 `APPROVE` 历史任务。
- 后续 `reject/return/withdraw/transfer/directSend/addSign/terminate/forceComplete` 等动作在 M5/M6 复用同一写入组件，只扩展 `action_type` 和 `extra_json`。
- 如果一次动作会取消多个活动任务，例如后续或签成功取消其他候选任务，应为每个被取消任务写一条 `CANCEL` 历史，且共享同一个 `operation_id`。

历史任务字段来源：

| 历史字段 | 来源 |
| --- | --- |
| `id` | C 线历史写入组件生成，建议 UUID |
| `instance_id` | 活动任务或运行时上下文 |
| `operation_id` | 本次修改请求的幂等号 |
| `active_task_id` | 被归档的 `process_active_task.id` |
| `node_code` | 活动任务的 `node_code` |
| `task_group_id` | 活动任务的 `task_group_id` |
| `branch_key` | 活动任务的 `branch_key` |
| `assignee_user_id` | 实际办理人，优先取当前操作人；如已有认领人需按 B 线语义确认 |
| `assignee_user_name` | 实际办理人名称快照 |
| `delegate_from_user_id` | 委托代办来源用户，非委托为空 |
| `delegate_from_user_name` | 委托代办来源用户名称，非委托为空 |
| `handle_type` | `NORMAL/DELEGATE/TRANSFER/ADMIN_PROXY` |
| `action_type` | 本次动作，例如 `SEND/APPROVE/CANCEL` |
| `comment_text` | 请求里的 `comment`，无意见可为空 |
| `variables_snapshot` | 任务完成后的 `process_instance.variables_json` 快照 |
| `started_at` | 活动任务 `created_at` 或业务指定的任务开始时间 |
| `completed_at` | 当前归档时间 |
| `extra_json` | 动作附加上下文 |

建议类与方法：

- `ProcessHistoryTaskRepository`
  - `insert(ProcessHistoryTaskEntity entity)`
  - `findByInstanceId(String instanceId)`
  - `findByActiveTaskId(String activeTaskId)`
  - `existsByTaskActionOperation(String activeTaskId, ActionTypeEnum actionType, String operationId)`
  - `queryCompletedTasks(CompletedTaskQuery query)`
  - `countCompletedTasks(CompletedTaskQuery query)`
  - `deleteByInstanceId(String instanceId)`
- `HistoryTaskWriter`
  - `archiveCompletedTask(RuntimeTaskContext context, ActionTypeEnum actionType, String comment, Map<String, Object> variablesSnapshot, String operationId)`
  - `archiveCanceledTask(ProcessActiveTaskEntity task, ActionTypeEnum actionType, String reason, String operationId)`
  - `archiveBatch(List<HistoryArchiveCommand> commands)`
- `HistoryArchiveCommand`
  - 承载一次归档所需的任务、实例、操作人、动作、意见、变量快照和扩展信息。
- `ProcessTraceAssembler`
  - `toHistoryTaskDTO(ProcessHistoryTaskEntity entity)`
  - `toCommentDTO(ProcessHistoryTaskEntity entity)`
  - `toCommentDTO` 只转换 `comment_text` 非空的历史任务。
- `DefaultTaskQueryService implements TaskQueryService`
  - `queryHistoryTasks(String instanceId)`
  - `queryComments(String instanceId)`
  - M2 可以先实现上述两个方法；同一类中其它 `TaskQueryService` 方法暂时按 M3 计划返回稳定的 `UnsupportedOperationException` 或保持既有骨架实现，不能留下编译缺口。
- `ProcessInstanceDetailAssembler`
  - 聚合 `ProcessInstanceDTO`、活动任务、历史轨迹和审批意见，供 `ProcessRuntimeService.getInstance` 复用。

Service 接入点：

- `TaskQueryService.queryHistoryTasks(instanceId)`
  - 校验 `instanceId` 非空。
  - 调用 `ProcessHistoryTaskRepository.findByInstanceId(instanceId)`。
  - 通过 `ProcessTraceAssembler.toHistoryTaskDTO` 转换为 `HistoryTaskDTO`。
  - 按 `startedAt, completedAt, historyTaskId` 保持稳定顺序。
- `TaskQueryService.queryComments(instanceId)`
  - 校验 `instanceId` 非空。
  - 复用历史任务查询结果。
  - 过滤 `comment_text` 为空或全空白的记录。
  - 映射为 `ProcessCommentDTO`。
  - `commentId` 建议使用历史任务 ID，避免制造第二套意见 ID。
  - `taskId` 对应原活动任务 ID，即 `process_history_task.active_task_id`。
  - `createdAt` 对应 `process_history_task.completed_at`。
- `ProcessRuntimeService.getInstance(instanceId)`
  - B 线提供实例基础信息。
  - C 线补齐或提供聚合方法查询 `activeTasks/historyTasks/comments`。
  - 返回 `ProcessInstanceDetailDTO`，其中 `historyTasks` 来自 `queryHistoryTasks`，`comments` 来自 `queryComments`。

与 B 线运行时的协作：

- B 线负责实例启动、任务创建、流转决策和任务 CAS。
- C 线提供 `HistoryTaskWriter`，由 B 在线程内、同事务中调用。
- B 必须在活动任务 CAS 成功后再调用 `HistoryTaskWriter`。
- B 创建下一活动任务后，把本次归档任务和新建任务一起交给回调事件构造组件。
- 如果 B 的动作因为状态校验或 CAS 失败而终止，C 不得写入历史轨迹。
- 重放成功请求时，B/C 应直接返回 `process_operation_record.result_json`，不得再次调用历史写入组件。

与回调和幂等的关系：

- 历史轨迹用于面向用户展示流程经过和审批意见。
- 回调日志用于通知外部系统，不替代历史轨迹。
- 幂等记录用于重放结果，不替代历史轨迹。
- 一次成功任务动作的同事务写入顺序建议为：
  1. 活动任务 CAS 更新为 `COMPLETED` 或 `CANCELED`。
  2. 写 `process_history_task`。
  3. 更新任务组或创建下一活动任务。
  4. 更新实例 `current_node_codes/instance_status/variables_json`。
  5. 写 `process_callback_log(PENDING)`。
  6. 更新 `process_operation_record(SUCCESS, result_json)`。

查询返回要求：

- `HistoryTaskDTO.historyTaskId` 映射 `process_history_task.id`。
- `HistoryTaskDTO.activeTaskId` 映射 `active_task_id`。
- `HistoryTaskDTO.comment` 映射 `comment_text`。
- `HistoryTaskDTO.variablesSnapshot` 由 `variables_snapshot` JSON 反序列化。
- `HistoryTaskDTO.actionType` 和 `handleType` 使用枚举转换；未知值应按稳定错误处理，不静默吞掉。
- `ProcessCommentDTO.commentId` 使用历史任务 ID。
- `ProcessCommentDTO.operatorUserId/operatorUserName` 映射历史任务实际办理人。
- `ProcessCommentDTO.createdAt` 映射历史任务完成时间。

测试要求：

  - 按实例 ID 查询，并按 `started_at, completed_at, id` 排序。
  - 相同 `active_task_id + action_type + operation_id` 重复插入被唯一约束阻止。
  - 删除实例或定义级级联时历史任务被清理。

### C2.5 回调日志 Outbox

目标：

- 实现 `ProcessCallbackLogRepository` 的写入、查询和状态更新能力。
- 支持业务事务内写入回调日志。
- 支持回调失败记录，不影响主业务结果。

能力要求：

- 每条回调日志包含唯一 `eventId`。
- 回调日志直接关联 `operationId`、实例 ID、事件类型和事件载荷；流程编码通过 `payload_json` 中的 `WorkflowEvent.processCode` 保存。
- `event_type` 必须使用现有 `WorkflowEventTypeEnum` 枚举值，不新增自由字符串事件类型。
- 事件载荷可以序列化完整 `WorkflowEvent`。
- 同一业务动作重放时不得重复写入新事件。
- 支持状态 `PENDING/SUCCESS/FAILED`。
- 支持记录失败原因和下次重试扩展字段。

数据库操作：

- 操作表：`process_callback_log`。
- 幂等键：`event_id`，依赖表唯一约束防止重复事件。
- 主业务事务内插入 `PENDING` 回调日志，字段至少包括：
  - `id`
  - `event_id`
  - `instance_id`
  - `operation_id`
  - `event_type`
  - `action_type`
  - `payload_json`
  - `callback_status = PENDING`
  - `retry_count = 0`
  - `last_error = NULL`
  - `created_at`
  - `updated_at`
- 投递成功后更新：
  - `callback_status = SUCCESS`
  - `updated_at = now`
- 投递失败后更新：
  - `callback_status = FAILED`
  - `retry_count = retry_count + 1`
  - `last_error = 失败原因`
  - `updated_at = now`
- 查询支持按 `instance_id`、`event_type`、`callback_status` 分页过滤。

回调幂等规则：

- 不新增单独的“回调幂等表”，直接使用 `process_callback_log.event_id`。
- `eventId` 不能随机生成，必须可稳定重建。
- 推荐格式：`operationId + ":" + eventType + ":" + sequence`。
- 同一业务操作产生多个事件时使用递增 `sequence` 区分，例如：
  - `op-001:TASK_COMPLETED:1`
  - `op-001:TASK_CREATED:2`
  - `op-001:PROCESS_COMPLETED:3`
- 重放同一成功 `operationId` 时直接返回 `process_operation_record.result_json`，不得重新构造事件或再次插入回调日志。
- 如果插入时发现 `event_id` 已存在且 `operation_id/event_type/action_type/payload_json` 均一致，视为幂等重放。
- 如果 `event_id` 已存在但载荷或动作不一致，说明事件生成规则错误，应返回内部冲突错误并阻断本次写入。

建议类与方法：

- `ProcessCallbackLogRepository`
  - `findByEventId(String eventId)`
  - `insertPending(ProcessCallbackLogEntity entity)`
  - `markSuccess(String eventId)`
  - `markFailed(String eventId, String lastError)`
  - `query(CallbackLogQuery query)`
  - `findPending(int limit)`，为后续扫描投递预留
- `CallbackOutboxService`
  - `appendPending(WorkflowEvent event)`
  - `appendPendingBatch(List<WorkflowEvent> events)`
  - 只负责事务内落库，不直接调用外部回调 SPI
- `DefaultCallbackService implements CallbackService`
  - `publishCallback(WorkflowEvent event)`
  - `queryCallbackLogs(CallbackLogQuery query)`
  - M2 当前只负责在调用方当前事务中写入 `PENDING` Outbox，不同步调用外部处理器
- `WorkflowEventFactory` 或 `WorkflowEventBuilder`
  - 生成稳定 `eventId`
  - 从本次归档任务、新建任务和变量快照构造完整 `WorkflowEvent`
- `CallbackLogMapper`
  - `ProcessCallbackLogEntity` 与 `CallbackLogDTO` 转换
  - `WorkflowEvent` 与 `payload_json` 序列化

调用边界：

- B 线运行时 Service 在主业务事务内调用 `CallbackOutboxService.appendPending`。
- `CallbackOutboxService` 必须和活动任务更新、历史任务、幂等成功结果处于同一事务。
- `CallbackService.publishCallback(event)` 在 M2 当前实现中等价于写入 `process_callback_log(PENDING)`，必须复用当前主业务事务，不开启独立事务。
- 外部投递通过后续扫描器或投递组件调用 `WorkflowCallbackHandler.handle(event)` 完成，必须发生在主事务提交之后。
- `WorkflowCallbackHandler` 抛异常时不能回滚流程实例、活动任务、历史任务或幂等成功结果；失败状态更新由后续投递组件处理。

验收：

- 实例启动、任务创建、任务完成、流程完成等关键动作有回调日志。
- 回调日志中的归档任务和新建任务信息与实际数据库记录一致。
- 模拟回调投递失败时主流程不回滚，失败状态可查询。

### 5.2 幂等动作处理流程

1. 接收状态修改请求，读取 `operationId`。
2. 对请求关键字段生成稳定 `requestHash`。
3. 查询 `process_operation_record`。
4. 如果不存在，插入 `PROCESSING` 记录。
5. 如果存在且 `requestHash` 不一致，返回 `FLOW_OPERATION_ID_CONFLICT`。
6. 如果存在且状态为 `SUCCESS`，反序列化首次结果并返回，标记 `replayed=true`。
7. 如果存在且状态为 `PROCESSING`，返回处理中或重复请求错误，具体按 B 线约定。
8. 进入业务事务，执行状态校验、任务 CAS、历史归档、后续任务创建和回调日志写入。
9. 业务事务成功后，把幂等记录更新为 `SUCCESS`，保存结果快照。
10. 业务事务失败时，把幂等记录更新为 `FAILED` 或允许后续重试，策略必须在 C2.1 固定。

落地要求：

- 幂等入口统一走 `OperationIdempotencyService.beginOrReplay`。
- 首次请求由 `ProcessOperationRecordRepository.insert` 写入 `process_operation_record(PROCESSING)`。
- `operation_id` 唯一约束是并发下的最终幂等入口；如果两个线程同时插入同一 `operationId`，只允许一个成功，另一个重新查询并按重放逻辑处理。
- `requestHash` 必须覆盖会影响业务结果的字段，例如 `instanceId/taskId/actionType/variables/comment/expectedTaskVersion`；不应包含当前时间、随机 ID、签名时间戳等非业务字段。
- `resultJson` 保存对外返回对象的最小快照，例如 `TaskActionResult` 或 `OperationResult`，确保重复请求无需重新查询复杂运行状态即可返回第一次结果。
- 权限不足、实例状态不允许、任务状态不允许、版本冲突、任务组冲突等确定性失败要 `markFailed(operationId, errorCode)`。
- 数据库连接中断、进程退出、未知异常等不确定失败不应误标 `FAILED`，保留 `PROCESSING` 等待租约过期后同请求接管。
- `SUCCESS + resultJson` 更新必须与主业务写入同事务提交，避免业务成功但幂等结果丢失。

### 5.3 任务办理处理流程

1. B 线收到 `submitTask` 或审批动作请求。
2. C 线幂等组件登记 `operationId`。
3. C 线状态校验器校验实例状态、任务状态和 `expectedTaskVersion`。
4. B 线用 `taskId + expectedTaskVersion + status` 执行 CAS 更新活动任务。
5. CAS 失败时返回并发冲突，不写历史、回调和后续任务。
6. CAS 成功后，B 线归档当前任务。
7. C 线辅助写入审批意见和历史轨迹。
8. B 线根据定义快照创建下一活动任务，或将实例置为完成。
9. C 线写入回调日志，事件中携带归档任务、新建任务和变量快照。
10. 事务提交后，返回 `TaskActionResult` 并保存到幂等结果快照。

建议伪代码：

```java
OperationIdempotencyDecision decision = idempotencyService.beginOrReplay(
        request.getOperationId(), actionType, operator.getUserId(), requestHash, now);
if (decision.isReplay()) {
    return restoreTaskActionResult(decision.getRecord().getResultJson(), true);
}
if (!decision.canExecute()) {
    throw mapIdempotencyDecision(decision);
}

return transactionTemplate.execute(status -> {
    RuntimeTaskContext context = runtimeStateValidator.validateTaskAction(
            request.getTaskId(),
            request.getExpectedTaskVersion(),
            actionType,
            operator);

    int updated = activeTaskRepository.complete(
            request.getTaskId(), request.getExpectedTaskVersion());
    if (updated != 1) {
        idempotencyService.markFailed(request.getOperationId(),
                "FLOW_TASK_CONCURRENT_MODIFIED");
        throw new RuntimeValidationException("FLOW_TASK_CONCURRENT_MODIFIED");
    }

    HistoryTaskDTO archived = historyWriter.archiveCurrentTask(context, request);
    List<TaskDTO> created = runtimeMainFlow.createNextTasks(context);
    callbackOutboxService.appendPendingBatch(
            workflowEventFactory.taskEvents(context, archived, created, request));

    TaskActionResult result = buildResult(request, archived, created);
    idempotencyService.markSuccess(request.getOperationId(), toJson(result));
    return result;
});
```

说明：上述伪代码只表达编排顺序；实际实现可按 `OperationIdempotencyDecisionType` 判断重放、处理中、接管或冲突，不要求现有 `OperationIdempotencyDecision` 必须已有 `isReplay/canExecute` 方法。

边界说明：

- 上述 `runtimeMainFlow.createNextTasks` 代表 B 线主状态机，C 不实现该决策。
- `RuntimeStateValidator` 只读库校验，最终并发控制仍由 `ActiveTaskRepository.complete/cancel/claim/...` 的 CAS 保证。
- CAS 失败后不能再写历史、回调、下一任务；如果已经写入，说明事务边界或调用顺序错误。
- `callbackOutboxService.appendPendingBatch` 只写 `process_callback_log(PENDING)`，不能在事务内调用外部回调。

### 5.4 回调日志处理流程

1. 业务动作完成状态修改后，构造 `WorkflowEvent`。
2. 使用稳定规则生成或传入唯一 `eventId`。
3. 在同一数据库事务内写入 `process_callback_log`，初始状态为 `PENDING`。
4. M2 当前 `CallbackService.publishCallback(event)` 只在当前事务内写入 `PENDING` Outbox。
5. 事务提交后由后续扫描器或投递器执行外部回调。
6. 投递成功时更新为 `SUCCESS`。
7. 投递失败时更新为 `FAILED`，记录失败原因。
7. 失败不回滚流程实例、活动任务、历史任务或幂等成功结果。

事件生成规则：

- `WorkflowEvent.eventId` 由 C 提供的工厂方法稳定生成，业务方可传入 `operationId/WorkflowEventTypeEnum/sequence`。
- 同一动作需要同时表达“任务完成”和“下一任务创建”时，可以生成多条事件，但每条事件的 `eventId` 必须不同且可复算。
- `payloadJson` 保存完整 `WorkflowEvent`，至少包含：
  - `eventId`
  - `operationId`
  - `eventType`
  - `processCode`
  - `instanceId`
  - `actionType`
  - `operator`
  - `archivedTasks`
  - `createdTasks`
  - `variables`
  - `occurredAt`

写入流程：

1. `WorkflowEventFactory` 根据本次业务结果生成事件列表。
2. `CallbackOutboxService.appendPendingBatch` 遍历事件。
3. 对每个事件先查 `ProcessCallbackLogRepository.findByEventId`。
4. 不存在则插入 `PENDING`。
5. 已存在且载荷一致则跳过，视为幂等重放。
6. 已存在但载荷不一致则抛出回调事件冲突错误，防止同一个 `eventId` 指向不同业务事实。

投递流程：

1. M2 当前不在 `CallbackService.publishCallback(event)` 内投递外部回调。
2. 后续扫描器读取 `PENDING/FAILED` 记录重试。
3. 投递组件调用 `WorkflowCallbackHandler.handle(event)`。
4. 调用成功后执行 `ProcessCallbackLogRepository.markSuccess(eventId)`。
5. 调用失败后捕获异常，执行 `markFailed(eventId, lastError)`。
6. 投递异常不继续向主流程抛出，只记录回调日志状态；必要时 M5/M6 再接入告警。

查询流程：

- `CallbackService.queryCallbackLogs(CallbackLogQuery query)` 和 `AdminProcessService.queryCallbackLogs(query)` 均可复用同一个查询组件。
- 查询入参支持 `instanceId/eventType/callbackStatus/pageNo/pageSize`。
- 返回 `PageResult<CallbackLogDTO>`，按 `created_at DESC, id DESC` 稳定排序。

### 5.5 入金申请联调流程

1. A 线创建并激活入金申请流程定义：开始、申请节点、部门经理审批、财务确认、结束。
2. B 线启动流程实例，保存流程变量，创建申请节点活动任务。
3. C 线根据启动结果写入回调日志；是否写启动历史由 B 线和产品展示统一决定。
4. B 线归档申请节点任务，创建部门经理审批任务。
5. C 线写入申请节点历史、审批意见和回调日志。
6. 部门经理审批通过，B 线创建财务确认任务，C 线同步写入历史、审批意见和回调。
7. 财务确认通过，B 线办结实例，C 线同步写入历史、审批意见和流程完成回调。
8. 查询实例历史轨迹，确认三段任务均存在且审批意见完整。
9. 查询回调日志，确认关键动作均可追踪。
10. 重放任一成功动作，确认返回首次结果且没有重复历史或回调。

## 8. 风险与决策点

1. 幂等记录失败策略需要统一：业务执行异常后是保留 `FAILED` 结果还是释放重试机会，必须与 B 线一致。
2. 回调日志与外部投递需要分层：M2 先保证 Outbox 持久化和状态记录，不把真实网络投递夹在主事务中。
3. 历史任务和回调日志容易重复表达同一事件，需要明确各自职责，避免查询层混用。
4. 审计日志不纳入 M2，否则会扩大事务副作用和查询范围；M2 只预留 `operationId/actionType/operator` 等字段，后续 M5 再接入审计写入。
5. 实例级附件不纳入 M2，否则会引入文件存储、权限和必填校验链路；M2 只消费变量和任务信息，附件运行时能力留到 M4。
6. 并发测试必须覆盖真实数据库约束和 CAS 更新，不能只用内存对象模拟。
7. C 不应实现 B 的流转状态机；C 组件只提供校验、记录、查询和外围支撑。

## 9. M2 完成标准

- 操作幂等记录具备生产级 Repository 和服务能力。
- 相同 `operationId` 重放不会重复生成历史、活动任务或回调。
- 同号不同请求被稳定拒绝。
- 任务级动作能通过 `expectedTaskVersion` 和 `lock_version` 防止并发重复办理。
- 审批意见和流程轨迹可按实例完整查询。
- 回调日志 Outbox 可写入、可查询、可标记失败。
- 与 B 线完成入金申请串行闭环联调。
- 审计日志和实例级附件运行时能力已明确移出 M2，并记录到后续阶段范围。
- `mvn -q -pl platform/platform-core -am test` 和根目录 `mvn -q test` 通过。
