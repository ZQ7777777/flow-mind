# 实习生 B 技术实现说明

本文件记录已落地的技术契约，避免与实施计划重复。后续 M1～M6 按阶段追加实际实现说明。
## M0：运行时请求契约

### 位置与边界

- 代码包：`com.flowmind.platform.api.request`，位于 `platform-core`。
- 使用 Java 8 JavaBean：公开无参构造及标准 getter/setter；可手写访问器，也可使用 Lombok `@Data`，禁止使用 `record` 或 Java 9+ API。
- M0 不包含流程流转、持久化、SPI、Starter 自动装配、事件或输入校验逻辑。

### 请求继承

```text
OperationRequest
├─ 实例级请求
│  ├─ StartProcessRequest
│  ├─ UpdateVariablesRequest
│  ├─ TerminateProcessRequest
│  ├─ DeleteProcessInstanceRequest
│  ├─ JumpNodeRequest
│  └─ ForceCompleteRequest
└─ TaskOperationRequest
   ├─ SubmitTaskRequest
   ├─ ApproveTaskRequest / RejectTaskRequest / ReturnTaskRequest
   ├─ WithdrawTaskRequest / DirectSendRequest
   ├─ TransferTaskRequest / AddSignRequest
   └─ ClaimTaskRequest / UnclaimTaskRequest / RemindTaskRequest
```

- `OperationRequest`：`operationId`，所有状态修改请求共用。
- `TaskOperationRequest`：继承 `OperationRequest`，增加 `taskId`、`expectedTaskVersion`（`Long`）、`operatorUserId`、`comment`。
- `JumpNodeRequest` 是实例级请求，只含实例 ID 与目标节点等字段，不继承任务基类，也不携带任务版本。

### 关键字段

| 类型 | 已冻结字段 |
| --- | --- |
| `StartProcessRequest` | 流程编码、业务键、实例标题、发起人、发起部门、变量 |
| `UpdateVariablesRequest` | 实例 ID、操作人、变量 |
| `SubmitTaskRequest` | 任务基类字段、变量、`List<AttachmentUploadItem>` |
| 定向动作 | 驳回、直送、跳转使用 `targetNodeCode`；转办使用 `targetUserId`；加签使用 `addSignUserIds` |
| 实例操作 | 终止、删除、跳转、强制办结均包含 `instanceId`；需要操作人/意见的请求显式携带相应字段 |
| `AttachmentUploadItem` | 附件模板编码、归属类型、文件名、内容类型、大小、`byte[] content` |

`AttachmentUploadItem` 位于 `com.flowmind.platform.api.request`，是上传请求的内存载荷，不表示文件存入 SQLite；后续实现须通过文件存储 SPI 保存实际内容。

### 附件访问失败关闭（B0.5）

- Starter 始终为缺失的 `AttachmentAccessProvider` 注册拒绝全部访问的后备实现；关闭本地 Mock 不会产生隐式放行。
- `AttachmentAccessGuard` 是附件 Service 的统一授权边界，只有 SPI 明确返回 `true` 才允许继续；SPI 缺失、返回拒绝或抛出运行时异常均返回 `false`。
- 单元测试分别覆盖缺失、拒绝、异常和明确允许；附件业务实现必须在调用 `FileStorageProvider` 之前通过 Guard。

### 已知阶段边界

- M0 的夹具只证明 DTO 可表达有效请求，不代替运行时非空、权限、幂等或乐观锁校验。
- 运行时校验、幂等执行、任务状态变更、附件 SPI 调用和数据库操作留待后续阶段实现。

## M2：运行时持久化原语（第一步）

- `ProcessDefinitionRepository.findActiveFullByProcessCode` 只服务新实例启动：严格筛选 `PUBLISHED`、`ACTIVE`、`gray_status=OFF` 的全量激活定义。SQLite 的局部唯一索引保证同一流程编码最多一条该状态的定义；运行中实例不使用此查询重新选择版本。
- `ProcessInstanceRepository` 提供实例插入、按 ID 读取、变量 JSON 与当前节点 JSON 的状态受限覆盖，以及从 `RUNNING` 到 `COMPLETED` 的办结原语。变量读取、浅合并和幂等语义由后续 Runtime Service 在事务内协调，仓储不重复实现业务规则。
- `ActiveTaskRepository` 与 `TaskGroupRepository` 在保留既有乐观锁 CAS 更新的前提下，补充插入、按 ID 读取和实例维度的活动记录统计；活动任务与历史任务分别以 `created_at + id`、`completed_at + id` 稳定排序。
- `HistoryTaskRepository` 只增写入归档快照，拒绝空 `operationId`，并让表上的 `(active_task_id, action_type, operation_id)` 唯一约束作为重复归档的最后防线。
- `RuntimeRowMappers` 集中映射四张运行时主表；`RuntimeJsonCodec` 使用 Jackson Java Time 模块处理变量、候选人、当前节点和分支状态 JSON。空白或 JSON 字面量 `null` 统一映射为空集合，候选人/节点数组必须全部为字符串，避免 Jackson 隐式类型转换污染运行时数据。
- `RuntimeModelMapper` 负责实体到 `ProcessInstanceDTO`、`TaskDTO` 和 `HistoryTaskDTO` 的枚举及 JSON 字段转换。任务节点名称和委托人展示名称仍由上层基于定义图和用户上下文补充。
- 新增 SQLite 集成测试覆盖定义选择、实例状态门禁、活动任务/任务组过滤与排序、历史唯一约束；新增 JSON/DTO 映射测试覆盖 Java Time、空值和异常结构。已执行 `mvn -q test`（`platform`）通过；子 agent 审查后补齐 JSON 边界回归。

## M2：定义加载、请求校验与幂等执行框架（第二步）

- `RuntimeDefinitionLoader` 不引入第二套定义读取接口。新实例通过 `ProcessDefinitionRepository.findActiveFullByProcessCode` 选择已发布、激活且非灰度的唯一版本，随后始终以 `definitionId` 读取 `ProcessDefinitionCache`；缓存缺失时先捕获世代令牌，读取 `ProcessDefinitionService#getDefinition` 的完整详情并执行 `DefinitionModelValidator`，确认仍可启动后再回填缓存。运行中实例绕过流程编码选版，只按冻结的 `definitionId` 加载，并核对 `processCode/version` 快照；已停用定义的缓存缺失读取不会回填缓存。
- `RuntimeRequestValidator` 依赖 `CurrentUserProvider` 作为身份真源。它校验启动、变量更新和任务操作的必填字段及当前用户一致性，限制变量更新到 `NOT_STARTED/RUNNING`，限制任务操作到 `RUNNING` 实例和 `ACTIVE/CLAIMED` 任务，并校验候选人/受理人权限与任务乐观锁版本。`ApproverResolver` 的结果保留首次出现顺序、按用户 ID 去重且不得为空；M2 只接受 `SINGLE`。
- `RuntimeRequestHasher` 针对请求对象、继承字段、Map、集合、枚举和附件生成稳定 SHA-256。它排除 `operationId`，排序 Map 键；`byte[]` 只作为内容摘要参与哈希。因此相同业务请求可重放，Map 插入顺序和幂等号变化不改变摘要，附件内容变化会改变摘要且原始字节不会进入操作记录。
- `OperationIdempotencyService` 保持为唯一幂等实现。新增带 `instanceId/taskId` 的重载和兼容性绑定；首次插入的唯一键竞争会重新读取记录；过期 `PROCESSING` 记录通过 `processing_expires_at <= now` 的条件更新竞逐接管权，确保一个请求获胜。`beginOrReplay` 改为参与外层事务，`RuntimeOperationExecutor.markSuccess` 与后续业务写入由同一 Runtime Service 事务提交；成功重放经 `RuntimeJsonCodec` 恢复 DTO，任务结果额外标记 `replayed=true`。`markFailed` 仅供确定性业务失败调用，数据库中断等未知结果继续保留处理中租约。
- 新增 `RuntimeDefinitionLoaderTest`、`RuntimeRequestValidatorTest`、`RuntimeRequestHasherTest` 和 `RuntimeOperationExecutorTest`，并扩展 `OperationIdempotencyServiceTest` 覆盖唯一键竞争重读、条件接管、目标绑定与延后绑定。`mvn -q test`（`platform`）已通过；子 agent 复审未发现 P0/P1。后续第五步需要补充业务写入失败时 SUCCESS 记录同步回滚的事务集成测试，并在 REST 异常收口时统一目标绑定冲突的异常类型。

## M2：统一节点推进器与任务创建（第三步）

- `DefinitionGraphIndex` 已从校验器包内实现公开为可复用只读图索引；它保留原有 `sortOrder`、`edgeCode` 的确定性排序和不可变节点/连线/邻接视图。运行时不再另写节点或出线解析器。
- 新增 `ConditionExpressionEvaluator` SPI，契约为 `evaluate(String expression, Map<String, Object> variables)`。B 线不解释或拼接表达式；表达式语言、沙箱和生产实现仍由 A 线提供。未配置 SPI、SPI 抛错或网关结构异常均以 `FLOW_GATEWAY_CONFIG_INVALID` 失败关闭。
- `RuntimeNodeAdvancer.advanceToNode(instance, definition, targetNodeCode, taskGroupId, branchKey)` 是后续启动、提交和审批服务共用的推进入口，返回 `RuntimeAdvanceResult`（本次创建的任务与办结标志）。它不接管历史归档、幂等结果或事务开启，后者保留给第四、五步的动作服务和事务执行器。
- `RuntimeAdvancePreparation` 是推进的前置只读阶段。它在任何运行时行变更、尤其是任务 CAS 前，遍历即将经过的自动节点，使用既有 `RuntimeRequestValidator.resolveApprovers` 与 `ApproverResolver` 解析并去重所有可达 `USER_TASK` 的候选人，M2 只接受 `SINGLE`。正式推进阶段只消费这份不可变准备结果，不会在 CAS 后调用外部审批人 SPI；并行路径的任务仍继承 `taskGroupId/branchKey`。变量和审批人规则配置均以 `RuntimeJsonCodec` 读取，脏 JSON 映射为冻结定义错误。
- `EXCLUSIVE_GATEWAY` 同样在准备阶段按共享图索引的稳定出线顺序计算非默认条件，选择首条命中；无命中时使用唯一默认线，仍无可用出线返回 `FLOW_GATEWAY_NO_MATCH`。选中的目标节点写入准备结果，正式推进直接复用，避免同一表达式在 CAS 前后重复求值。每条自动路径维护独立访问集，重复自动节点或超过“节点数 + 连线数 + 1”上限返回配置错误，防止自动循环。
- `PARALLEL_SPLIT_GATEWAY` 创建 `PARALLEL_GATEWAY` 任务组，将每条出线编码写为 `RUNNING` 分支后分别推进；M2 显式拒绝嵌套并行。`PARALLEL_JOIN_GATEWAY` 校验任务组实例、配对汇聚点和分支状态，复用已有 `markBranchArrived` 条件更新。是否沿汇聚出线继续只由 CAS 前 `completedCount + 1 == totalCount` 决定，非最后分支即使在重读前被其他分支完成任务组也不会重复推进。
- `END` 仅在没有活动任务和活动任务组时清空 `currentNodeCodes` 并办结。其他推进结束后统一从数据库当前的 `ACTIVE/CLAIMED` 任务重算节点集合，避免串行、条件和并行路径维护不同的内存状态。
- `RuntimeNodeAdvancerTest` 覆盖候选任务创建、稳定条件路由、默认线、无匹配、表达式失败/缺失、自动环路、并行拆分、嵌套拒绝、部分/最后分支汇聚、并发交错完成防重复推进和 `END` 办结门禁。`mvn -q test`（`platform`）通过；独立审查首先发现并行汇聚的“重读后误判最后分支”竞态，修复并补测试后复审无 P0/P1。

## M2：六个 Runtime Service 方法（第四步）

- `DefaultProcessRuntimeService` 是 `ProcessRuntimeService` 的首个 M2 Bean。它只编排既有 Repository、`RuntimeDefinitionLoader`、`RuntimeRequestValidator`、`RuntimeOperationExecutor` 与 `RuntimeNodeAdvancer`；不复制定义选版、图解析、CAS 或幂等逻辑。M3/M5 的接口继续抛出明确的阶段未实现异常。
- `startProcess` 校验可信发起人、加载可启动定义后只插入 `NOT_STARTED` 实例，`startedAt/currentNodeCodes/createdTasks` 均为空语义，不调用推进器或回调。`startAndSubmit` 先在内存中构造 `RUNNING` 实例、初始变量快照并完成起始路径准备，再插入实例并从唯一 `START` 出线推进；返回值来自推进后的持久化实例，并携带首批新任务。
- 两个启动方法使用同一种 `StartProcessRequest`，因此在 `RuntimeOperationTypes` 中固定不同的幂等记录动作：`START` 表示仅建实例，`START_AND_SUBMIT` 表示创建并推进。后者只存在于 `process_operation_record.action_type`，流程事件和历史任务仍使用 `ActionTypeEnum.START`，避免把 Service 入口差异污染业务动作语义。`UPDATE_VARIABLES` 同理仅表示变量更新的幂等记录动作。
- 任务动作先通过 `validateTaskIdentity` 校验操作号、任务版本和可信当前用户，再读取幂等决定；成功重放直接恢复 `TaskActionResult(replayed=true)`，不再读取已终态活动任务。首次执行才读取任务/实例、校验权限和冻结定义。这样同一请求在任务 CAS 成功后重试不会重复附件、历史、下一任务或回调。
- `submitTask` 限定 `STARTER` 用户任务。它按提交项构造正式 `SaveTaskAttachmentRequest` 调用附件服务，再调用 `CheckAttachmentRequest` 校验必传附件；二者都在 `ActiveTaskRepository.complete` 之前。随后基于合并后的内存变量完成后继路径准备（审批人 SPI 与条件选择均在此时发生），才执行任务 CAS；CAS 成功后写变量、归档 `SEND/NORMAL` 历史快照，并以准备结果推进。`approve` 限定非 `STARTER` 用户任务，不接受变量更新，同样在 CAS 前完成后继路径准备，归档为 `APPROVE/NORMAL` 后走同一推进路径。
- `updateVariables` 仅允许 `NOT_STARTED/RUNNING` 实例，合并已保存 JSON 对象与请求 Map，状态条件更新成功后保存可重放 DTO。`getInstance` 按冻结定义补齐活动任务节点名称，聚合 Repository 已稳定排序的活动任务/历史任务，并把非空历史意见投影为 `ProcessCommentDTO`，不新增重复意见表。
- 服务为启动、任务创建、任务提交/完成和流程办结组装 `WorkflowEvent`，事件 ID 为 `operationId:eventType:targetId`；实际 Outbox 写入仍委托 `CallbackService` 的 C 线实现。跨线协作收口后，五个修改型入口已建立 Spring 事务边界，使 CAS、变量、归档、推进、Outbox 和幂等成功结果原子提交。
- 新库由 `001_init_flow_platform.sql` 创建时已接受 `START_AND_SUBMIT`、`UPDATE_VARIABLES`。为保证已有 SQLite 库可升级，新增一次性 `002_m2_runtime_operation_actions.sql`：在事务中复制原 `process_operation_record` 的全部字段与数据、替换动作 CHECK 约束并恢复四个索引。`schema/sqlite/README.md` 固定其部署前手动执行要求，迁移回归验证已有 `APPROVE` 记录保留且两个 M2 动作可写。
- `DefaultProcessRuntimeServiceTest` 覆盖六个方法的主路径、附件保存/校验先于任务 CAS、变量浅合并、历史/详情聚合及提交/审批的终态成功重放无副作用；`FlowPlatformSchemaTest` 覆盖新动作和旧库迁移。独立子 agent 首轮发现启动入口串用重放和 SQLite 旧库 CHECK 约束两项 P1，修复并复审后无 P0/P1。

## M2：跨线运行时协作收口

`DefaultProcessRuntimeService` 的 Spring 主构造器额外注入 C 线的 `RuntimeStateValidator` 与 `HistoryTaskWriter`。任务动作先由状态校验器读取并核对实例、任务状态和乐观锁版本，随后仍保留 B 的 `RuntimeRequestValidator` 做可信身份、候选人/受理人权限及节点动作语义校验；两者职责不重叠，也不替代 Repository 的 CAS。

任务 CAS 成功后，历史快照统一交由 `HistoryTaskWriter` 按 `(active_task_id, action_type, operation_id)` 幂等归档，再由 B 的节点推进器创建后续任务或办结实例。回调继续通过 `CallbackService.publishCallback` 写入 C 的 Outbox；五个修改型公开入口会先建立/判断幂等租约，再委托独立 `RuntimeTransactionExecutor` 执行主事务，因此历史、Outbox 与运行时主状态及成功结果同事务提交。保留兼容构造器仅供既有直接构造测试使用，Spring 生产装配固定使用完整构造器。

附件配置组的公共原语采用定义范围校验：保存草稿前校验同批配置的组 ID 一致性；null 配置列表按空列表处理；激活时若 `definitionId + attachmentConfigId` 找不到任何记录即返回冻结校验错误。该修正不会改变无附件定义可激活、或定义激活时唯一 DRAFT 配置组切换为 ACTIVE 的既有业务规则。

## 2026-07-24：startAndSubmit 发起即提交实现说明

### 业务语义

依据导师确认，发起表单的字段值和附件在一次请求中一并提交；申请节点不应再暴露为需要调用方二次 `submitTask` 的待办。附件保存为实例级材料，供后续节点查看。

### 实现链路

`StartProcessRequest` 增加 `attachments`。`DefaultProcessRuntimeService.startAndSubmit` 在同一事务内依次执行：

1. 创建 `RUNNING` 实例并保存 `variables`；
2. 推进至唯一的 `STARTER` 申请任务；
3. 调用 `AttachmentService.saveInstanceAttachment` 保存请求附件，并调用 `checkRequiredAttachments` 校验申请节点；
4. 以任务版本完成申请任务，写入 `SEND/NORMAL` 历史快照；
5. 推进到申请节点的后继节点，保存幂等成功结果并写入流程启动、任务提交和后继任务创建事件。

附件校验、任务 CAS、历史归档、后继任务创建、Outbox 事件和幂等成功结果仍位于同一运行时事务边界；任一步失败会回滚数据库侧状态。该流程要求起始路径最终只创建一个 `STARTER` 用户任务；否则视为定义不满足“发起即提交”语义并拒绝执行。


## M3：实例管理与管理员命令

### 1. 命令边界

`DefaultProcessRuntimeService` 在既有 M2 运行时编排上增加 `terminate` 和 `deleteInstance`；`DefaultAdminProcessService` 实现 `AdminProcessService` 的写命令 `jumpToNode` 与 `forceComplete`。管理员查询接口不在 B 线重复实现，保持显式 UnsupportedOperationException，由 C 线的查询服务与查询适配层承担。

所有实例级命令先调用 `RuntimeRequestValidator.validateInstanceOperationIdentity` 校验操作号、实例 ID 与可信当前用户的一致性，再通过 `RuntimeOperationExecutor` 建立/重放幂等租约。M3 没有独立管理员授权 SPI，因此只提供防伪造身份校验；宿主系统应在进入平台前完成管理员角色、租户和数据范围授权。

### 2. 状态机和任务清理

- 终止：仅 `RUNNING -> TERMINATED`，同时清空当前节点并记录结束时间；所有 `ACTIVE/CLAIMED` 任务转为 `CANCELED`，活动任务组转为 `CANCELED`，任务以 `TERMINATE` 动作归档。
- 强制办结：仅 `RUNNING -> COMPLETED`，执行同一套待办清理，历史动作是 `FORCE_COMPLETE`。
- 跳转：允许 `RUNNING` 和 `TERMINATED` 实例；终止实例先原子恢复为 `RUNNING`，再取消旧待办、预演并推进目标节点。目标必须属于冻结定义，且不能是 `START` 或直接的并行汇聚网关；后者缺少合法 `taskGroupId/branchKey`，因此失败关闭。

`InstanceTaskCancellationService` 是终止、跳转和强制办结共用的协调器。它按稳定顺序读取开放任务和活动任务组，对每项执行带 `lockVersion` 的 CAS；成功的任务以完整实例、操作者、变量快照和操作号交给 `HistoryTaskWriter` 归档。任一 CAS 或归档失败均抛出运行时异常，由外层事务回滚。

### 3. 删除和可追溯性

`ProcessInstanceDeletionRepository` 负责数据库内的物理删除顺序：附件元数据、已读、提醒、告警、历史任务、活动任务和任务组先清理，再将审计/回调日志的 `instance_id` 置空并以 SQLite JSON 函数写入 `targetDeleted=1`、`deleteMode=HARD`，最后删除实例行。`process_operation_record` 不存在实例外键，刻意保留以支持重复删除请求的成功重放。

删除命令统一使用既有 `CANCEL` 操作记录及 `PROCESS_CANCELED` 事件，避免扩展既有 schema 的动作约束。外部存储对象并不在本阶段删除；本阶段只清理 `process_attachment` 元数据，实际文件清理由 M4 附件服务承担。

### 4. 审计、回调与一致性

每个 M3 命令会以实例为 `targetType` 写入审计日志，并将操作原因和被归档任务数量写入 detail JSON。回调事件携带操作者快照、变量快照、归档任务和新建任务；终止发出 `PROCESS_TERMINATED`，跳转发出 `PROCESS_JUMPED`，强制办结发出 `PROCESS_COMPLETED`，删除发出 `PROCESS_CANCELED`。审计、Outbox、运行状态和幂等成功结果都位于 `RuntimeTransactionExecutor` 的同一事务中。

### 5. 验证

- 新增 `DefaultAdminProcessServiceTest` 覆盖跳转、强制办结与禁止直跳并行汇聚。
- 扩展 `DefaultProcessRuntimeServiceTest` 覆盖终止、删除、审计/回调与幂等成功结果。
- 新增 `InstanceTaskCancellationServiceTest` 覆盖任务/任务组 CAS、取消归档和冲突失败。
- 新增 `ProcessInstanceDeletionRepositoryIntegrationTest` 以真实 SQLite schema 覆盖运行数据删除、日志标记与操作记录保留。
- 损坏的实例变量 JSON 会被转换为确定的 `RuntimeStateException`，从而冻结 M3 管理命令的幂等失败；兼容构造器缺少 M3 依赖时也在异常处理范围内冻结失败，避免遗留 `PROCESSING` 租约。
- 修复既有 M2 测试对 final `RuntimeAdvancePreparation` 的 mock 及并行汇聚测试缺失审批人桩数据；`mvn -q -pl platform-core -am test` 在 `platform` 目录通过。独立子 agent 审查无 P0/P1，以上两项 P2 建议均已纳入回归。

## M4：附件运行时管理

`DefaultAttachmentService` 是唯一运行期附件实现。它依赖既有实例、活动任务、附件配置/模板 Repository、`FileStorageProvider`、`CurrentUserProvider` 和 `AttachmentAccessGuard`；Controller 与 Starter 都只调用这一实现，不保留第二套附件业务逻辑。

保存实例附件必须提供创建该附件的 `sourceTaskId` 与读取到的 `expectedTaskVersion`。服务验证来源任务属于实例且仍为 `ACTIVE/CLAIMED`，并将任务 ID 写入附件元数据。任务附件使用自身 `taskId` 和版本走同一校验路径。因此删除也可基于该来源任务状态失败关闭，不会在任务推进后篡改历史材料。

上传顺序固定为：可信用户校验、宿主授权、实例冻结配置与模板校验、文件 SPI 保存、事务内元数据写入。授权拒绝、SPI 异常和身份不一致均在文件 SPI 调用之前失败。模板目前只定义扩展名和大小限制，故 M4 校验文件名扩展名、内容字节数和最大大小；`contentType` 仅保留元数据。

查询与下载使用 `VIEW`/`DOWNLOAD` 授权，软删除附件不可读。删除使用 `DELETE` 授权并软删除元数据；事务提交后调用文件 SPI 做最佳努力清理，失败不撤销删除。若外层 Runtime 事务回滚，已保存文件通过事务同步回调做最佳努力补偿。

Starter 在宿主未提供附件授权 SPI 时仍拒绝全部访问；独立应用显式提供仅用于本地联调的允许 Mock。新增附件 REST 适配实例上传、任务上传、列表查询、下载和删除，二进制内容沿用 JSON/Base64 请求模型。

## M4：附件运行时管理与验收补测

`DefaultAttachmentService` 是唯一的运行时附件实现，负责可信用户校验、失败关闭的附件授权、实例固化附件配置校验、文件保存、元数据写入、查询下载和逻辑删除。它只依赖 `AttachmentAccessGuard`；`AttachmentAccessProvider` 的生产实现或本地 Mock 由装配层提供，避免把环境策略写入领域服务。

## M5：增强任务动作实现

`DefaultProcessRuntimeService` 仍是唯一公开 `ProcessRuntimeService` Bean。新增的内部 `EnhancedTaskActionCoordinator` 只承载六项 M5 动作及加签临时任务的审批收口，避免增加同义 Service、DTO 或 Controller。协调器先校验可信操作人与请求幂等号，成功重放直接返回首次 `TaskActionResult`；首次执行在统一运行时事务中完成任务 CAS、历史归档、目标任务或临时组创建、回调和幂等成功记录。

- 驳回读取源节点 `listenerConfig.taskActionRules.reject`，只接受启用且目标节点在 `targetNodeCodes` 中的用户任务；历史 JSON 固化来源节点、来源任务和实际创建任务 ID。直送只允许消费该任务 ID 关联的驳回历史，并要求 `directSend.targetMode=REJECT_SOURCE`，因此不能用作任意节点跳转。
- 退回发起人从本实例实际 `SEND` 历史定位 `STARTER` 节点；撤回只接受单一串行下游待办，并要求操作人是上一条终态节点历史的实际办理人。两者都先预演目标节点审批人，再执行当前任务 CAS。
- 转办在 CAS 前通过 `OrganizationProvider.findUser` 固化目标用户快照，复用 `ActiveTaskRepository.transfer` 原子更新办理人和锁版本。历史扩展 JSON 同时保存原办理人和目标用户；响应的 `updatedTasks` 返回新版本任务。
- 加签取消来源任务并创建 `COUNTERSIGN` 临时任务组，`branch_state_json` 使用 `purpose=ADD_SIGN`、`schemaVersion=1` 和来源任务快照。每名加签人得到同节点独立待办；每次审批只增加组完成数，最后一人重新创建来源节点任务，不沿流程出线推进。

历史定位统一扩展 `ProcessHistoryTaskRepository`：按实例、动作集合以 `completed_at DESC, id DESC` 稳定排序，并提供扩展 JSON 更新原语。新增错误码区分驳回目标、撤回历史/权限、直送来源、目标用户、加签上下文与不支持的分组动作，避免将领域拒绝压缩为通用 `FLOW_INVALID_ACTION`。

增强动作统一通过 C 线 `AuditLogWriter` 写入 `process_audit_log`，不再直接借用定义仓储的审计 SQL。审计命令以 `TASK` 作为目标类型、原请求任务为目标 ID，明细保存 `schemaVersion`、意见和历史任务 ID，并在与任务状态、历史、Outbox 和幂等成功结果相同的运行时事务中提交。`TRANSFER`、`ADD_SIGN`、`CLAIM`、`UNCLAIM` 属于过程控制历史，已办查询和统计显式排除它们；直送反查只接受 `schemaVersion=1` 且实际创建任务 ID 命中的驳回来源。撤回不校验操作人是否有当前下游待办权限，而是根据上一条终态节点历史验证其为实际办理人。

Starter 基线修复新增独立 Knife4j/OpenAPI 自动配置，保留 `spring.factories` 的声明；附件服务仅在本地 Mock SPI 启用时由 Starter 创建，避免 Mock 被显式禁用后产生缺失 `FileStorageProvider` 的启动失败。验证命令为 `mvn -q -pl platform-starter -am test`（`platform` 目录）。

## M6：定义级会签技术实现

### 1. 任务创建与上下文模型

`RuntimeNodeAdvancer` 在用户任务持久化分支读取固化节点的 `multiInstanceMode`。`SINGLE` 和现有 `OR_SIGN` 路径保持不变；`COUNTERSIGN` 使用已预解析、去重并排序的审批人创建一条 `process_task_group` 和逐人活动任务。组固定使用 `COUNTERSIGN/ACTIVE`、`completedCount=0`、`lockVersion=0`，每条任务的候选人 JSON 只包含一名用户且办理人为空。

会签组是并行上下文内的一层运行时容器。进入会签时，原 `taskGroupId/branchKey` 写入会签组的 `parentGroupId/parentBranchKey`；活动任务的 `taskGroupId` 改为内层会签组 ID，同时保留外层 `branchKey`。这样查询和会签计数定位内层组，最终推进又能恢复外层并行分支并参与原汇聚。

### 2. 审批计数与唯一推进

`CountersignTaskCoordinator` 是包内运行时组件，不形成第二套公共 Service。`DefaultProcessRuntimeService.approve` 仍复用原有身份校验、幂等租约、事务、任务 CAS、历史归档、回调和成功结果；当节点为 `COUNTERSIGN` 且任务带组 ID 时，只把组上下文冻结和计数推进交给协调器。

协调器在任务 CAS 前验证实例、节点、任务和组的一致性，排除 `branch_state_json.purpose=ADD_SIGN` 的 M5 临时组，并预解析唯一出线及下游审批人。任务归档后调用既有 `TaskGroupRepository.incrementCompletedCount`：

- 成功 CAS 前的 `completedCount + 1 < totalCount` 时返回空推进结果，只归档本次审批；
- 成功 CAS 前的 `completedCount + 1 == totalCount` 时取得唯一推进权，使用组的父上下文调用 `RuntimeNodeAdvancer.advanceToNode`；
- CAS 冲突时重读活动组并最多重试三次；组已完成、已取消或重试耗尽时抛出 `FLOW_TASK_GROUP_CONCURRENT_MODIFIED`。

以上步骤位于 `RuntimeTransactionExecutor` 的同一事务内，因此任务状态、历史、组计数、实例节点、下游任务、Outbox 和幂等成功结果原子提交。相同 `operationId` 继续由既有运行时幂等框架重放首次 `TaskActionResult`。

### 3. 串行会签一票驳回

`EnhancedTaskActionCoordinator.reject` 继续使用源节点 `listenerConfig.taskActionRules.reject` 校验目标。若当前任务属于定义级会签组，则只接受没有父并行上下文的串行组；并行分支内会签返回 `FLOW_GROUPED_TASK_ACTION_NOT_SUPPORTED`。

写入前先预解析驳回目标。随后完成当前任务并以 `REJECT` 归档，通过任务组状态和版本 CAS 将组置为 `CANCELED`，再使用 `ActiveTaskRepository.findOpenByTaskGroupId` 按创建时间和 ID 稳定读取其余开放任务，逐条按自身版本取消并以 `CANCEL` 归档。任一任务 CAS 失败都会抛出并回滚整笔事务。最后沿目标节点重新推进；目标本身为会签节点时，统一推进器会创建一套新组。

结果中的 `archivedTasks` 包含驳回任务和本次取消的兄弟任务，`createdTasks` 包含目标推进实际创建的任务；事件继续使用 `PROCESS_REJECTED` 和逐任务 `TASK_CREATED`，审计记录关联本次全部历史 ID。

### 4. 兼容性与验证

本阶段没有修改 SQLite schema、公开 API、请求/结果 DTO、枚举或 REST 路由。加签临时组继续由 `EnhancedTaskActionCoordinator.approveAddSign` 收口，不进入定义级会签计数；其他分组动作门禁保持 M5 语义。

测试覆盖会签组与逐人任务创建、父并行上下文、一人会签、任务插入失败、部分审批、最终推进、版本冲突重试、重试耗尽、终态冲突、一票驳回整组取消、兄弟任务 CAS 冲突、并行驳回门禁、运行时审批分派和 SQLite 同组稳定查询。最终执行 `mvn -q clean test`（`platform`）通过：72 个测试套件、476 项测试，0 失败、0 错误、0 跳过。独立子 agent 审查未发现 P0/P1。
