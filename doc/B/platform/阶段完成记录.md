### M2.1 实现边界

- 定义选择仅用于新实例启动；已存在实例后续必须用冻结的 `definitionId` 加载，不能按 `processCode` 重新选版。
- 实例仓储只在 `NOT_STARTED/RUNNING` 状态下更新已序列化的变量或当前节点；变量浅合并属于后续 Runtime Service 的业务职责。
- 既有活动任务 `complete` 和任务组 `markBranchArrived` 的 CAS SQL 未修改；本次仅补齐插入、读取和统计原语。
- 历史任务为只增快照，要求非空 `operationId`，并继续依赖 `(active_task_id, action_type, operation_id)` 唯一约束防止重复归档。

### M2.2 实现边界

- `RuntimeDefinitionLoader` 将新启动和运行中实例拆为两条读侧：前者仅先按 `processCode` 选择唯一 `PUBLISHED + ACTIVE + OFF` 版本，再以 `definitionId` 命中或回填 `ProcessDefinitionCache`；后者只使用实例冻结的 `definitionId`，`processCode/version` 仅校验快照一致性。定义后续停用时，已有实例仍可从数据库读取并继续流转，但不会回填仅缓存激活定义的缓存。
- `RuntimeRequestValidator` 通过 `CurrentUserProvider` 固化可信发起人/操作人，统一校验幂等号、必填字段、实例与任务状态、候选人或受理人权限和 `expectedTaskVersion`。审批人 SPI 结果按用户 ID 去重且不得为空，M2 明确拒绝 `OR_SIGN` 与 `COUNTERSIGN`。
- `RuntimeRequestHasher` 对所有运行时请求反射生成带类型和长度的规范化内容，排除 `operationId`、稳定排序 Map，并将 `byte[]` 附件内容替换为 SHA-256 摘要；幂等记录不会保存原始文件字节。
- `RuntimeOperationExecutor` 复用既有幂等服务：唯一键竞争后重新读取、以条件更新原子接管过期租约、绑定实例/任务目标、反序列化成功重放结果并设置 `TaskActionResult.replayed=true`。成功标记由后续 Runtime Service 在同一业务事务内调用；确定性业务失败才冻结为 `FAILED`，不确定的数据库中断保留 `PROCESSING` 租约。

### M2.3 实现边界

- `RuntimeNodeAdvancer.advanceToNode` 是启动、提交和审批的唯一内部节点推进入口；它只编排运行时状态，不归档任务、不创建操作幂等记录，且由第五步的外层事务执行器负责原子提交。
- `DefinitionGraphIndex` 公开为只读共享索引，继续复用原有 `sortOrder/edgeCode` 稳定出线顺序和不可变集合；不复制第二套节点或连线解析逻辑。
- 新增 `ConditionExpressionEvaluator` 仅冻结 `evaluate(expression, variables)` SPI，不实现表达式语法。未配置、求值异常或网关拓扑非法统一失败关闭为 `FLOW_GATEWAY_CONFIG_INVALID`；无条件命中且无默认线为 `FLOW_GATEWAY_NO_MATCH`。
- `USER_TASK` 继续通过 `RuntimeRequestValidator.resolveApprovers` 调用既有 `ApproverResolver`，M2 仅创建一条 `SINGLE` 候选任务；并行分支任务携带任务组和出线分支键。
- 并行拆分以出线 `edgeCode` 初始化 `RUNNING` 分支，嵌套拆分明确拒绝。并行汇聚复用 `TaskGroupRepository.markBranchArrived` 的条件更新，并以 CAS 前的完成计数判定唯一最后分支，避免并发重读导致多条分支重复推进。
- 推进正常结束后从数据库活动任务重算 `currentNodeCodes`；`END` 在没有活动任务和任务组时先清空当前节点再办结实例。自动路径使用独立访问集合和上限防止无任务闭环。

### M2.4 实现边界

- `startProcess` 只固化 `NOT_STARTED` 实例和初始变量快照，不设置启动时间、不创建任务或回调；`startAndSubmit` 才创建 `RUNNING` 实例、从唯一开始节点出线调用 `RuntimeNodeAdvancer`，并返回首批任务或直接办结结果。
- 两个启动入口共享 `StartProcessRequest`，但幂等记录分别使用 `START` 与仅用于 `process_operation_record` 的 `START_AND_SUBMIT`；同一操作号跨入口会被识别为冲突，不会错误回放另一种启动语义。`UPDATE_VARIABLES` 同样是仅用于幂等记录的内部动作名，历史任务和回调继续使用正式 `ActionTypeEnum`。
- `submitTask` 只办理 `STARTER` 节点，逐项调用现有 `AttachmentService.saveTaskAttachment` 后调用 `checkRequiredAttachments`，两者均发生在活动任务 CAS 之前；随后浅合并变量、归档为 `SEND/NORMAL` 并调用统一推进器。`approve` 仅办理非 `STARTER` 用户任务，不写变量，归档为 `APPROVE/NORMAL`。
- 任务动作先完成操作人身份与请求字段校验，再读取幂等决定；成功重放在读取活动任务、附件调用、CAS、历史写入和回调之前直接返回，因而不依赖原任务仍处于活动态。
- `updateVariables` 只允许 `NOT_STARTED/RUNNING` 实例，按键浅合并并保存可重放实例快照，不创建、完成或归档任务。`getInstance` 基于冻结定义聚合稳定排序的活动任务、历史任务，并从非空历史意见映射 `comments`。
- 回调仅通过既有 `CallbackService` 发布流程启动、任务创建、提交/完成和流程办结事件；事件 ID 固定为 `operationId:eventType:targetId`。本步不实现 Outbox，事务原子性仍由第五步收口。
- 新库初始化脚本已允许 `START_AND_SUBMIT`、`UPDATE_VARIABLES`；已有 SQLite 库在部署 M2 前必须手动执行 `002_m2_runtime_operation_actions.sql`，该脚本重建并复制 `process_operation_record` 及索引。未实现的 M3/M5 动作继续明确抛出阶段未实现异常。
