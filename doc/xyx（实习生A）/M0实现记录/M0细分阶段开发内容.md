# 实习生 A：M0 契约冻结 Vibe Coding 计划

版本：v1.0  
阶段：M0 契约冻结  
参考文档：《流程平台技术路线 v5.2》《流程平台设计与接口文档 v4》  
技术基线：Java 8、Spring Boot 2.7.18、Spring JDBC、SQLite

## 产物与边界

M0 的目标不是完成流程定义 CRUD 或运行时流转，而是冻结后续 M1-M6 共同依赖的数据与并发契约。实习生 A 的主责是数据模型、流程状态和乐观锁设计，并把设计落成可编译、可建库、可执行条件更新、可自动验收的工程基线。

A 的工作需要同时满足三类下游依赖：

- 向 B 线提供状态枚举、持久化字段、任务版本字段、合法状态迁移和乐观锁条件更新规则；
- 向 C 线提供 `operation_id` 关联、回调 `event_id` 唯一性以及事务和并发不变量；
- 为 M1 的流程定义开发提供最小定义模型，为 M2 的运行时开发提供实例、任务、任务组和历史模型。

M0 结束后，表名和字段名、枚举值、状态迁移、唯一约束、乐观锁条件均视为冻结契约。变更必须由 A、B、C 三方评审。

A 主责内容：

- 17 张 SQLite 业务表的字段、类型、默认值、检查约束、外键和索引；
- 定义、实例、任务、任务组和操作记录的状态模型；
- 活动任务和任务组的 `lock_version` 设计及条件更新 Repository；
- 数据库表对应的持久化实体；
- 定义、实例、任务、任务组和操作状态校验器；
- Schema、状态、乐观锁和并发不变量测试；
- M0 三方评审材料和冻结清单。

M0 不包含：

- 流程定义 CRUD、发布、激活、停用、归档和灰度发布业务逻辑；
- 实例启动、审批推进、历史归档和完整幂等处理器；
- 条件表达式执行、会签、或签、并行汇聚的完整运行时引擎；
- 附件文件读写、外部 SPI 实现、Starter 自动装配和 REST Controller；
- Oracle 或国产数据库适配，以及复杂数据库迁移框架。

## 并行与等待

A、B、C 可并行推进，但以下契约需要合并前强制对齐：

| 依赖方 | 必须对齐内容 | A 的处理 |
|---|---|---|
| B | `operationId`、`expectedTaskVersion`、`TaskDTO.taskVersion`、运行时动作结果和并发错误码 | A 提供数据库字段、版本字段、状态边界和并发错误码语义，B 不重复定义持久化或运行时逻辑 |
| C | 历史、审计、回调的 `operation_id`，回调 `event_id` 唯一规则，并发、幂等、回滚验收断言 | A 提供可表达这些用例的模型、约束和事务不变量，C 不重复定义表结构 |

推荐执行顺序：

```text
M0.0 基线核对
  -> M0.1 SQLite Schema
  -> M0.2 持久化实体
  -> M0.3 乐观锁 Repository
  -> M0.4 状态与模型校验器
  -> M0.5 三方联调冻结
```

M0.1 评审通过后，B、C 即可并行使用字段和版本契约；M0.3-M0.4 用于证明冻结设计可以真正执行，而不是只停留在文档层面。

## 微任务与编码提示词

### M0.0 基线核对与冻结台账

开发内容：

1. 对照设计文档逐表核对 17 张业务表，建立“表名-字段-约束-索引-责任人”台账。
2. 对照接口文档核对所有状态修改请求必须包含 `operationId`，任务级修改还必须包含 `expectedTaskVersion`。
3. 确认查询侧 `TaskDTO.taskVersion` 映射 `process_active_task.lock_version`。
4. 记录 A 与 B、C 的输入输出边界、待确认项和契约变更流程。
5. 确认工程基线仅使用 Java 8、Spring Boot 2.7.18、Spring JDBC 和 SQLite。

产出：

- M0 契约清单；
- 表与接口字段映射表；
- 三方评审问题清单。

完成标准：

- 17 张表、核心状态和冻结接口均有唯一来源；
- 不存在同一概念在文档、DDL、Java 类中使用不同名称的情况；
- B、C 已确认 A 提供的字段和状态边界。

### M0.1 SQLite Schema 与约束实现

开发内容：

1. 编写 SQLite 初始化脚本，一次创建以下 17 张表：
   - 定义侧：`process_definition`、`process_node`、`process_edge`、`process_form_field`、`process_attachment_template`、`process_definition_attachment_config`；
   - 运行侧：`process_instance`、`process_active_task`、`process_task_group`、`process_history_task`、`process_read_record`、`process_attachment`、`process_audit_log`、`process_callback_log`、`process_reminder_record`、`process_alert_record`、`process_operation_record`。
2. 使用 `CREATE TABLE/INDEX IF NOT EXISTS`，并启用 `PRAGMA foreign_keys = ON`。
3. 按设计文档实现字段类型：JSON 使用 `TEXT`，布尔值使用 `INTEGER 0/1`，时间采用统一文本格式。
4. 实现关键唯一约束：
   - `process_code + version`；
   - 定义内节点编码、连线编码和表单字段编码；
   - `attachment_code + template_version`；
   - 历史任务 `active_task_id + action_type + operation_id`；
   - `process_operation_record.operation_id`；
   - `process_callback_log.event_id`。
5. 实现关键检查约束：状态取值、灰度规则、附件数量、非负计数、`lock_version >= 0`。
6. 为定义查询、待办查询、实例查询、历史、附件、审计、回调、提醒、告警和幂等记录建立访问路径索引。
7. 审查外键删除策略；操作记录的实例和任务字段保持逻辑关联，避免删除后破坏幂等重试。

产出：

- `001_init_flow_platform.sql`；
- Schema 字段、约束和索引说明；
- 内存 SQLite 初始化测试。

完成标准：

- 空数据库可重复执行初始化脚本并创建 17 张表；
- 外键、唯一约束和代表性 `CHECK` 约束实际生效；
- DDL 不引入设计文档之外的唯一业务语义。

### M0.2 持久化实体与字段映射

开发内容：

1. 为 17 张表建立持久化实体，放入 `com.flowmind.platform.persistence.entity`。
2. 实体字段与 SQLite 列一一映射，统一下划线列名与 camelCase 属性名。
3. 数据承载类使用 Lombok `@Data`，只承载数据，不包含状态迁移、并发判断和数据库操作。
4. 为每个类和字段补充中文 Javadoc，状态字段列出典型取值，JSON 字段说明内容结构。
5. 统一 ID、版本、计数、布尔和时间字段的 Java 类型，避免 DTO、实体与 SQL 参数类型不一致。
6. 明确 DTO 与实体的边界：DTO 面向 API，实体面向持久化，不直接复用 DTO 作为数据库实体。

产出：

- 17 张表对应的持久化实体；
- 字段映射核对表；
- 实体结构测试或反射校验测试。

完成标准：

- 每个 DDL 字段都有明确的实体映射；
- 实体无业务逻辑；
- 实体、状态值和数据库取值不存在命名冲突。

### M0.3 乐观锁 Repository

开发内容：

1. 为活动任务提供条件更新方法，至少覆盖完成、取消、认领、取消认领和转办所需的原子更新能力。
2. 活动任务条件必须包含 `id + 允许的当前状态 + lock_version`，成功后 `lock_version + 1`，方法返回受影响行数。
3. 为任务组提供条件更新方法，条件包含 `id + group_status=ACTIVE + lock_version`。
4. 为会签和并行汇聚提供原子计数更新能力，确保 `completed_count < total_count`。
5. 为并行分支到达提供 `branch_key` 去重所需的读取与条件更新接口。
6. 明确冲突处理契约：任务冲突返回 `FLOW_TASK_CONCURRENT_MODIFIED`，任务组超过有限重试返回 `FLOW_TASK_GROUP_CONCURRENT_MODIFIED`。
7. Repository 只提供持久化原语，不在 M0 实现完整审批推进、历史归档、回调发送或重试编排。

产出：

- 活动任务 Repository；
- 任务组 Repository；
- 条件更新 SQL 与返回值约定；
- Repository 集成测试。

完成标准：

- 两个请求使用同一任务版本更新时只有一个受影响行数为 1；
- 过期版本、非法状态或终态任务更新返回 0；
- 任务组计数不超过 `total_count`；
- Repository 不采用“先查后无条件写”。

### M0.4 状态与模型校验器

开发内容：

1. 实现流程定义状态组合校验器。
2. 实现流程实例状态迁移校验器。
3. 实现活动任务状态迁移校验器。
4. 实现任务组状态、计数和分支到达校验器。
5. 实现操作记录状态迁移校验器。
6. 实现定义模型结构校验的最小能力：
   - 必须有且仅有一个开始节点；
   - 至少一个结束节点；
   - 节点和连线引用合法；
   - 用户任务具有审批人规则；
   - 条件网关最多一个默认出线；
   - 并行分支与汇聚网关正确配对。
7. 校验器只表达冻结规则，不在 M0 执行完整流程发布或运行时推进。

产出：

- 定义、实例、任务、任务组和操作状态校验器；
- 合法与非法用例参数化测试。

完成标准：

- 每条状态迁移规则至少有一个正向和一个反向测试；
- 非法网关配对、孤立节点和用户任务无审批人能够被拒绝；
- 校验错误使用冻结错误码，不以通用运行时异常替代业务错误。

### M0.5 三方联调与契约冻结

开发内容：

1. 与 B 线核对：
   - 请求 `operationId` 与操作记录字段；
   - `expectedTaskVersion` 与 `lock_version`；
   - `TaskDTO.taskVersion` 的查询映射；
   - 动作结果和并发错误码。
2. 与 C 线核对：
   - 历史、审计、回调的 `operation_id`；
   - 回调 `event_id` 唯一和稳定生成规则；
   - 并发、幂等、回滚验收断言。
3. 运行模块测试和仓库根目录测试，清理契约差异。
4. 形成冻结版本和变更规则；冻结后修改字段、状态、迁移或锁条件必须提交三方评审。

产出：

- 三方评审记录；
- M0 冻结版 DDL、实体、Repository、校验器和测试；
- M0 验收报告及遗留项清单。

完成标准：

- B、C 的代码可基于 A 的契约编译和编写测试；
- `mvn -q -pl platform/platform-core -am test` 通过；
- Maven 结构或公共契约有变更时，仓库根目录 `mvn -q test` 通过；
- 不存在未确认的表字段、状态、错误码或版本字段。

## 验收与合并门禁

M0 总体验收清单：

- [ ] 17 张 SQLite 表可创建且初始化脚本可重复执行；
- [ ] 状态值与设计文档一致；
- [ ] 节点、连线可表达条件网关和并行分支/汇聚；
- [ ] 活动任务含 `task_group_id`、`branch_key`、`lock_version`；
- [ ] 任务组含嵌套并行、分支状态、计数和乐观锁字段；
- [ ] 历史、审计、回调可关联 `operation_id`;
- [ ] 操作记录包含请求哈希、处理租约、结果、错误快照和保留期限；
- [ ] 回调 `event_id` 唯一；
- [ ] 非法定义状态组合和非法状态迁移被拒绝；
- [ ] 同版本并发修改活动任务时仅一个请求成功；
- [ ] 会签、或签和并行汇聚所需的任务组原子更新能力可用；
- [ ] 同一 `branch_key` 不会重复增加汇聚计数；
- [ ] 乐观锁失败不会留下部分业务数据；
- [ ] 条件网关、并行网关、孤立节点和用户任务审批人规则通过模型校验覆盖；
- [ ] A、B、C 已完成字段、状态、接口和测试基线评审；
- [ ] 模块测试及必要的仓库级测试通过。

最终交付物：

1. M0 三方评审冻结文档；
2. SQLite 表、约束和索引初始化脚本；
3. 17 张表的持久化实体；
4. 活动任务与任务组乐观锁 Repository；
5. 定义、实例、任务、任务组和操作状态校验器；
6. Schema、非法状态、任务并发、任务组并发和事务回滚测试。
