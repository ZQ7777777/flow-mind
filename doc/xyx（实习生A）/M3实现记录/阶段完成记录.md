## 4. 当前可验收能力

- 草稿定义通过 `publish` 发布前会执行完整流程模型校验。
- 校验通过后定义状态变为 `PUBLISHED + INACTIVE + OFF`。
- 已发布未激活定义可以通过 `activate` 激活为 `PUBLISHED + ACTIVE + OFF`。
- 激活新版本时，会停用同流程编码下其他 `PUBLISHED + ACTIVE + OFF` 全量版本。
- 数据库唯一索引保证同一 `processCode` 最终不会存在多个全量激活版本。
- 已激活定义可以通过 `deactivate` 停用。
- 停用后该定义不再作为新实例启动的全量激活版本。
- 已发布未激活定义可以通过 `archive` 归档。
- 归档定义状态为 `ARCHIVED + INACTIVE + OFF`，不能再次激活。
- 发布、激活、停用、归档均要求 `operationId`。
- 相同 `operationId` 和相同请求成功重放返回首次结果。
- 相同 `operationId` 但不同动作或请求摘要由幂等服务拒绝。
- 生命周期操作成功后写入定义审计日志。
- 生命周期操作成功后失效对应定义的流程图缓存；激活时同时失效旧全量版本缓存。
- 灰度接口不会误返回成功，当前固定抛出未实现异常。

## 7. 并发说明

当前并发能力满足 M3 基础验收口径：

- 幂等唯一键处理相同 `operationId` 重试。
- 状态条件更新处理同一定义的重复状态流转。
- SQLite 部分唯一索引处理同流程编码全量激活唯一性。

当前没有定义级 `lock_version`。不同 `operationId` 并发激活同一流程编码下不同版本时，最终状态只有一个全量 active，但不保证先执行的激活请求保持 active。后续如需要强串行化版本治理，应增加定义级乐观锁或流程编码级锁。

## 9. 后续建议

1. C 线在 starter 自动装配中复用 A 线的 `DefaultProcessDefinitionService` 和 Repository，不重复实现生命周期逻辑。
2. B 线运行时启动流程继续按 `PUBLISHED + ACTIVE + OFF` 选择全量定义；已有实例按固化 `definitionId` 加载。
3. 灰度实现应单独补充规则 JSON 校验、灰度命中选择、关闭灰度、审计和测试，不应直接复用 `activateFull` 作为灰度启用。
4. 若版本治理需要更强并发语义，应在后续阶段正式引入定义级 `lock_version` 或流程编码级互斥锁。
