技术基线：Java 8、Spring Boot 2.7.18、Spring JDBC、SQLite

## 1. 实现边界

本阶段在 `platform-core` 内补齐组织架构 SPI 和审批人解析 SPI 的非 Mock 能力。平台只定义和消费公共 SPI，不接入真实组织架构系统，不新增生产级本地组织 Mock，也不引入网络调用。

已实现：

- `OrganizationProvider` 组织架构查询契约。
- `ApproverResolver` 审批人解析契约。
- `ApproverResolveRequest` 承载定义、实例、节点、审批规则、多人模式、发起人和变量上下文。
- `UserDTO` 补充部门、角色和有效状态公共字段。
- `DefaultApproverResolver` 基于 `OrganizationProvider` 解析六类审批规则。
- 审批人结果按用户 ID 去重并稳定排序。
- 审批人解析失败统一映射为 `FLOW_APPROVER_RESOLVE_FAILED`。
- 运行时任务创建前通过 `ApproverResolveRequestFactory` 和 `ApproverResolver` 解析候选人。
- `OR_SIGN`、`COUNTERSIGN` 不再被审批人解析入口提前拒绝。

未实现：

- 生产级本地组织 Mock。
- 真实组织架构系统接入。
- 网络调用、缓存组织数据或多数据源适配。
- 完整或签/会签任务组运行闭环；本阶段只保证审批人解析结果可保留并传递。

## 3. SPI 契约

`OrganizationProvider` 提供以下组织查询能力：

| 方法 | 作用 |
| --- | --- |
| `listDepartments` | 查询部门列表 |
| `listUsersByDepartment` | 查询部门有效用户 |
| `listUsersByRole` | 查询角色有效用户 |
| `listUsersByRoleAndDepartment` | 查询角色与部门交集用户 |
| `findUser` | 按用户 ID 查询单个用户 |
| `findDepartment` | 按部门 ID 查询单个部门 |

`ApproverResolver` 提供统一入口：

```java
List<UserDTO> resolveApprovers(ApproverResolveRequest request);
```

调用方只依赖公共 API 类型，不暴露 persistence 包类型。

## 4. 请求与用户 DTO

`ApproverResolveRequest` 当前承载：

- `definitionId`
- `instanceId`
- `nodeCode`
- `nodeName`
- `approverRuleType`
- `approverRuleConfig`
- `multiInstanceMode`
- `starterUserId`
- `starterDeptId`
- `variables`

其中 `multiInstanceMode` 由 `ApproverResolveRequestFactory` 从节点配置读取并写入请求，典型值为 `SINGLE`、`OR_SIGN`、`COUNTERSIGN`。

`UserDTO` 当前承载：

- `userId`
- `userName`
- `departmentId`
- `departmentName`
- `roleCodes`
- `active`

`active = false` 的用户不会作为有效审批人返回；`active = null` 表示宿主系统未提供有效状态，当前按有效处理。

## 5. 审批规则解析

`DefaultApproverResolver` 支持六类规则：

| 规则 | 配置 | 解析方式 |
| --- | --- | --- |
| `USER` | `{"userIds":["u1","u2"]}` | 逐个调用 `findUser` 查询用户 |
| `STARTER` | `{}` | 使用 `starterUserId` 查询用户 |
| `DEPARTMENT` | `{"departmentId":"d1"}` | 调用 `listUsersByDepartment` |
| `ROLE` | `{"roleCode":"finance"}` | 调用 `listUsersByRole` |
| `ROLE_IN_DEPARTMENT` | `{"roleCode":"manager","departmentId":"d1"}` | 调用 `listUsersByRoleAndDepartment` |
| `APPROVER_EXPRESSION` | `{"expression":"departmentManager(starterDeptId)"}` | 解析受限表达式后继续调用组织 SPI |

`ROLE_IN_DEPARTMENT` 未显式配置 `departmentId` 时，使用请求中的 `starterDeptId`。

## 6. 受限表达式

`APPROVER_EXPRESSION` 不执行脚本、反射、类加载、系统属性、文件或网络访问，只支持白名单函数和白名单上下文字段。

当前支持的表达式函数：

| 函数 | 示例 | 说明 |
| --- | --- | --- |
| `departmentManager` | `departmentManager(starterDeptId)` | 使用内置角色编码 `manager` 查询指定部门经理 |
| `roleInDepartment` | `roleInDepartment("finance", starterDeptId)` | 查询指定角色和部门交集用户 |
| `role` | `role("finance")` | 查询指定角色用户 |
| `department` | `department(starterDeptId)` | 查询指定部门用户 |
| `user` | `user(starterUserId)` | 查询指定用户 |

当前允许的参数来源：

- 字符串字面量，如 `"finance"`；
- `starterUserId`；
- `starterDeptId`；
- `variables.xxx`，其中 `xxx` 必须是简单标识符。

访问未授权上下文、表达式语法非法、参数为空、组织数据为空时，均返回 `FLOW_APPROVER_RESOLVE_FAILED`。

## 7. 结果规范

审批人解析结果在返回前会统一处理：

1. 忽略 `null` 用户。
2. 忽略 `userId` 为空白的用户。
3. 忽略 `active = false` 的用户。
4. 按 `userId` 去重。
5. 按 `userId` 稳定排序。
6. 保留 `UserDTO` 中的用户名称、部门、角色和有效状态字段。
7. 结果为空时抛出 `RuntimeStateException`，错误码为 `FLOW_APPROVER_RESOLVE_FAILED`。

该处理同时存在于 `DefaultApproverResolver` 和 `RuntimeRequestValidator.resolveApprovers`，保证外部自定义 `ApproverResolver` 返回的数据也会被运行时二次规整。

## 8. 运行时接入

运行时进入用户任务节点前，由 `RuntimeNodeAdvancer` 调用：

1. `ApproverResolveRequestFactory.create(...)` 从实例固化的定义快照和节点配置构造请求。
2. `ApproverResolver.resolveApprovers(request)` 解析审批人。
3. `RuntimeRequestValidator.resolveApprovers(...)` 规整结果并校验非空。
4. 将候选人 ID 写入 `process_active_task.candidate_user_ids`。

`RuntimeRequestValidator` 不再拒绝 `OR_SIGN`、`COUNTERSIGN`，因此多人审批模式的候选人列表可以完整传递给后续任务组运行逻辑。

## 9. 错误处理

当前错误处理原则：

- 请求缺少解析器或请求对象：`FLOW_APPROVER_RESOLVE_FAILED`。
- 解析器抛出运行时异常：运行时统一包装为 `FLOW_APPROVER_RESOLVE_FAILED`。
- 结果为空：`FLOW_APPROVER_RESOLVE_FAILED`。
- 表达式非法或访问未授权上下文：`FLOW_APPROVER_RESOLVE_FAILED`。
- 节点配置 JSON 非法或必填配置缺失：保持节点配置错误，由配置读取阶段抛出。

## 14. Starter 与独立运行接线补充（2026-07-27）

`DefaultProcessRuntimeService` 保持只依赖 `RuntimeNodeAdvancer` 的职责边界；进入用户任务时由推进器构造解析请求并调用 `ApproverResolver`。本次在装配层补上默认实现：

```text
宿主 OrganizationProvider
        │
        ▼
PlatformAutoConfiguration.approverResolver(...)
        │
        ▼
DefaultApproverResolver
        │
        ▼
RuntimeNodeAdvancer → DefaultProcessRuntimeService
```

自动装配条件为：容器存在 `OrganizationProvider`，且不存在宿主自定义的 `ApproverResolver`。这使宿主只实现组织架构 SPI 即可使用 A 线六类审批规则；如宿主提供自定义解析器，则继续完全接管解析逻辑。

独立运行环境注册最小 `StandaloneOrganizationProvider`，并以其构造同一个 `DefaultApproverResolver`。该实现只返回已知的本地部门、角色和用户；对未知部门、角色、用户或不匹配的角色-部门组合严格返回空值/空集合，遵守公共 SPI 契约并使运行时失败关闭。

新增验证覆盖：

- 独立运行解析器确为 `DefaultApproverResolver`，并可解析配置用户；
- 未知部门和角色不会产生候选人；
- Starter 默认解析器实际调用宿主 `OrganizationProvider`；
- 宿主自定义 `ApproverResolver` 会覆盖自动装配默认值。

定向 Maven 回归已通过：`platform-core` 25 项、`platform-starter` 13 项。完整核心套件执行时仍存在 3 项与本次 SPI 接线无关的基线失败：附件模板版本计数、旧迁移脚本缺表、前端静态页断言。
