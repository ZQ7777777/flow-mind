# 基于对话方式实现的业务办理全流程自动化构建平台需求文档

## 1. 项目概述

### 1.1 项目名称

基于对话方式实现的业务办理全流程自动化构建平台（以下简称"平台"或"newoa"）。

### 1.2 文档目标

本文档用于指导实习生重新实现 `newoa`。系统由**三块**独立产物组成：流程平台、Agent、业务流程代码。本文档按这三块划分需求，明确：

- 每块产物是什么、边界在哪、彼此如何衔接。
- 各自要做什么、包含哪些核心能力。
- 数据归属和调用关系，避免三块互相侵入。
- 哪些能力属于本期必须实现，哪些能力明确不在本期范围。

本文档只描述功能需求，不限定接口形式，不展开字段级接口协议，也不包含 `flow-ui` 前端设计器实现细节。

### 1.3 三块架构总览（核心）

系统由三块产物组成，**Agent 是主线**，流程平台是底座，业务流程代码是 Agent 的产物。

```
        用户（业务人员）
             │ 自然语言对话
             ▼
   ┌─────────────────────────┐
   │  ② Agent（生产者）        │
   │  理解需求 → 调平台建流程   │
   │  定义 → 生成业务代码       │
   └──────────┬──────┬───────┘
              │      │ 生成真实代码文件
   调 Starter │      ▼
   建流程定义 │   ┌──────────────────────────┐
              │   │  ③ 业务流程代码（产物）     │
              │   │  后端：Spring Boot 适配层  │
              │   │  前端：Vue3 页面           │
              │   │  不建业务表，数据走流程变量 │
              │   └──────────┬───────────────┘
              │              │ 依赖 Starter（同进程）
              ▼              ▼
   ┌──────────────────────────────┐
   │  ① 流程平台（引擎底座）         │
   │  流程定义/实例/任务/SPI/回调/附件│
   │  与具体业务无关，只管流转        │
   └──────────────────────────────┘
```

**主线链路**（用户视角）：

1. **对话表达**：用户以自然语言描述业务办理场景（如"我要做一个入金申请流程"）。
2. **Agent 理解**：Agent 通过多轮对话理解需求，沉淀为结构化配置，并允许用户确认修正。
3. **Agent 调平台**：Agent 调用流程平台能力，创建流程定义（含节点、连线、表单字段、附件模板）。
4. **Agent 生成代码**：Agent 生成 ③ 业务流程代码——一套真实可编译运行的 Spring Boot 后端 + Vue3 前端文件，落到代码仓库。
5. **业务运行**：业务人员使用 ③ 的页面发起流程、审批人处理待办，③ 的后端通过 Starter 调 ① 平台完成流转；业务数据作为流程变量存在平台，不另建业务表。

### 1.4 项目目标

让业务人员通过自然语言对话，即可从零得到一套**可独立运行的业务办理流程**（页面 + 后端 + 审批流转），而无需开发人员手写业务代码。

实习生按"先 ① 后 ② 再 ③"的顺序交付：先把流程平台做通，再用平台能力做 Agent，最后由 Agent 生产出第一个真实业务流程代码。

| 附件模板 | 流程定义阶段预配置的材料清单，用于约束流程实例中应上传的附件类型、数量及规则。 |
| Mock | 本地开发环境中模拟外部依赖的能力。 |

## 3. 范围边界

### 3.1 本期包含

**① 流程平台**：

- 流程引擎的设计与实现，覆盖流程定义、流程实例、任务流转、历史轨迹等核心能力。
- 完整的审批流转能力，包括串行、并行、会签、或签、条件分支、驳回、撤回、加签、转办、委托代办、任意节点跳转等。
- 查询与流程跟踪能力，包括待办、办结、我发起的、已阅、提醒、审批意见等。
- 组织架构与审批人解析 SPI，引擎不直接管理真实组织数据。
- 回调、监听与外部事件集成。
- 流程定义级附件模板配置及流程实例/任务级附件上传、查询、下载、删除能力。
- 以 Spring Boot Starter 形式对外提供能力（业务适配层依赖此 Starter 同进程调用）。
- 管理与运维能力，包括异常流程修复、管理员查询、审计日志、超时监控、多数据库适配等。

**② Agent**：

- 对话沟通能力：支持自然语言及多轮对话采集业务需求。
- 需求解析能力：将自然语言需求转换为结构化配置。
- 流程定义创建能力：调用流程平台创建流程定义（节点、连线、表单字段、附件模板）。
- 业务代码生成能力：生成真实可运行的 Spring Boot 后端 + Vue3 前端代码文件。
- 人工确认与修正能力：解析与生成结果在确认前不进入运行阶段。

**③ 业务流程代码（产物规范）**：

- 明确产物清单、文件结构、与平台的集成约定。
- 后端为业务适配层，不建实体表，业务数据走流程变量。
- 前端为 Vue3 业务页面（录入页、待办、审批）。

### 3.2 本期不包含

- 前端设计器（`flow-ui`）的详细需求。
- 固化接口报文格式或完全复刻旧 RPC 协议。
- 生产级消息队列、分布式事务、容器化部署方案。
- 历史字段的全部兼容映射（保留核心语义即可）。
- Agent 自动化测试、自动修复生成代码等高级能力（本期 Agent 生成后由人工确认）。

## 4. 总体架构与核心数据模型

### 4.1 三块职责切分

- **① 流程平台**负责：流程定义管理、流程实例运行、任务调度、历史轨迹、表单模型、附件元数据、回调触发。**不包含任何具体业务逻辑，不感知"入金""报销"等业务概念**。
- **② Agent**负责：理解业务需求、把需求转成流程平台可消费的结构化配置、调用平台落地、生成业务流程代码。Agent 是开发期工具，产物落库落仓后，Agent 本身不参与业务运行期（运行期由 ③ 调 ①）。
- **③ 业务流程代码**负责：面向最终业务用户的前端页面和后端适配层。**③ 内部分两层**：一层是**基础底座**（通用前端 + 通用业务后端，业务无关，只开发一次，提供待办/我发起的/审批框架等通用能力）；另一层是**业务产物**（Agent 按具体业务生成的前端页面和后端接口）。后端通过 Starter 调用平台能力，前端通过通用业务后端间接调平台；**不维护业务实体表，业务表单值作为流程变量存在 ① 平台**。
- **宿主系统**负责：提供组织架构、用户、角色、部门、委托关系、消息推送、文件存储等基础数据和能力，通过 SPI 暴露给 ① 平台。

### 4.2 调用与部署关系

- **③ 业务代码 → ① 平台**：③ 后端依赖 ① 提供的 Spring Boot Starter，同进程直接调用 Service 层，不走 HTTP。这是本期**唯一**的业务调平台方式。
- **② Agent → ① 平台**：Agent 在开发期调用平台能力创建流程定义。可走 Starter，也可走平台管理 API，由实现选择，但必须能落地为平台中持久化的流程定义。
- **① 平台 → 宿主系统**：通过 SPI 调用组织、审批人解析、委托、消息、文件存储等能力。
- **① 平台 → ③/宿主**：通过回调机制通知流程状态变更。

平台自身仍需支持三种运行形态：Starter 嵌入（供 ③ 使用）、独立服务（平台自身开发联调）、本地演示应用（端到端验证）。业务代码只用 Starter 这一种。

### 4.3 数据归属（重要边界）

| 数据 | 归属 | 说明 |
|------|------|------|
| 流程定义、节点、连线、表单字段配置、附件模板 | ① 平台 | Agent 写入，平台持久化。 |
| 流程实例、活动任务、历史任务、审批意见、已阅 | ① 平台 | 业务运行期由 ③ 通过 Starter 创建和流转。 |
| **业务表单值（入金金额、入金账号、申请人姓名等）** | **① 平台流程变量** | **③ 业务代码不建实体表**，表单值作为流程变量存在流程实例上，由平台统一存取。 |
| 附件元数据 | ① 平台 | 附件文件内容通过 SPI 委托宿主/Mock 存储。 |
| 组织架构、用户、角色、部门、委托关系 | 宿主系统 | 平台不维护，通过 SPI 查询。 |
| 业务校验规则、业务聚合查询逻辑 | ③ 业务代码 | ③ 后端可包含业务校验，但校验对象仍是平台中的流程变量。 |

> 边界一句话：**③ 业务代码不拥有数据，只拥有业务语义和业务校验；所有流程相关数据都在 ① 平台**。

### 4.4 核心数据模型

| 领域对象 | 主要职责 | 所属 |
|----------|----------|------|
| 流程定义 | 维护流程编码、名称、版本、发布状态、激活状态、节点与连线结构。 | ① 平台 |
| 节点定义 | 维护节点编码、名称、类型、坐标、审批人规则、多人处理模式、监听配置。 | ① 平台 |

| 流程实例 | 维护标题、业务编码、流程编码、当前节点、发起人、**变量数据（含业务表单值）**、业务状态。 | ① 平台 |

## 5. 端到端示例：入金申请（贯穿三块）

本示例展示主线链路如何贯穿三块，实习生验收时以此为基准场景。

### 5.1 用户与 Agent 对话（②）

用户："我要做一个入金申请流程。"
Agent："请描述该流程的办理目标和参与角色。"
用户："业务员提交入金申请，部门经理审批，财务确认后完成。"
Agent："请补充需要收集的字段和材料。"
用户："需要申请人姓名、入金金额、入金账号、附件上传银行回单。"
Agent：（识别到信息完整，输出结构化预览，请求用户确认）

### 5.2 Agent 解析与确认（②）

Agent 输出结构化解析结果：

- 业务名称：入金申请
- 业务编码：`entry_application`
- 办理目标：完成资金入账申请及审批
- 参与角色：业务员、部门经理、财务
- 审批层级：业务员 → 部门经理 → 财务
- 表单字段：申请人姓名（文本/必填）、入金金额（数字/必填）、入金账号（文本/必填）
- 附件模板：银行回单（必填，适用申请节点，允许格式 pdf/jpg/png，大小限制 10MB）
- 流程结构：开始 → 申请节点 → 部门经理审批 → 财务确认 → 结束

用户确认后，Agent 进入下一步。

### 5.3 Agent 调用平台 + 生成业务代码（② → ① + ③）

- Agent 调用 ① 平台：创建流程定义 `entry_application`，写入节点、连线、表单字段、附件模板；执行发布前校验、发布、激活。
- Agent 生成 ③ 业务代码（真实文件落仓）：
  - 后端（Spring Boot）：`EntryApplicationController`（暴露 `POST /api/entry-application/submit` 等业务接口）、`EntryApplicationService`（封装 Starter 调用：启动流程实例，把申请人姓名/入金金额/入金账号作为流程变量传入）。
  - 前端（Vue3）：`EntryApplicationApply.vue`（录入页，含三个字段 + 银行回单上传控件），构建时打包进基础底座通用前端。
  - 待办、我发起的、审批框架等通用页面直接复用基础底座，不由 Agent 生成。

### 5.4 业务运行（③ → ①）

- 业务员在前端录入页填写并提交 → ③ 后端调 Starter 启动流程实例，流程变量含表单值 → 申请节点要求上传银行回单（按附件模板校验）。
- 部门经理在待办中看到任务，查看表单值与附件，审批通过 → 推进到财务确认。
- 财务确认 → 流程结束，实例办结，历史轨迹完整保留。
- 全程业务数据存在 ① 平台的流程变量中，③ 后端不建任何实体表。

## 6. 功能需求 —— ② Agent（主线）

> Agent 是三块中的主线产物。它面向业务人员，通过对话理解需求，调用流程平台创建流程定义，并生成可运行的业务流程代码。Agent 主要在**开发期**工作，产物（流程定义 + 业务代码）落库落仓后，运行期由 ③ 调 ①。
>
> **Agent 形态**：Agent 是一个 **Web 应用**，业务人员在浏览器中完成对话、查看解析预览、确认与修正、查看生成代码并落仓。Agent 后端集成 LLM 能力完成自然语言理解与代码生成，前端提供对话界面和产物预览。LLM 选型不在本文档范围，由实现方自行决定。

### 6.1 对话沟通

- 当用户通过自然语言描述业务办理场景时，Agent 应记录并理解用户输入。
- 当关键信息缺失时（业务名称、办理目标、参与角色、审批层级、表单字段、材料清单、办理规则），Agent 应通过多轮追问补齐，而不是直接生成不完整流程。
- Agent 应识别并整理业务名称、办理目标、参与角色、审批层级、表单字段、材料清单、办理规则等信息。
- Agent 应将对话过程沉淀为结构化需求结果，供后续解析与生成使用。
- 当信息不完整时，Agent 应主动提示缺失项。

验收要点：
- 能基于多轮对话采集"入金申请"所需业务信息。
- 在信息缺失时能主动追问，不直接生成结果。
- 最终输出为结构化需求，而非原始聊天记录。

### 6.2 需求解析

- 当 Agent 接收到业务描述时，应对其进行语义解析，提取流程定义所需的核心要素。
- Agent 应将自然语言需求转换为结构化配置，包括：业务编码、业务名称、表单字段（含控件类型与校验）、附件材料与附件模板、审批节点、审批人规则、流转条件、多人处理模式、办理角色等。
- 解析结果应可被人工确认和修正，避免一次解析错误直接进入运行阶段。
- 解析结果应同时满足两个下游消费方：① 流程平台（建流程定义）和 ③ 代码生成器（生成业务代码），字段配置需覆盖两者需要。

验收要点：
- 能将自然语言需求解析为包含表单、附件模板、节点、连线、审批人规则的结构化配置。
- 解析结果在确认前不进入运行阶段。
- 解析结果同时能驱动平台建流程定义和代码生成器生成代码。

### 6.3 调用流程平台创建流程定义

- 用户确认解析结果后，Agent 应调用 ① 流程平台能力，落地流程定义：
  - 创建流程定义，写入基础信息（编码、名称、所属系统、版本）。
  - 写入节点与连线结构（开始、用户任务、结束、网关）。
  - 配置节点审批人规则与多人处理模式。
  - 写入流程定义级表单字段配置。
  - 写入流程定义级附件模板。
  - 执行发布前校验，校验通过后发布并激活。
- Agent 应将平台返回的流程定义标识回写记录，便于追溯"哪个流程定义由哪次对话生成"。
- 流程定义创建失败时（校验不通过、冲突等），Agent 应将错误反馈给用户并支持修正后重试。

验收要点：
- 确认后的解析结果能成功落地为平台中已发布激活的流程定义。
- 流程定义包含节点、连线、表单字段、附件模板。
- 创建失败时有清晰反馈和重试路径。

### 6.4 生成业务流程代码（③ 的生产者）

- 用户确认后，Agent 应生成一套真实可编译运行的业务流程代码文件，落到代码仓库指定目录。
- **代码生成方式为 LLM 直接生成**（非模板填充）：Agent 将解析后的结构化配置连同代码栈约定（Spring Boot + Vue3、平台 Starter 用法、不建实体表等约束）作为上下文交给 LLM，由 LLM 直接产出源代码文件。因此必须配合强约束的上下文描述和严格的人工确认。
- **后端代码（Spring Boot）**：
  - 生成业务 Controller，对前端暴露业务语义的 REST 接口（如发起、查询详情、审批动作、查询待办）。
  - 生成业务 Service，封装 ① 平台 Starter 调用：启动流程实例时把表单字段值作为流程变量传入、查询/审批时转调平台能力。
  - 生成相关配置（依赖平台 Starter 的引入）。
  - **不生成实体表、Mapper、业务库建表语句**——业务数据走流程变量。
- **前端代码（Vue3）**：
  - 生成业务录入页，根据表单字段配置渲染对应控件，按附件模板渲染上传控件。
  - 作为路由模块，构建时打包进基础底座通用前端。
  - 前端只调用 ③ 业务后端的业务 REST 接口，不直接调平台。
  - **不重复生成待办、我发起的、已办、审批框架等通用页面**——这些由基础底座提供。
- 生成代码应满足：经人工确认修正后开箱即能启动、能与已落地的流程定义端到端跑通入金申请场景。
- 生成结果应允许人工确认和修正后才落仓。

验收要点：
- 能生成包含后端 Controller/Service/配置和前端 Vue3 页面的完整代码文件。
- 生成的后端不建实体表，业务数据通过流程变量存取。
- 生成的前端录入页字段与流程定义表单字段一致。
- 生成的代码经人工确认后能端到端跑通发起 → 审批 → 办结。

### 6.5 人工确认与修正

- 解析结果、流程定义创建结果、生成代码均应支持人工确认和修正。
- 确认前，流程定义不进入激活状态，生成代码不落仓。
- 由于代码由 LLM 直接生成，质量存在不确定性，**生成代码的确认环节尤其关键**：Agent 应在前端提供生成代码的预览，并支持用户直接编辑修正后再落仓。
- 修正后可重新走解析 → 创建 → 生成流程。

验收要点：
- 关键产物在人工确认前不产生不可逆影响。
- 生成代码可在前端预览并编辑后才落仓。
- 修正后能重新生成。

### 6.6 Agent 自身管理与运维

- Agent 应记录每次对话、解析、创建、生成的过程，便于追溯。
- Agent 应支持查询"由 Agent 创建的流程定义"和"由 Agent 生成的业务代码"清单。
- Agent 调用平台失败、代码生成失败时应有清晰错误反馈。

## 7. 功能需求 —— ① 流程平台（底座）

> 流程平台是三块中的底座。它不感知任何具体业务，只提供流程定义、实例、任务、查询、SPI、回调、附件等通用能力，通过 Spring Boot Starter 暴露给 ③ 业务代码同进程调用，并供 ② Agent 在开发期创建流程定义。

### 7.1 流程定义与设计管理

- 系统应支持创建流程定义，维护流程编码、流程名称、版本号、所属系统、发布状态、激活状态等基础信息。
- 系统应支持复制流程定义，生成新的流程编码和名称，并复制原有节点与连线配置。
- 系统应支持删除流程定义，并级联删除该定义下的节点、连线、实例、任务、历史任务等运行数据。
- 系统应支持查询流程定义列表，按流程编码、名称、系统归属、发布状态等维度筛选。
- 系统应支持保存流程图结构，至少包含节点、连线、节点坐标、节点顺序等设计数据。
- 系统应支持基础节点类型：开始节点、用户任务节点、结束节点、网关节点。
- 系统应支持流程发布前校验，至少校验开始/结束节点是否存在、节点是否孤立、连线是否完整、用户节点是否配置审批人。
- 系统应支持流程发布与激活，只有已发布且激活的定义才能被运行时使用。
- 系统应支持查询流程下的节点信息，供运行时、调试和管理使用。
- 系统应支持节点审批人规则配置，至少包括指定用户、发起人、部门、角色、表达式等类型。
- 系统应支持节点多人处理模式配置，包括或签、会签等能力。
- 系统应支持节点监听配置，用于节点创建和完成时触发事件。
- 系统应支持连线条件表达式配置，用于条件分支判断。
- 系统应支持流程定义级表单字段/控件配置，供业务适配层按流程动态渲染表单。
- 系统应支持流程定义级附件模板配置，约束流程实例中应上传的附件类型、数量、大小限制、适用节点及是否必填。
- 系统应支持同一流程编码下的多版本共存、灰度发布、版本归档等治理能力。

验收要点：
- 能创建、复制、删除、查询流程定义。
- 能保存包含节点、连线、坐标的流程图结构。
- 发布前校验能拦截明显错误的流程定义。
- 只有已发布激活的流程定义才能被发起。
- 能配置审批人规则、多人处理模式、监听、连线条件、表单字段、附件模板。

### 7.2 流程实例管理

- 系统应支持启动流程，根据流程定义创建流程实例。
- 系统应支持启动并自动发送，即发起后直接将流程推进到第一个用户任务节点。
- 系统应支持保存实例的标题、业务编码、流程编码、当前节点、发起人、变量数据（含业务表单值）、业务状态等运行信息。
- 系统应支持获取流程表单数据和流程实例详情。
- 系统应支持更新流程表单数据，允许业务适配层在流程运行中更新变量内容。
- 系统应支持删除流程实例及其关联任务、历史任务、已阅等运行数据。
- 系统应支持终止流程，将流程强制办结并清理活动任务。
- 系统应支持流程在终止后通过管理员操作恢复流转，例如配合"任意节点跳转"重新拉起流程。
- 系统应支持流程状态在"未流转、流转中、已结束、已归档、强制办结"等阶段之间正确切换。

验收要点：
- 能根据流程定义创建实例，并自动推进到首个用户任务。
- 能查询实例详情和表单数据，能更新表单变量。
- 能删除和终止实例，终止后活动任务被清理。
- 流程状态切换符合预期。

### 7.3 任务流转与审批动作

- 系统应支持正常发送/审批通过，即当前任务归档后按流程连线创建下一节点任务。
- 系统应支持串行审批闭环，能从开始节点逐步流转到结束节点。
- 系统应支持流程到达结束节点后自动结束，实例状态更新为办结状态。
- 系统应支持活动任务归档到历史任务，保留节点、办理人、流转动作、审批时间等基本轨迹。
- 系统应支持驳回到指定节点。
- 系统应支持一键退回发起人或退回首节点。
- 系统应支持撤回或回收已发送任务，将流程从当前节点恢复到上一个历史节点。
- 系统应支持直送，即从被打回后的起点重新跳回原打回来源节点。
- 系统应支持任意节点跳转，用于管理员修复异常流程或执行特殊运维操作。
- 系统应支持并行网关分支，允许一个节点同时流向多个后续节点。
- 系统应支持并行汇聚，多个分支全部满足后再继续后续流转。
- 系统应支持或签，即多个候选人中任一人办理即可推动流程。
- 系统应支持会签，即多个审批人全部办理完成后流程才可继续。
- 系统应支持条件分支，根据流程变量判断后续走向。
- 系统应支持加签，在当前节点临时增加审批人。
- 系统应支持转办，将当前任务交给其他人处理。
- 系统应支持委托代办，通过宿主系统提供的委托关系，让代理人代为处理委托人的任务。
- 系统应支持多人任务认领和取消认领。
- 系统应支持边界事件、超时自动处理、自动催办、自动跳转、自动终止等高级流转能力。

验收要点：
- 串行流程能从开始节点完整流转到结束节点。
- 审批通过、驳回、撤回、直送、跳转动作能正确更新活动任务和历史任务。
- 并行网关和汇聚能正确处理分支同步。
- 或签、会签、条件分支、加签、转办、委托代办、认领/取消认领均能正常运行。
- 超时自动处理、自动催办、自动跳转、自动终止能按配置触发。

### 7.4 查询与流程跟踪

- 系统应支持查询某个流程实例当前的活动任务。
- 系统应支持查询用户待办列表。
- 系统应支持查询用户办结列表。
- 系统应支持查询用户发起的流程列表。
- 系统应支持查询流程的完整任务轨迹，包括历史任务和当前任务。
- 系统应支持按流程编号、流程名称、标题、发起人、时间范围等条件过滤查询结果。
- 系统应支持分页查询能力，避免列表接口默认返回无限数据。
- 系统应支持查询已阅列表。
- 系统应支持查询提醒列表。
- 系统应支持查询流程审批意见列表。
- 系统应支持待办列表区分"自己的任务"和"委托代办任务"。
- 系统应支持在查询结果中返回当前节点、审批人、认领人、办理时间、委托来源等业务关键信息。
- 系统应支持更完整的审计追溯视图，用于管理员排查流程异常。

验收要点：
- 能查询活动任务、待办、办结、我发起的、已阅、提醒、审批意见等列表。
- 查询支持过滤和分页。
- 待办列表能区分本人任务与委托代办任务。
- 流程轨迹完整，包含关键业务信息。

### 7.5 审批辅助与业务扩展能力

- 系统应支持保存审批意见。
- 系统应支持在任务归档时将审批意见同步沉淀到历史任务中，避免流程轨迹缺失意见内容。
- 系统应支持查询某个流程的审批意见记录。
- 系统应支持已阅标记，记录某个用户已查看某个流程。
- 系统应支持查询已阅用户或已阅记录。
- 系统应支持流程定义字段或控件配置的新增、查询、删除。
- 系统应支持在运行时保存审批人姓名、部门、委托来源等快照信息，保证历史数据可追溯。
- 系统应支持对认领、转办、加签等特殊动作保留必要的审计标记。

验收要点：
- 审批意见能被保存并随任务归档沉淀到历史。
- 已阅标记和查询功能正常。
- 流程字段/控件配置可维护。
- 任务和历史任务中保留审批人快照及特殊动作标记。

### 7.6 组织架构与审批人解析

- 系统应通过 SPI 与宿主系统的组织架构集成，引擎本身不直接管理真实组织数据。
- 系统应提供组织树所需的部门、角色、用户查询能力，供流程配置和调试使用。
- 系统应支持按部门解析审批人。
- 系统应支持按角色加部门解析审批人。
- 系统应支持按表达式和流程变量动态解析审批人。
- 系统应支持"发起人"作为审批人来源。
- 系统应支持精确查询某个用户在某个部门下的信息，用于补齐任务和历史任务中的用户名称、部门名称等字段。
- 系统应支持根据部门名称解析部门编码等辅助能力。
- 系统应支持宿主系统提供委托关系查询，用于代办场景。
- 系统应支持将审批人快照写入活动任务与历史任务，避免历史查询时再依赖外部组织数据补数。

验收要点：
- 引擎通过 SPI 获取组织数据，不直接维护真实组织架构。
- 能按部门、角色+部门、表达式、发起人等方式解析审批人。
- 委托关系可通过 SPI 查询并用于代办场景。
- 审批人快照被正确写入任务和历史任务。

### 7.7 回调、监听与外部事件集成

- 系统应在发起、发送、驳回、撤回、退回、直送、转办、跳转、终止、取消等动作后触发流程状态变更回调，通知宿主系统或业务适配层。
- 系统应在流程级回调事件中携带本次归档任务和新建任务信息。
- 系统应支持节点级生命周期事件，至少包括节点任务创建时触发和节点任务完成时触发。
- 系统应将节点事件配置为流程定义数据的一部分，由流程定义决定是否启用。
- 系统应以异步方式触发回调和监听事件，回调异常不能阻断主流程。
- 系统应允许宿主系统自行决定回调的落地方式，例如 HTTP、消息队列、日志等。
- 系统应支持更丰富的事件类型和更完善的重试、告警、失败治理机制。

验收要点：
- 关键动作后能触发回调并携带必要信息。
- 节点创建和完成事件可按流程定义配置触发。
- 回调异常不影响主流程运行。
- 支持重试、告警、失败治理。

### 7.8 宿主系统集成与兼容能力

- 系统应支持以 Spring Boot Starter 形式嵌入宿主业务系统或 ③ 业务代码（本期业务调平台的唯一方式）。
- 系统应支持以独立后端服务方式运行，便于平台自身本地开发和验证。
- 系统应提供本地演示应用，便于验证流程定义、流程发起、流程流转和回调联调。
- 系统应支持宿主系统通过 SPI 提供组织架构、审批人解析、委托关系、消息推送、文件存储等外部能力。
- 系统应保留老系统中的核心业务语义，例如发起、发送、驳回、撤回、直送、认领、已阅、意见、跳转等动作。
- 系统应支持关键业务对象和查询结果的兼容映射，避免重做后在业务层出现大量字段语义偏差。
- 系统应支持本地开发环境下的 Mock 能力，至少覆盖认证、组织架构、业务配置、客户信息、消息推送、文件存储等外部依赖。

验收要点：
- 能以 Starter 嵌入业务代码，也能独立部署。
- 本地演示应用可完成端到端验证。
- SPI 覆盖组织、审批人、委托、消息推送、文件存储。
- 保留老系统核心语义，关键对象字段映射无明显偏差。
- 提供本地 Mock 能力。

### 7.9 管理与运维能力

- 系统应支持管理员对异常流程执行人工修复动作，例如任意节点跳转、强制办结等。
- 系统应支持管理员查询流程定义、实例、任务、历史任务等核心运行数据。
- 系统应记录全量审计日志，记录关键管理动作和流程变更轨迹。
- 系统应支持流程版本治理，包括发布、停用、归档、灰度等管理动作。
- 系统应支持任务超时监控、催办策略和异常告警。
- 系统应支持多数据库适配，至少考虑 SQLite、Oracle 及国产数据库的兼容性。

验收要点：
- 管理员能执行跳转、强制办结等修复动作。
- 能查询流程定义、实例、任务、历史任务等核心数据。
- 审计日志覆盖关键管理动作。
- 版本治理、超时监控、催办、告警功能可用。
- 至少能在 SQLite 上完整运行，Oracle 和国产数据库在设计上保留兼容性。

### 7.10 附件管理

- 系统应支持流程定义级附件模板配置，包括附件编码、名称、说明、必填标识、允许格式、大小限制、适用节点、数量限制。
- 系统应在流程实例发起时，根据流程定义的附件模板校验必填附件是否已上传。
- 系统应支持流程实例级附件上传，附件归属整个流程实例，所有当前及后续节点审批人均可查看。
- 系统应支持任务级附件上传，附件绑定到具体任务节点，用于补充当前办理节点的审批材料。
- 系统应保存附件元数据（附件编码、名称、类型、大小、存储路径、上传人、上传时间、流程实例ID、任务ID、字段编码），不直接保存文件内容。
- 系统应通过 SPI 将文件内容存储委托给宿主系统，支持本地文件系统、对象存储等实现；本地开发环境提供 Mock 存储实现。
- 系统应支持按流程实例、任务、字段编码查询附件列表。
- 系统应支持下载附件，下载时校验当前用户是否有查看权限。
- 系统应支持删除未进入下一节点的附件，删除后保留元数据并标记删除状态，不影响流程历史轨迹。
- 系统应支持在流程轨迹中记录附件上传、删除等操作的关键审计信息。

验收要点：
- 能在流程定义中配置附件模板，并在发起时校验必填附件。
- 能在"入金申请"发起时上传银行回单等实例级附件。
- 审批人能查看流程实例关联的附件。
- 任务办理时能上传任务级附件。
- 附件元数据与文件存储解耦，可通过 SPI 替换存储方式。
- 附件删除后不影响流程实例和历史轨迹记录。

## 8. 功能需求 —— ③ 业务流程代码（产物规范）

> 业务流程代码是 Agent 的产物，面向最终业务用户。每个具体业务（入金申请、费用报销等）对应一套业务产物。**③ 内部分两层**：基础底座（开发一次、永远复用）和业务产物（按业务生成）。本节定义两层各自的规范，约束 Agent 必须生成什么、不能生成什么，以及基础底座必须提供什么。

### 8.0 两层结构（核心）

```
③ 业务流程代码
├── 基础底座（只开发一次，所有业务共用）
│   ├── 通用前端（Vue3）：待办、我发起的、已办、已阅、审批详情框架
│   │   （流程图、意见区、附件区、流转记录）
│   └── 通用业务后端：给通用前端供数的 REST 接口，转调平台 Starter
└── 业务产物（Agent 按业务生成）
    ├── 业务前端：具体业务录入页（如入金申请录入页）
    └── 业务后端：具体业务语义接口，转调平台 Starter
```

**关键约定**：

- **通用能力只开发一次**。待办、我发起的、已办、已阅、审批详情框架等业务无关的页面，由基础底座提供，**Agent 不得为每个业务重复生成**。
- **业务页面只做业务特定的部分**（主要是录入页），其余复用基础底座。
- **业务页面通过构建时打包集成进通用前端**：Agent 生成的业务页面作为路由模块，与基础底座一起重新构建，形成完整的业务前端。不做运行时动态加载。
- **前端一律不直接调平台**：通用前端走通用业务后端，业务前端走业务后端，两者再各自调平台 Starter。

### 8.1 基础底座产物清单（只开发一次）

- **通用前端（Vue3）**：
  - 待办列表页：展示当前用户待办，区分本人任务与委托代办任务。
  - 我发起的列表页：展示当前用户发起的流程。
  - 已办列表页：展示当前用户已处理的流程。
  - 已阅列表页：展示当前用户已阅的流程。
  - 审批详情框架页：通用骨架，包含流程图、审批意见区、附件区、流转记录区；具体业务的录入表单作为可嵌入区域，由业务页面填充。
- **通用业务后端（Spring Boot）**：
  - 待办、我发起的、已办、已阅、审批意见、流程轨迹、附件等查询接口，转调平台 Starter，按通用前端需要封装返回。

验收要点：
- 基础底座只开发一次，所有业务共用同一套待办/我发起的/审批框架页面。
- 通用前端不直接调平台，统一走通用业务后端。
- 审批详情框架能嵌入不同业务的录入表单。

### 8.2 业务产物清单（Agent 按业务生成）

每个业务产物应包含：

- **业务前端（Vue3）**：
  - 业务录入页：按表单字段配置渲染业务字段控件，按附件模板渲染上传控件。
  - 作为路由模块，构建时打包进基础底座通用前端。
  - **不重复生成待办、我发起的、审批框架等通用页面**——复用基础底座。
- **业务后端（Spring Boot 业务适配层）**：
  - 业务 Controller：暴露业务语义 REST 接口。
  - 业务 Service：封装平台 Starter 调用，处理业务校验与聚合。
  - 启动配置与依赖声明（引入平台 Starter、通用业务后端依赖）。

### 8.3 后端代码规范（业务适配层）

- 后端定位为**业务适配层（BFF）**，职责是把平台能力包装成业务语义接口。
- **禁止生成实体表、Mapper、业务库建表语句、业务数据库迁移脚本**。业务表单值（入金金额等）一律作为流程变量通过平台存取。
- 业务 Controller 应提供至少以下业务接口（以入金申请为例）：
  - 发起：`POST /api/entry-application/submit`，接收表单值，调用平台 Starter 启动流程实例并把表单值写入流程变量。
  - 查询详情：`GET /api/entry-application/{instanceId}`，从平台读取流程变量返回业务视图。
  - 审批动作：`POST /api/entry-application/{taskId}/approve` 等，转调平台审批能力。
  - （待办/已办/我发起的等通用查询走基础底座的通用业务后端，业务层不必重复实现。）
- Service 层通过 `@Autowired` 平台 Starter 暴露的 Service 进行调用，同进程，不走 HTTP。
- 业务校验（如金额上限、账号格式）可在 Service 层实现，校验对象为流程变量值。
- 后端可订阅平台回调，做业务侧联动（可选）。

验收要点：
- 后端不包含任何实体表或建表逻辑。
- 所有业务数据通过流程变量存取。
- Controller 接口语义清晰，内部正确转调平台 Starter。
- 通用查询接口不重复实现，复用基础底座。

### 8.4 前端代码规范（Vue3）

- 业务前端只调用对应业务后端的业务 REST 接口，不直接调用平台。
- 业务录入页根据流程定义的表单字段配置渲染对应控件，根据附件模板渲染上传控件。
- **待办、我发起的、已办、审批框架等通用页面直接复用基础底座，Agent 不为业务重新生成**。
- 业务前端字段与流程定义表单字段保持一致。
- 业务前端作为路由模块，构建时打包进基础底座通用前端。

验收要点：
- 录入页字段与流程定义一致。
- 业务前端不重复生成通用页面。
- 业务前端不直接调平台。
- 业务前端构建打包后，与基础底座通用前端形成完整业务前端。

### 8.5 与平台的集成约定

- ③ 后端（含通用业务后端和业务适配层）通过平台 Starter 同进程调用，不部署为独立服务。
- ③ 不维护组织、用户、委托等数据，全部通过平台 SPI 间接获取。
- ③ 不自行实现流程流转逻辑（审批通过、驳回、会签等），一律转调平台。

## 9. 非功能需求

### 9.1 性能

- 普通流程实例启动、任务处理等核心操作响应时间应满足常规业务系统要求。
- 待办、办结、我发起的等列表查询应支持分页，避免单次返回大量数据。
- 回调事件应采用异步方式触发，避免阻塞主流程。
- Agent 代码生成应在可接受时间内完成单业务产物。

### 9.2 兼容性

- 平台应能在本地以 Spring Boot 服务方式运行，并以 Starter 形态被业务代码嵌入。
- 数据库访问层应考虑多数据库兼容，至少支持 SQLite，并为 Oracle 及国产数据库预留适配空间。
- 关键业务对象字段语义应尽量与老系统保持一致，减少业务层迁移成本。
- Agent 生成的代码技术栈固定为 Spring Boot + Vue3。

### 9.3 可扩展性

- 审批人解析、组织架构查询、委托关系、消息推送、文件存储等能力应通过 SPI 开放给宿主系统实现。
- 节点监听、回调机制应支持扩展新的事件类型。
- 流程定义的表单字段配置应支持扩展新的控件类型。
- Agent 代码生成应通过上下文约束（代码栈约定、平台 Starter 用法、不建实体表等）保证 LLM 输出稳定可控，并支持扩展新的控件类型和页面模式。

### 9.4 安全性

- 流程操作应基于当前用户身份进行权限校验（由宿主系统或本地 Mock 提供）。
- 审批人、发起人、部门等敏感信息在快照中应准确记录，便于审计追溯。
- Agent 生成代码落仓前应经人工确认。

### 9.5 可观测性

- 关键管理动作和流程状态变更应记录审计日志。
- 回调失败、超时等异常应提供告警或重试机制。
- 管理员应能查询流程运行数据和历史轨迹，用于问题排查。
- Agent 应记录对话、解析、创建、生成全过程。

## 10. 接口与集成边界

### 10.1 SPI 能力清单

| SPI 能力 | 用途 |
|----------|------|
| 组织架构查询 | 获取部门、角色、用户树，供流程配置和审批人解析使用。 |
| 审批人解析 | 根据部门、角色、表达式、流程变量等解析具体办理人。 |
| 委托关系查询 | 查询用户的委托代理人，用于代办场景。 |
| 消息推送 | 用于待办提醒、催办、异常告警等通知。 |
| 文件存储 | 用于附件文件内容的上传、下载、删除，引擎只保存附件元数据。 |

### 10.2 回调事件清单

流程状态变更回调应至少覆盖以下动作：发起、发送、驳回、撤回、退回、直送、转办、跳转、终止、取消。

节点级生命周期事件应至少覆盖：节点任务创建、节点任务完成。

### 10.3 Mock 能力

本地开发环境应提供以下 Mock 能力：

- 认证 Mock：模拟当前登录用户。
- 组织架构 Mock：模拟部门、角色、用户数据。
- 业务配置 Mock：模拟业务编码、流程编码等配置。
- 客户信息 Mock：模拟业务场景所需的客户数据。
- 消息推送 Mock：模拟回调和消息通知。
- 文件存储 Mock：模拟附件上传、下载、删除的存储能力。

## 11. 验收标准

### 11.1 Agent 验收（主线）

- 能通过对话方式采集"入金申请"场景所需业务信息，信息缺失时主动追问。
- 能将需求解析为结构化结果（含表单字段、附件模板、节点、连线、审批人规则）。
- 解析结果经人工确认后，能调用平台创建已发布激活的流程定义。
- 能通过 LLM 直接生成一套真实代码文件：后端 Spring Boot 业务适配层 + 前端 Vue3 页面。
- 生成的后端不含实体表/建表逻辑，业务数据走流程变量。
- 生成的前端录入页字段与流程定义一致。
- 业务人员能在 Web 界面完成对话、查看解析预览、查看生成代码并编辑、确认后落仓。
- 解析与生成结果在人工确认前不进入运行阶段、不落仓。

### 11.2 流程平台验收

- 能创建一个包含开始、申请、审批、结束的流程定义。
- 流程定义可以完成校验、发布、激活。
- 用户可以发起流程并生成首个活动任务。
- 审批人可以处理待办并推动流程流转到下一节点。
- 流程结束后可以查到完整历史轨迹。
- 可以查询待办、办结、我发起的流程三类基础列表。
- 至少具备终止流程和删除流程两项基础管理能力。
- 能支持驳回、撤回、加签、转办、委托代办等动作。
- 能支持并行、会签、或签、条件分支等场景。
- 能支持任意节点跳转和强制办结等运维操作。
- 关键动作后能触发回调并携带归档/新建任务信息。
- 能以 Starter 形态被业务代码嵌入，也能独立运行。
- 至少能在 SQLite 上完整运行，数据库层为 Oracle 及国产数据库预留兼容空间。

### 11.3 业务产物验收

- 基础底座（通用前端 + 通用业务后端）开发一次后，所有业务共用同一套待办/我发起的/审批框架页面。
- Agent 生成的入金申请业务代码能独立编译启动。
- 业务后端通过 Starter 调平台完成发起、查询、审批，不建实体表；通用查询复用基础底座，不重复实现。
- 业务前端录入页能填写并提交，附件能按模板上传，构建时打包进通用前端。
- 能端到端跑通：业务员在通用前端发起入金申请 → 经理在通用待办审批 → 财务确认 → 办结，历史轨迹完整。

### 11.4 端到端验收

以入金申请为例，从用户与 Agent 对话开始，到最终业务人员使用生成的前端页面完成一次完整审批办结，全链路打通且数据存于平台流程变量，视为整体验收通过。

## 13. 风险与外部依赖

### 13.1 风险

- **LLM 解析准确性**：自然语言到结构化配置的转换可能存在歧义，必须保留人工确认和修正环节。
- **代码生成质量**：Agent 代码由 LLM 直接生成（非模板填充），可能存在编译错误、API 误用、不符合约束等问题，必须通过强上下文约束 + 严格的人工确认与编辑环节兜底。
- **数据归属混淆**：③ 业务代码与 ① 平台的数据边界容易混淆，必须严格遵守"业务数据走流程变量、③ 不建实体表"的约定。
- **组织数据依赖**：审批人解析高度依赖宿主系统组织数据，接口不稳定会直接影响流程运行。
- **老系统兼容**：保留核心语义即可，完全复刻旧接口和字段将显著增加工作量。
- **实习生经验**：项目涉及流程引擎、SPI、Agent、代码生成等较复杂概念，需预留学习和评审时间。建议按 ①→②→③ 顺序分阶段交付。

### 13.2 外部依赖

- 宿主系统提供的组织架构、用户、角色、部门、委托关系等数据。
- 宿主系统或 Mock 提供的认证能力。
- 宿主系统选择的消息推送/回调落地方式（HTTP、消息队列、日志等）。
- Agent 依赖的 LLM 能力（自然语言理解、结构化解析、代码生成）。LLM 选型不在本文档范围，由实现方自行决定，需在代码生成场景下保证输出可控性。
