# 流程平台设计与接口文档 v3

版本：v0.3  
范围：① 流程平台。本文档根据需求文档 11.2 流程平台验收编写，用于指导三名实习生同时推进流程平台编码；第一阶段数据库只覆盖 SQLite。

## 1. 设计边界

1. 平台只负责流程定义、流程实例、任务、历史轨迹、查询、SPI、回调、附件。
2. 平台不包含具体业务逻辑，不感知“入金”“报销”等业务概念。
3. 业务表单值作为流程变量保存。
4. 业务运行期通过 Spring Boot Starter 同进程调用平台。
5. 独立 REST API 用于平台本地运行、调试、管理和 Agent 开发期建流程。
6. 组织、审批人、委托、消息、文件存储通过 SPI 或 Mock 提供。
7. SQLite 为第一阶段实际运行数据库，三人通过复制 SQLite 数据库文件同步本地演示数据；第一阶段不考虑 Oracle 或国产数据库适配。

## 2. 11.2 验收对应设计

| 11.2 验收项                        | 设计位置                                                                                                                                           |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 创建开始、申请、审批、结束流程定义 | 流程定义、节点、连线接口                                                                                                                           |

| 终止流程和删除流程                 | 运行接口、管理接口；删除流程定义时级联删除节点、连线、表单字段、附件模板关联、实例、活动任务、任务组、历史任务、审批意见、已阅、附件记录等运行数据 |
| 驳回、撤回、加签、转办、委托代办   | 任务动作接口                                                                                                                                       |
| 并行、会签、或签、条件分支         | 节点配置、连线条件、任务组                                                                                                                         |

| Starter 嵌入、独立运行             | `platform-starter` 自动装配和 `platform-core` 内 REST 适配；如独立服务形成单独交付物，再拆 Web 模块                                                |
| SQLite 完整运行                    | SQLite 表结构和文件数据库                                                                                                                          |

前五章补充能力在本设计中一并落地：

- 版本治理覆盖发布、激活、停用、归档、灰度发布和关闭灰度。
- 提醒、超时监控、催办、异常告警补充数据模型、Starter 接口和 REST 调试入口。
- 回调第一阶段采用数据库回调日志 + Mock 消息推送落地，HTTP 回调只预留扩展点。

```text
platform-core

  ├── persistence
  │   ├── entity
  │   ├── repository
  │   └── schema
  ├── web
  └── mock

platform-starter
  └── autoconfigure
```

模块收敛规则：

- `platform-core` 是流程平台主体模块，第一阶段承载 API 合约、核心逻辑、SQLite 持久化、REST 适配和本地 Mock。
- `platform-starter` 只负责 Spring Boot 自动装配，依赖 `platform-core`，不重复实现流程逻辑。

## 5. 数据模型

### 5.1 process_definition 流程定义

| 字段              | 说明                                          |
| ----------------- | --------------------------------------------- |
| id                | 主键                                          |
| process_code      | 流程编码                                      |
| process_name      | 流程名称                                      |
| system_code       | 所属系统                                      |
| version           | 版本号                                        |
| definition_status | DRAFT、PUBLISHED、ARCHIVED                    |
| activation_status | INACTIVE、ACTIVE                              |
| gray_status       | OFF、ON                                       |
| gray_rule_config  | 灰度规则 JSON，可按用户、部门、角色、比例命中 |
| archived_by       | 归档信息                                      |
| archived_at       | 归档时间                                      |
| remark            | 备注                                          |
| created_by        | 创建信息                                      |
| created_at        | 创建时间                                      |
| updated_by        | 更新信息                                      |
| updated_at        | 更新时间                                      |

约束：

- `process_code + version` 唯一。
- 同一流程编码允许多版本共存。
- 同一流程编码默认只允许一个全量激活版本；灰度版本可同时开启，但必须配置 `gray_rule_config`。
- 归档版本不可再次激活或灰度发布，只能复制出新草稿版本。

## 6. Starter 服务接口

### 6.1 ProcessDefinitionService

```java
public interface ProcessDefinitionService {
    ProcessDefinitionDTO createDefinition(CreateProcessDefinitionRequest request);

    ProcessDefinitionDTO saveGraph(String definitionId, SaveProcessGraphRequest request);

    ValidationResult validateForPublish(String definitionId);

    ProcessDefinitionDTO publish(String definitionId);

    ProcessDefinitionDTO activate(String definitionId);

    ProcessDefinitionDTO deactivate(String definitionId);

    ProcessDefinitionDTO archive(String definitionId);

    ProcessDefinitionDTO enableGray(GrayReleaseRequest request);

    ProcessDefinitionDTO disableGray(String definitionId);

    ProcessDefinitionDTO copyDefinition(String definitionId, CopyProcessDefinitionRequest request);

    void deleteDefinition(String definitionId);

    ProcessDefinitionDetailDTO getDefinition(String definitionId);

    PageResult<ProcessDefinitionDTO> searchDefinitions(ProcessDefinitionQuery query);

    List<ProcessNodeDTO> listNodes(String definitionId);
}
```

说明：

- `archive` 用于归档已停用或不再使用的流程定义版本。
- `enableGray` 用于开启灰度发布，灰度规则可按用户、部门、角色或比例命中；`disableGray` 用于关闭灰度。
- `deleteDefinition` 删除流程定义时，应级联删除该定义下的节点、连线、表单字段、附件模板关联、实例、活动任务、任务组、历史任务、审批意见、已阅记录、附件记录等运行数据。
- 审计日志和回调日志默认保留，并在详情中标记目标已删除；本地演示环境重置时可物理清理。

### 6.2 ProcessRuntimeService

```java
public interface ProcessRuntimeService {
    ProcessInstanceDTO startProcess(StartProcessRequest request);

    ProcessInstanceDTO startAndSubmit(StartProcessRequest request);

    TaskActionResult submitTask(SubmitTaskRequest request);

    TaskActionResult approve(ApproveTaskRequest request);

    TaskActionResult reject(RejectTaskRequest request);

    TaskActionResult returnToStarter(ReturnTaskRequest request);

    TaskActionResult withdraw(WithdrawTaskRequest request);

    TaskActionResult directSend(DirectSendRequest request);

    TaskActionResult transfer(TransferTaskRequest request);

    TaskActionResult addSign(AddSignRequest request);

    TaskActionResult claim(ClaimTaskRequest request);

    TaskActionResult unclaim(UnclaimTaskRequest request);

    ProcessInstanceDTO terminate(TerminateProcessRequest request);

    void deleteInstance(DeleteProcessInstanceRequest request);

    ProcessInstanceDTO updateVariables(UpdateVariablesRequest request);

    ProcessInstanceDetailDTO getInstance(String instanceId);
}
```

说明：

- `startAndSubmit` 负责启动流程并推进到首个用户任务，即申请节点，返回结果中应包含申请节点任务标识。
- `submitTask` 用于办理申请节点或普通发送动作。
- 办理申请节点时，必须按附件模板校验银行回单。
- 若前端一次提交了表单和附件，业务适配层应先调用 `startAndSubmit`，再使用返回的申请节点任务标识调用 `submitTask` 提交银行回单；平台不在启动请求中写入具体业务逻辑。
- `deleteInstance` 删除流程实例时，应同步删除关联活动任务、任务组、历史任务、审批意见、已阅记录、附件记录等运行数据。

## 12. 核心运行规则

### 12.1 发布前校验

1. 存在且仅存在一个开始节点。
2. 至少存在一个结束节点。
3. 所有连线的来源和目标节点存在。
4. 不存在孤立用户任务节点。
5. 用户任务节点配置审批人规则。
6. 表单字段编码不重复。
7. 同一流程定义版本下附件模板绑定不重复。
8. 流程定义附件模板关联中的适用节点必须存在。
9. 激活前流程状态必须是已发布。

### 12.2 启动流程

1. 根据 `processCode` 查询激活版本；如存在灰度版本，则先按灰度规则判断是否命中。
2. 校验发起人身份。
3. 保存流程变量。
4. 创建流程实例。
5. 沿开始节点连线找到首个用户任务。
6. 创建首个活动任务，即申请节点。
7. 触发流程发起和任务创建回调。
8. 返回实例信息和申请节点任务标识。

### 12.3 办理申请节点

1. 查询申请节点活动任务。
2. 校验办理人为发起人。
3. 校验申请节点附件模板。
4. 银行回单必须上传。
5. 银行回单格式必须为 `pdf/jpg/png`。
6. 银行回单大小不得超过 `10MB`。
7. 文件内容通过文件存储 SPI 保存。
8. 附件元数据写入平台；银行回单保存为实例级附件，后续节点审批人可查看。
9. 申请节点归档为历史任务，动作记为 `SEND`。
10. 根据连线创建部门经理审批任务。
11. 触发任务完成和任务创建回调。

### 12.4 审批通过

1. 查询活动任务并校验办理权限。
2. 保存审批意见。
3. 活动任务归档为历史任务。
4. 判断下一节点。
5. 下一节点为用户任务时，解析审批人并创建活动任务。
6. 下一节点为结束节点时，实例状态改为 `COMPLETED`。
7. 触发回调。

### 12.5 驳回

1. 校验目标节点是否合法。
2. 当前任务归档，动作记为 `REJECT`。
3. 创建目标节点活动任务。
4. 记录驳回来源，用于直送。
5. 触发回调。

### 12.6 撤回

1. 校验撤回人权限。
2. 找到上一历史节点。
3. 取消当前活动任务。
4. 重新创建上一节点活动任务。
5. 写历史或审计记录。
6. 触发回调。

### 12.7 加签

1. 在当前节点增加临时审批任务。
2. 加签任务完成后回到原节点处理。
3. 写历史或审计记录。
4. 触发回调。

### 12.8 转办

1. 校验转办人权限。
2. 修改当前任务办理人或候选人。
3. 写历史或审计记录。
4. 触发回调。

### 12.9 委托代办

1. 通过委托关系 SPI 查询代理人。
2. 待办查询中标记委托来源。
3. 代理人可办理委托任务。
4. 历史任务记录实际办理人和委托来源。

### 12.10 或签

1. 节点可有多个候选人。
2. 任一候选人办理后节点完成。
3. 其他未办理任务取消。
4. 节点继续向后流转。

### 12.11 会签

1. 为多个审批人创建任务。
2. 所有人完成后节点完成。
3. 节点继续向后流转。

### 12.12 并行与汇聚

1. 并行分支节点可同时创建多个后续任务。
2. 汇聚节点等待多个分支完成。
3. 分支全部满足后继续后续流转。

### 12.13 条件分支

1. 按连线顺序判断条件表达式。
2. 条件表达式读取流程变量。
3. 命中条件后创建目标节点任务。

### 12.14 跳转与强制办结

1. 管理员可将流程跳转到指定节点。
2. 管理员可强制办结流程。
3. 操作写审计日志。
4. 操作触发回调。

### 12.15 版本治理

1. 草稿流程定义通过校验后可发布。
2. 已发布流程定义可激活，作为默认运行版本。
3. 已激活流程定义可停用，停用后不再承接新实例。
4. 已停用或不再使用的流程定义可归档，归档后不能再次激活，只能复制出新草稿。
5. 灰度发布必须基于已发布流程定义，并配置灰度规则。
6. 启动流程时先判断灰度规则，命中则使用灰度版本，否则使用默认激活版本。
7. 发布、激活、停用、归档、开启灰度、关闭灰度均写审计日志。

### 12.16 提醒、超时监控与异常告警

1. 创建活动任务时，根据节点 `timeout_config` 计算 `due_at`。
2. 手动催办调用 `remindTask`，通过消息推送 SPI 或 Mock 发送提醒，并写入提醒记录。
3. 超时扫描任务读取 `due_at` 已过期且仍处于活动状态的任务。
4. 超时任务按节点 `reminder_config` 生成自动提醒，按 `timeout_config` 生成异常告警。
5. 回调失败、动作异常等平台异常也应生成异常告警。
6. 告警处理只更新告警状态和处理信息，不直接改变流程实例状态。

## 13. 权限规则

1. 待办只返回当前用户可办理任务。
2. 委托代办任务需要标记委托来源。
3. 附件下载校验当前用户是否有查看权限。
4. 管理动作需要管理员权限。
5. 历史任务保存用户名称、部门名称、委托来源快照。
6. 手动催办仅允许当前任务办理人、流程发起人或管理员触发。
7. 告警处理仅允许管理员执行。

## 16. 入金申请验收用例

### 16.1 准备数据

Mock 用户：

| 用户         | 角色               | 部门         |
| ------------ | ------------------ | ------------ |
| u_sales_01   | salesperson        | sales_dept   |
| u_manager_01 | department_manager | sales_dept   |
| u_finance_01 | finance            | finance_dept |

### 16.2 步骤

1. 创建入金申请流程定义。
2. 保存开始、申请、部门经理审批、财务确认、结束五个节点。
3. 保存四条连线。
4. 保存三个表单字段。
5. 保存银行回单附件模板，并建立流程定义附件模板关联，适用节点为申请节点。
6. 发布并激活流程。
7. 业务员提交表单变量和银行回单，业务适配层调用 `startAndSubmit`。
8. 平台生成申请节点活动任务，并返回申请节点任务标识。
9. 业务适配层继续调用 `submitTask` 办理申请节点，提交银行回单。
10. 平台校验银行回单附件模板并保存为实例级附件。
11. 申请节点归档为历史任务。
12. 平台生成部门经理审批任务。
13. 部门经理审批通过。
14. 平台生成财务确认任务。
15. 财务确认通过。
16. 流程状态为 `COMPLETED`。
17. 查询历史任务包含申请、部门经理审批、财务确认。
18. 查询银行回单作为实例级附件仍可查看。
19. 查询回调记录包含归档任务和新建任务信息。

### 16.3 断言

- 流程定义状态为 `PUBLISHED + ACTIVE`。
- 启动后首个活动任务为申请节点。
- 流程变量包含申请人姓名、入金金额、入金账号。
- `startAndSubmit` 返回申请节点任务标识。
- 申请节点必须校验银行回单。
- 申请节点进入历史任务。
- 部门经理和财务任务按顺序创建。
- 办结后无活动任务。
- 历史任务顺序正确。
- 审批意见可查询。
- 附件元数据存在，银行回单作为实例级附件保存，文件内容通过文件存储 SPI 读取。
- 关键动作产生回调记录。
