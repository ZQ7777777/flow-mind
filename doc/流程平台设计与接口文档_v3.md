# 流程平台设计与接口文档 v3

版本：v0.3  
范围：① 流程平台。本文档根据需求文档 11.2 流程平台验收编写，用于指导三名实习生同时推进流程平台编码；第一阶段数据库只覆盖 SQLite。

## 1. 设计边界

1. 平台只负责流程定义、流程实例、任务、历史轨迹、查询、SPI、回调、附件。
2. 平台不包含具体业务逻辑，不感知“入金”“报销”等业务概念。
3. 业务表单值作为流程变量保存。
4. 业务运行期通过 Spring Boot Starter 同进程调用平台。
5. 独立 REST API 用于平台本地运行、调试、管理和 Agent 开发期建流程。
6. 组织、审批人、委托、消息、文件存储通过 SPI 或 Mock 提供。
7. SQLite 为第一阶段实际运行数据库，三人通过复制 SQLite 数据库文件同步本地演示数据；第一阶段不考虑 Oracle 或国产数据库适配。

前五章补充能力在本设计中一并落地：

- 版本治理覆盖发布、激活、停用、归档、灰度发布和关闭灰度。
- 提醒、超时监控、催办、异常告警补充数据模型、Starter 接口和 REST 调试入口。
- 回调第一阶段采用数据库回调日志 + Mock 消息推送落地，HTTP 回调只预留扩展点。

模块收敛规则：

- `platform-core` 是流程平台主体模块，第一阶段承载 API 合约、核心逻辑、SQLite 持久化、REST 适配和本地 Mock。
- `platform-starter` 只负责 Spring Boot 自动装配，依赖 `platform-core`，不重复实现流程逻辑。

## 5. 数据模型

### 5.1 process_definition 流程定义

| 字段              | 说明                                          |
| ----------------- | --------------------------------------------- |
| id                | 主键                                          |
| process_code      | 流程编码                                      |
| process_name      | 流程名称                                      |
| system_code       | 所属系统                                      |
| version           | 版本号                                        |
| definition_status | DRAFT、PUBLISHED、ARCHIVED                    |
| activation_status | INACTIVE、ACTIVE                              |
| gray_status       | OFF、ON                                       |
| gray_rule_config  | 灰度规则 JSON，可按用户、部门、角色、比例命中 |
| archived_by       | 归档信息                                      |
| archived_at       | 归档时间                                      |
| remark            | 备注                                          |
| created_by        | 创建信息                                      |
| created_at        | 创建时间                                      |
| updated_by        | 更新信息                                      |
| updated_at        | 更新时间                                      |

约束：

- `process_code + version` 唯一。
- 同一流程编码允许多版本共存。
- 同一流程编码默认只允许一个全量激活版本；灰度版本可同时开启，但必须配置 `gray_rule_config`。
- 归档版本不可再次激活或灰度发布，只能复制出新草稿版本。

### 5.2 process_node 节点定义

| 字段                    | 说明                                             |
| ----------------------- | ------------------------------------------------ |
| id                      | 主键                                             |
| definition_id           | 流程定义 ID                                      |
| node_code               | 节点编码                                         |
| node_name               | 节点名称                                         |
| node_type               | START、USER_TASK、EXCLUSIVE_GATEWAY、PARALLEL_SPLIT_GATEWAY、PARALLEL_JOIN_GATEWAY、END |
| paired_gateway_code     | 配对网关节点编码，仅并行分支/汇聚网关使用        |
| approver_rule_type      | 审批人规则类型                                   |
| approver_rule_config    | 审批人规则 JSON                                  |
| multi_instance_mode     | SINGLE、OR_SIGN、COUNTERSIGN                     |
| listener_config         | 节点监听配置 JSON                                |
| timeout_config          | 超时配置 JSON，含超时时长、提醒策略、告警策略    |
| reminder_config         | 催办配置 JSON，含自动提醒频率和目标人            |
| position_x / position_y | 流程图画布坐标，用于保存节点在设计器中的展示位置 |
| sort_order              | 顺序                                             |

说明：

- 入金申请中的申请节点是 `USER_TASK`。
- 申请节点审批人规则为 `STARTER`。
- 申请节点是启动流程后生成的首个活动任务。
- `EXCLUSIVE_GATEWAY` 是条件分支网关，按出线 `sort_order` 依次计算条件并选择一条出线。
- `PARALLEL_SPLIT_GATEWAY` 是并行分支网关，同时激活全部有效出线；`paired_gateway_code` 指向对应的 `PARALLEL_JOIN_GATEWAY`。
- `PARALLEL_JOIN_GATEWAY` 是并行汇聚网关，等待配对分支全部到达后再继续；`paired_gateway_code` 指回对应的 `PARALLEL_SPLIT_GATEWAY`。
- 网关节点不配置审批人规则，也不创建活动任务。
- `APPROVER_EXPRESSION` 仅用于 `USER_TASK` 的审批人动态解析，表达式保存在 `approver_rule_config` 中；它不负责选择流程出线，也不替代 `process_edge.condition_expression`。

### 5.3 process_edge 连线定义

| 字段                 | 说明         |
| -------------------- | ------------ |
| id                   | 主键         |
| definition_id        | 流程定义 ID  |
| edge_code            | 连线编码     |
| source_node_code     | 来源节点     |
| target_node_code     | 目标节点     |
| condition_expression | 条件表达式   |
| default_edge         | 是否默认出线 |
| sort_order           | 条件判断顺序 |

说明：

- `EXCLUSIVE_GATEWAY` 的非默认出线通过 `condition_expression` 判断，表达式只读取流程变量和当前上下文。
- 同一个 `EXCLUSIVE_GATEWAY` 最多只能有一条 `default_edge=true` 的出线；所有条件均未命中时走默认出线，没有默认出线则流转失败。
- `PARALLEL_SPLIT_GATEWAY` 的出线不计算 `condition_expression`，全部作为独立分支激活。

### 5.8 process_active_task 活动任务

| 字段                  | 说明                 |
| --------------------- | -------------------- |
| id                    | 主键                 |
| instance_id           | 流程实例 ID          |
| definition_id         | 流程定义 ID          |
| node_code             | 节点信息             |
| candidate_user_ids    | 候选人 JSON          |
| assignee_user_id      | 办理人或认领人       |
| assignee_user_name    | 办理人名称快照       |
| delegate_from_user_id | 委托来源用户         |
| task_status           | ACTIVE、CLAIMED、COMPLETED、CANCELED |
| task_group_id         | 会签、或签、并行分组 |
| branch_key            | 并行分支标识，可空   |
| lock_version          | 乐观锁版本，默认 0   |
| created_at            | 创建时间             |
| due_at                | 超时时间             |

说明：

- 认领、取消认领和转办通过 `id + task_status + lock_version` 条件更新任务；受影响行数为 0 表示任务已被其他请求修改。
- 提交、审批、驳回等完成类动作先以乐观锁将任务改为 `COMPLETED` 或 `CANCELED`，再在同一事务内写历史任务并从活动任务表移除；终态只作为事务内的并发控制状态。

### 5.9 process_task_group 任务组

用于支持会签、或签、并行和汇聚。

| 字段              | 说明                                             |
| ----------------- | ------------------------------------------------ |
| id                | 主键                                             |
| instance_id       | 流程实例 ID                                      |
| node_code         | 会签/或签用户节点或并行分支网关节点编码          |
| join_node_code    | 配对的并行汇聚网关节点编码，仅并行网关组使用     |
| parent_group_id   | 外层并行任务组 ID，非嵌套并行时为空              |
| parent_branch_key | 当前并行组在外层任务组中的分支标识，可空         |
| group_type        | OR_SIGN、COUNTERSIGN、PARALLEL_GATEWAY           |
| total_count       | 总任务数或并行分支总数                           |
| completed_count   | 已完成任务数或已到达汇聚网关的分支数             |
| branch_state_json | 并行分支状态 JSON，仅并行网关组使用              |
| group_status      | ACTIVE、COMPLETED、CANCELED                      |
| lock_version      | 乐观锁版本，防止多个分支同时到达时重复完成汇聚   |
| created_at        | 创建时间                                         |
| completed_at      | 完成时间                                         |

说明：

- `branch_state_json` 示例：`[{"branchKey":"edge_a","status":"RUNNING"},{"branchKey":"edge_b","status":"ARRIVED"}]`。
- 并行分支从分支网关开始，后续创建的活动任务继续携带同一个 `task_group_id` 和各自的 `branch_key`，直到到达 `join_node_code`。
- 分支到达汇聚网关时以 `task_group_id + branch_key` 幂等更新分支状态，并通过 `lock_version` 原子递增 `completed_count`；仅最后一个到达的分支负责继续向后推进。
- 嵌套并行通过 `parent_group_id + parent_branch_key` 保存外层分支上下文；内层汇聚完成后恢复外层任务组和分支标识继续推进。
- `OR_SIGN` 通过 `group_status=ACTIVE + lock_version` 原子竞争完成权，只有第一个成功将任务组改为 `COMPLETED` 的请求可以推进流程。
- `COUNTERSIGN` 通过 `lock_version` 原子增加 `completed_count`；仅将计数更新到 `total_count` 的请求可以完成任务组并推进流程。

### 5.17 process_operation_record 操作幂等记录

| 字段             | 说明                                                    |
| ---------------- | ------------------------------------------------------- |
| id               | 主键                                                    |
| operation_id     | 调用方生成的操作幂等号，全局唯一                        |
| instance_id      | 流程实例 ID，可空                                       |
| task_id          | 活动任务 ID，可空                                       |
| action_type      | 操作类型                                                |
| operator_id      | 操作人                                                  |
| request_hash     | 规范化请求内容的哈希，用于识别同号不同请求              |
| operation_status | PROCESSING、SUCCESS、FAILED                             |
| result_json      | 成功结果快照，重复请求直接返回                           |
| error_code       | 已落库失败结果的错误码，可空                             |
| processing_expires_at | PROCESSING 租约截止时间，用于进程异常后的安全接管   |
| expires_at       | 幂等记录保留截止时间                                     |
| created_at       | 创建时间                                                |
| updated_at       | 更新时间                                                |

约束：

- `operation_id` 唯一，所有会修改流程定义、实例、任务、附件或管理状态的请求都必须携带该字段。
- 相同 `operation_id + request_hash` 再次请求时，`SUCCESS` 直接返回 `result_json`；未超过 `processing_expires_at` 的 `PROCESSING` 返回处理中状态；租约已过期时允许同一请求原子接管并继续；已记录的 `FAILED` 返回原错误。需要重新执行业务操作时必须生成新的 `operation_id`。
- 相同 `operation_id` 携带不同 `request_hash` 时拒绝执行，返回幂等号冲突错误。
- 任务状态更新、历史归档、任务组更新、下一任务创建、审计日志、回调日志和操作结果必须在同一数据库事务内提交。事务异常整体回滚时不得留下部分成功数据。
- `instance_id`、`task_id` 为逻辑关联，不配置级联删除外键。删除实例或流程定义后，操作记录至少保留到 `expires_at`，以便删除请求重试时返回原结果；过期后由清理任务删除。

## 12. 核心运行规则

### 12.0 事务、并发与幂等规则

所有会修改流程状态的 Service 方法先执行本节规则，再执行各动作的业务规则：

1. 调用方为一次业务操作生成全局唯一 `operationId`。平台对去除时间戳等非业务字段后的规范化请求计算 `request_hash`，在短事务中插入 `process_operation_record(PROCESSING)` 并设置 `processing_expires_at`；`operation_id` 唯一约束是幂等入口。
2. `operationId` 已存在且 `request_hash` 相同时：状态为 `SUCCESS` 直接反序列化并返回 `result_json`；`PROCESSING` 且租约未过期时返回操作处理中；租约过期时通过条件更新原子接管；状态为 `FAILED` 返回已记录错误。哈希不一致时返回幂等号冲突，禁止复用该幂等号执行另一请求。
3. 任务级操作读取 `process_active_task.lock_version`，并通过 `id + 当前允许状态 + expectedTaskVersion` 条件更新任务。提交、审批、驳回等完成类动作将任务更新为 `COMPLETED`；撤回、或签取消等取消类动作更新为 `CANCELED`；认领、取消认领和转办只修改任务状态或办理人。受影响行数必须为 1。
4. 条件更新受影响行数为 0 时，先按 `operationId` 查询是否为同一请求的成功重试；不是重试则将本次操作记录为 `FAILED/FLOW_TASK_CONCURRENT_MODIFIED`，禁止继续写历史任务、任务组、下一任务或回调。
5. 任务组更新同样使用 `group_status + lock_version` 条件更新。乐观锁冲突时重新读取最新任务组；仅在业务条件仍允许时有限次重试，超过重试次数将操作记录为 `FAILED/FLOW_TASK_GROUP_CONCURRENT_MODIFIED`，不得无上限自旋。
6. 活动任务条件更新、历史任务写入、任务组计数、下一任务创建、实例状态更新、审计日志、回调日志以及 `process_operation_record` 的 `SUCCESS + result_json` 更新必须在同一数据库事务内完成。
7. 事务回滚时上述数据全部回滚；同步外部 SPI 调用不得夹在任务抢占与事务提交之间。回调和消息推送先在事务内写待处理记录，提交后异步发送。
8. 成功事务生成的每个回调使用稳定且唯一的 `event_id`；重复 `operationId` 直接返回原结果，不重新生成下一任务、历史记录或回调事件。
9. 权限不足、状态不允许、并发冲突等确定性失败应更新幂等记录为 `FAILED` 并保存 `error_code`；进程异常或数据库连接中断等不确定失败保留 `PROCESSING`，租约到期后由相同请求接管重试。

任务完成类动作的条件更新语义如下：

```sql
UPDATE process_active_task
SET task_status = 'COMPLETED',
    lock_version = lock_version + 1
WHERE id = :taskId
  AND task_status IN ('ACTIVE', 'CLAIMED')
  AND lock_version = :expectedTaskVersion;
```

任务组计数更新必须同时检查活动状态和版本号；并行汇聚还必须确认当前 `branch_key` 尚未到达，避免同一分支重复增加计数：

```sql
UPDATE process_task_group
SET completed_count = completed_count + 1,
    branch_state_json = :newBranchStateJson,
    group_status = CASE
        WHEN completed_count + 1 = total_count THEN 'COMPLETED'
        ELSE group_status
    END,
    lock_version = lock_version + 1
WHERE id = :taskGroupId
  AND group_status = 'ACTIVE'
  AND completed_count < total_count
  AND lock_version = :expectedGroupVersion;
```

### 12.1 发布前校验

1. 存在且仅存在一个开始节点。
2. 至少存在一个结束节点。
3. 同一流程定义版本下节点编码、连线编码分别唯一，所有连线的来源和目标节点存在。
4. 不存在孤立用户任务节点，`START` 和 `USER_TASK` 节点只能有一条出线；需要分支时必须显式配置网关。
5. 用户任务节点必须配置审批人规则，网关节点不得配置审批人规则或多人处理模式。
6. `EXCLUSIVE_GATEWAY` 至少有两条出线，最多一条默认出线；非默认出线必须配置条件表达式。
7. `PARALLEL_SPLIT_GATEWAY` 至少有两条出线，必须配置存在且类型正确的配对 `PARALLEL_JOIN_GATEWAY`，其出线不得配置条件表达式。
8. `PARALLEL_JOIN_GATEWAY` 至少有两条入线且只能有一条出线，必须与 `PARALLEL_SPLIT_GATEWAY` 双向配对；分支网关的每条路径必须能够到达该汇聚网关。
9. 表单字段编码不重复。
10. 同一流程定义版本下附件模板绑定不重复。
11. 流程定义附件模板关联中的适用节点必须存在。
12. 激活前流程状态必须是已发布。

### 12.2 启动流程

1. 根据 `processCode` 查询激活版本；如存在灰度版本，则先按灰度规则判断是否命中。
2. 校验发起人身份。
3. 保存流程变量。
4. 创建流程实例。
5. 读取开始节点的唯一出线，将目标节点交给 12.4.1 通用节点推进规则。
6. 推进过程可经过条件网关或并行网关，直到创建一个或多个首批用户任务或直接到达结束节点。
7. 触发流程发起回调；对推进过程中创建的每个用户任务触发任务创建回调，网关节点不产生任务回调。
8. 返回实例信息和 `createdTasks`；入金申请基准流程中首批任务只有申请节点任务。

### 12.3 办理申请节点

1. 按 12.0 校验 `operationId`，查询申请节点活动任务并校验办理人为发起人。
2. 校验申请节点附件模板，银行回单必须上传，格式必须为 `pdf/jpg/png`，大小不得超过 `10MB`。文件内容在任务状态事务开始前通过文件存储 SPI 暂存，存储键包含 `operationId`，同一请求重试不得重复生成文件。
3. 开启数据库事务，使用 `expectedTaskVersion` 条件更新活动任务；只有成功将任务更新为 `COMPLETED` 的请求继续执行。乐观锁失败时回滚事务并清理本次未被引用的暂存文件。
4. 附件元数据写入平台，银行回单保存为实例级附件，后续节点审批人可查看；事务提交失败时按 `operationId` 补偿清理暂存文件。
5. 申请节点归档为历史任务，动作记为 `SEND` 并写入 `operation_id`。
6. 读取申请节点的唯一出线，将目标节点交给 12.4.1 通用节点推进规则；入金申请基准流程将创建部门经理审批任务，如果中间存在网关则先完成网关处理。
7. 在事务内写任务完成回调记录，并在 `createdTasks` 中携带本次推进实际创建的全部任务；保存操作成功结果后提交事务。

### 12.4 审批通过

1. 按 12.0 校验 `operationId`，查询活动任务并校验办理权限。
2. 使用 `expectedTaskVersion` 条件更新活动任务；只有成功将任务更新为 `COMPLETED` 的请求获得本次任务处理权。
3. 保存审批意见，将活动任务归档为历史任务并写入 `operation_id`。
4. 若当前节点是或签/会签节点，按 12.10 或 12.11 以任务组乐观锁判断该节点是否满足完成条件；未取得任务组推进权时不向后推进。
5. 当前节点满足完成条件且当前请求取得推进权后，读取其唯一出线，将目标节点交给 12.4.1 通用节点推进规则。
6. 推进到用户任务时解析审批人并创建活动任务；推进到条件网关时选择一条出线；推进到并行分支网关时创建多个分支；推进到并行汇聚网关时等待全部分支；推进到结束节点时办结实例。
7. 在事务内写任务完成回调记录，`createdTasks` 携带推进过程中实际创建的全部活动任务；到达结束节点时同时写流程办结回调记录。保存操作成功结果后提交事务。

#### 12.4.1 通用节点推进规则

所有会改变当前节点的动作统一调用 `advanceToNode(instanceId, targetNodeCode, taskGroupId, branchKey)`，避免启动、审批、会签、跳转分别实现不同的网关逻辑：

1. 目标为 `USER_TASK`：解析审批人并创建活动任务；若处于并行分支，活动任务继承 `taskGroupId` 和 `branchKey`，随后停止本条路径的自动推进。
2. 目标为 `EXCLUSIVE_GATEWAY`：按出线 `sort_order` 依次计算非默认出线的 `condition_expression`，选择第一条命中的出线；均未命中时选择默认出线；仍无可用出线则抛出流程流转异常。选定后递归推进到该出线的目标节点。
3. 目标为 `PARALLEL_SPLIT_GATEWAY`：创建 `PARALLEL_GATEWAY` 任务组，以每条出线的 `edge_code` 作为 `branchKey` 初始化分支状态，并对全部出线分别递归推进；嵌套并行时在新任务组中保存外层 `taskGroupId + branchKey`。
4. 目标为 `PARALLEL_JOIN_GATEWAY`：校验当前 `taskGroupId` 对应的 `join_node_code` 与目标节点一致，以 `taskGroupId + branchKey` 幂等标记当前分支到达；尚有分支未到达时结束当前路径，不创建任务；全部分支到达时由最后一个成功更新任务组的线程将任务组置为 `COMPLETED`，恢复外层分支上下文并沿汇聚网关唯一出线继续推进。
5. 目标为 `END`：确认不存在尚未完成的活动任务或并行任务组后，将实例状态改为 `COMPLETED` 并写入结束时间。
6. 目标为 `START`：除流程初始化外禁止进入，视为流程定义或流转异常。
7. 单次推进必须记录已访问的自动节点并设置最大推进步数，发现无任务闭环或超过上限时终止事务，避免网关环路导致无限递归。
8. 同一次推进在一个事务中完成；任务组状态更新使用 `lock_version`，保证多个分支同时到达汇聚网关时只推进一次。

### 12.5 驳回

1. 校验目标节点属于当前流程定义版本且类型为 `USER_TASK`；驳回不得直接指向开始、网关或结束节点。
2. 当前任务归档，动作记为 `REJECT`。
3. 创建目标节点活动任务。
4. 记录驳回来源，用于直送。
5. 触发回调。

### 12.6 撤回

1. 校验撤回人权限。
2. 找到上一历史节点。
3. 取消当前活动任务。
4. 重新创建上一节点活动任务。
5. 写历史或审计记录。
6. 触发回调。

### 12.7 加签

1. 在当前节点增加临时审批任务。
2. 加签任务完成后回到原节点处理。
3. 写历史或审计记录。
4. 触发回调。

### 12.8 转办

1. 校验转办人权限。
2. 修改当前任务办理人或候选人。
3. 写历史或审计记录。
4. 触发回调。

### 12.9 委托代办

1. 通过委托关系 SPI 查询代理人。
2. 待办查询中标记委托来源。
3. 代理人可办理委托任务。
4. 历史任务记录实际办理人和委托来源。

### 12.10 或签

1. 节点可有多个候选人。
2. 任一候选人完成自己的活动任务后，使用 `group_status=ACTIVE + lock_version` 条件将任务组原子更新为 `COMPLETED`；受影响行数为 1 的请求获得唯一推进权。
3. 获得推进权的请求将同组其他未办理任务以各自 `lock_version` 更新为 `CANCELED` 并归档；未获得推进权的并发请求不得再次推进。
4. 获得推进权的请求调用 12.4.1 通用节点推进规则，后续节点可以是用户任务、条件网关、并行网关或结束节点。

### 12.11 会签

1. 为多个审批人创建任务。
2. 每个审批人完成自己的活动任务后，通过 `group_status=ACTIVE + lock_version` 条件原子增加 `completed_count`；冲突时读取新版本并有限次重试。
3. 只有将 `completed_count` 更新到 `total_count` 的请求才能同时把任务组更新为 `COMPLETED` 并获得唯一推进权，其余请求只归档自己的任务。
4. 获得推进权的请求调用 12.4.1 通用节点推进规则，后续节点可以是用户任务、条件网关、并行网关或结束节点。

### 12.12 并行与汇聚

1. 流程到达 `PARALLEL_SPLIT_GATEWAY` 时，为该网关创建 `PARALLEL_GATEWAY` 任务组，`total_count` 等于出线数量，`join_node_code` 来自分支网关的 `paired_gateway_code`。
2. 每条出线以自身 `edge_code` 作为 `branch_key`，分别调用 12.4.1；分支可经过多个用户任务或条件网关，沿途任务持续携带任务组和分支标识。
3. 分支到达配对的 `PARALLEL_JOIN_GATEWAY` 时不创建活动任务，只将对应分支从 `RUNNING` 幂等更新为 `ARRIVED`，并原子递增 `completed_count`。
4. `completed_count < total_count` 时该分支停止推进，实例的 `current_node_codes` 仍保留其他活动分支节点。
5. `completed_count = total_count` 时仅最后一个到达的分支完成任务组，并沿汇聚网关唯一出线继续推进；并行任务组不得被重复完成。
6. 并行分支中任一任务驳回、终止或管理员跳转时，必须在同一事务中更新对应分支和任务组状态，不能只修改单条活动任务。

### 12.13 条件分支

1. 条件分支必须使用 `EXCLUSIVE_GATEWAY`，普通用户任务不直接配置多条条件出线。
2. 按出线 `sort_order` 判断 `condition_expression`，表达式只读取流程变量和当前流程上下文。
3. 选择第一条命中的非默认出线；全部未命中时走唯一默认出线；没有可用出线时流转失败并回滚当前事务。
4. 命中出线后调用 12.4.1 继续推进，因此网关后仍可连接用户任务、其他条件网关、并行分支网关或结束节点。

### 12.14 跳转与强制办结

1. 管理员可将流程跳转到当前流程定义版本中的指定节点；目标为用户任务时创建任务，目标为网关时调用 12.4.1 继续推进，目标为结束节点时办结实例，禁止跳转到开始节点。
2. 管理员可强制办结流程。
3. 跳转前必须取消受影响的活动任务，并同步取消或重建相关并行任务组，避免遗留孤立分支。
4. 操作写审计日志。
5. 操作触发回调，回调携带本次取消、归档和新建的任务集合。

### 12.15 版本治理

1. 草稿流程定义通过校验后可发布。
2. 已发布流程定义可激活，作为默认运行版本。
3. 已激活流程定义可停用，停用后不再承接新实例。
4. 已停用或不再使用的流程定义可归档，归档后不能再次激活，只能复制出新草稿。
5. 灰度发布必须基于已发布流程定义，并配置灰度规则。
6. 启动流程时先判断灰度规则，命中则使用灰度版本，否则使用默认激活版本。
7. 发布、激活、停用、归档、开启灰度、关闭灰度均写审计日志。

### 12.16 提醒、超时监控与异常告警

1. 创建活动任务时，根据节点 `timeout_config` 计算 `due_at`。
2. 手动催办调用 `remindTask`，通过消息推送 SPI 或 Mock 发送提醒，并写入提醒记录。
3. 超时扫描任务读取 `due_at` 已过期且仍处于活动状态的任务。
4. 超时任务按节点 `reminder_config` 生成自动提醒，按 `timeout_config` 生成异常告警。
5. 回调失败、动作异常等平台异常也应生成异常告警。
6. 告警处理只更新告警状态和处理信息，不直接改变流程实例状态。

## 13. 权限规则

1. 待办只返回当前用户可办理任务。
2. 委托代办任务需要标记委托来源。
3. 附件下载校验当前用户是否有查看权限。
4. 管理动作需要管理员权限。
5. 历史任务保存用户名称、部门名称、委托来源快照。
6. 手动催办仅允许当前任务办理人、流程发起人或管理员触发。
7. 告警处理仅允许管理员执行。

## 15. 第一阶段接口冻结清单

## 16. 入金申请验收用例

### 16.1 准备数据

Mock 用户：

| 用户         | 角色               | 部门         |
| ------------ | ------------------ | ------------ |
| u_sales_01   | salesperson        | sales_dept   |
| u_manager_01 | department_manager | sales_dept   |
| u_finance_01 | finance            | finance_dept |

### 16.2 步骤

1. 创建入金申请流程定义。
2. 保存开始、申请、部门经理审批、财务确认、结束五个节点。
3. 保存四条连线。
4. 保存三个表单字段。
5. 保存银行回单附件模板，并建立流程定义附件模板关联，适用节点为申请节点。
6. 发布并激活流程。
7. 业务员提交表单变量和银行回单，业务适配层调用 `startAndSubmit`。
8. 平台生成申请节点活动任务，并返回申请节点任务标识。
9. 业务适配层继续调用 `submitTask` 办理申请节点，提交银行回单。
10. 平台校验银行回单附件模板并保存为实例级附件。
11. 申请节点归档为历史任务。
12. 平台生成部门经理审批任务。
13. 部门经理审批通过。
14. 平台生成财务确认任务。
15. 财务确认通过。
16. 流程状态为 `COMPLETED`。
17. 查询历史任务包含申请、部门经理审批、财务确认。
18. 查询银行回单作为实例级附件仍可查看。
19. 查询回调记录包含归档任务和新建任务信息。

### 16.3 断言

- 流程定义状态为 `PUBLISHED + ACTIVE`。
- 启动后首个活动任务为申请节点。
- 流程变量包含申请人姓名、入金金额、入金账号。
- `startAndSubmit` 返回申请节点任务标识。
- 申请节点必须校验银行回单。
- 申请节点进入历史任务。
- 部门经理和财务任务按顺序创建。
- 办结后无活动任务。
- 历史任务顺序正确。
- 审批意见可查询。
- 附件元数据存在，银行回单作为实例级附件保存，文件内容通过文件存储 SPI 读取。
- 关键动作产生回调记录。

## 17. 11.2 其他验收用例清单

除入金申请外，还需准备以下用例：

1. 终止流程。
2. 删除流程或实例。
3. 驳回到指定节点。
4. 撤回到上一历史节点。
5. 加签。
6. 转办。
7. 委托代办。
8. 或签。
9. 会签。
10. 并行分支和汇聚：分支网关同时创建多个分支任务；部分分支到达时不得提前推进；全部分支到达时只创建一次后续任务。
11. 条件分支：命中第一条条件时走对应出线；全部未命中时走默认出线；没有默认出线时返回 `FLOW_GATEWAY_NO_MATCH` 并回滚。
12. 任意节点跳转。
13. 强制办结。
14. 回调异常不影响主流程。
15. 版本治理：停用、归档、灰度发布、关闭灰度。
16. 手动催办、超时扫描、异常告警处理。
17. 任务并发：使用两个不同 `operationId` 和相同 `expectedTaskVersion` 同时审批一条任务，只允许一个请求成功；只能产生一条对应历史记录和一组后续任务。
18. 请求幂等：相同 `operationId` 重复提交审批、发起或删除请求时返回第一次结果，不重复更新任务组、不重复创建下一任务和回调事件；同号不同请求必须返回 `FLOW_OPERATION_ID_CONFLICT`。
