# 三阶段业务系统文件结构设计

## 1. 目标

本文档固化 `flow-mind` 从 ① 流程平台、② Agent Web 到 ③ 业务流程代码的最终文件结构，确保：

- ① 流程平台、② Agent Web、③ 业务运行期系统三块产物边界清晰。
- ② 生成的代码只落在 ③ 的生成白名单目录中。
- ③ 基础底座代码与 ② 生成的业务代码共同构成最终业务系统。
- ③ 不建业务实体表，业务表单值统一作为 ① 平台流程变量存储。

## 2. 当前结构结论

当前仓库已经存在两块产物：

- `platform/`：① 流程平台，包含 `platform-core` 与 `platform-starter`。
- `agent-web/`：② Agent Web，目前已实现 M0-M2，包含需求对话、结构化需求门禁、流程平台草稿落地、流程预览、发布和激活能力。

当前缺少独立的 ③ 业务流程代码根目录。③ 应作为与 `platform/`、`agent-web/` 同级的运行期业务系统工程，而不是放进 ① 或 ② 内部。

## 4. 三块职责边界

### 4.1 ① `platform/`

`platform/` 是流程平台底座，只负责流程定义、流程实例、任务、历史、附件、回调、SPI、管理运维和 Starter 封装。

约束：

- 不放入金申请、报销等具体业务语义。
- 不承担 Agent 对话和代码生成职责。
- `platform-starter` 是 ③ 后端调用 ① 的唯一运行期集成方式。

### 4.2 ② `agent-web/`

`agent-web/` 是开发期生产者。它负责对话采集、结构化需求确认、调用 ① 创建流程定义，并在人工确认后把业务代码写入 ③。

约束：

- 不参与业务运行期。
- 不生成待办、已办、我发起、已阅、审批详情、审批动作、流程轨迹等通用能力。
- 不直接改写 ③ 非白名单目录。
- M3-M6 只新增生成、校验、验证、审核、修复和安全写入能力。

### 4.3 ③ `business-base/`

`business-base/` 是最终业务系统。它由两层共同构成：

- 基础底座：只开发一次，提供通用业务后端与通用 Vue3 前端。
- 业务产物：由 ② 按具体业务生成，只包含业务发起页面、业务发起后端和相关测试。

约束：

- 后端通过 `platform-starter` 同进程调用 ①。
- 前端不直接调用 ① 平台。
- 不维护业务实体表、Mapper、Repository、业务库建表语句或业务数据库迁移脚本。
- 业务表单值、附件元数据、流程实例、任务和历史轨迹全部归属 ① 平台。

## 5. ② 写入 ③ 的白名单

② 只能写入以下路径：

```text
business-base/backend/src/main/java/com/flowmind/business/generated/**
business-base/backend/src/test/java/com/flowmind/business/generated/**
business-base/frontend/src/modules/generated/**
business-base/frontend/src/api/generated/**
business-base/frontend/src/router/generated-routes.ts
```

其中：

- `backend/src/main/java/com/flowmind/business/generated/**` 存放业务 Controller、Service 和 DTO。
- `backend/src/test/java/com/flowmind/business/generated/**` 存放生成业务后端测试。
- `frontend/src/modules/generated/**` 存放业务录入页。
- `frontend/src/api/generated/**` 存放业务 API 客户端。
- `frontend/src/router/generated-routes.ts` 是生成业务页面进入 ③ 通用前端的路由注册点。

② 不允许写入：

- `platform/**`
- `agent-web/**` 的非 Agent 自身实现目录
- `business-base/backend/src/main/java/com/flowmind/business/workflow/**`
- `business-base/backend/src/main/java/com/flowmind/business/platform/**`
- `business-base/backend/pom.xml`
- `business-base/frontend/package.json`
- `.git/**`
- `.env` 或任何凭据文件

## 6. 入金申请组合方式

入金申请作为首个验收业务时，最终由以下文件共同运行：

```text
business-base/backend/src/main/java/com/flowmind/business/workflow/**          # ③ 基座通用能力
business-base/backend/src/main/java/com/flowmind/business/platform/**          # ③ 基座 Starter 封装
business-base/backend/src/main/java/com/flowmind/business/generated/**         # ② 生成业务发起后端

business-base/frontend/src/views/**                                           # ③ 基座通用页面
business-base/frontend/src/api/workflow.ts                                    # ③ 基座通用 API
business-base/frontend/src/modules/generated/entry-application/**             # ② 生成入金申请录入页
business-base/frontend/src/api/generated/**                                   # ② 生成业务 API
business-base/frontend/src/router/generated-routes.ts                         # ② 生成路由注册
```

运行链路：

1. 用户在 ③ 通用前端中打开入金申请录入页。
2. 录入页调用 ② 生成的业务 API 客户端。
3. 业务 API 客户端调用 ② 生成的后端发起接口。
4. 生成后端只调用 `ProcessRuntimeService.startAndSubmit()`，写入流程变量和附件并推进到下一用户节点。
5. 后续待办、审批详情、审批动作、附件查看、流程轨迹和办结全部由 ③ 基座通用能力调用 ① 平台完成。

## 7. 实施顺序

1. 保留现有 `platform/` 与 `agent-web/` 结构。
2. 新建 `business-base/` 目录骨架。
3. 先实现 ③ 基础底座的通用业务后端、通用前端、可信身份接口、路由注册点和 `.flowmind/generation-target.json`。
4. 再实现 ② M3-M6，使 Agent 根据目标契约生成代码、验证代码并安全写入 ③。
5. 最后由 ② 生成入金申请业务产物，与 ③ 基础底座共同跑通完整业务流程。
